# AI 变的越来越懂你，也学会了你的烂习惯——@database 和记忆感知的双刃剑

**写在前面：**

大概用 Qoder 一个月之后，我注意到一个现象——它开始"猜"我接下来要写什么了。不是那种 IDE 补全式的"你写了 `import` 它猜你后面要写什么"，而是"你做了一个数据库表变更，它自动在你还没说的文件里也做了同步修改。"

一开始我以为是自己记错了——可能我确实提过这个要求。后来专门留意了一下，发现 Qoder 确实在"学习"我的编码习惯，而且学得很快。

这就是记忆感知的效果。

同时，我还在用一个叫 @database 的功能——让 AI 直接看数据库结构，不用我每次手动描述表结构。这两个功能结合之后，Qoder 从一个"听指令干活的助手"变成了一个"大概知道你在干嘛的同事"。这是好事，但也有一个不小的坑。

---

## 一、@database —— 终于不用再手动描述表结构了

如果你是后端开发者，下面这个场景你一定熟悉：

**以前的工作流：**

> 你："我要在 users 表加一个 status 字段，然后修改相关的查询逻辑"
> AI："请描述 users 表的当前结构"
> 你：粘贴一大段 SQL DDL → "这里有 15 个字段，其中 phone 和 email 有唯一索引……"
> AI："明白了。那 status 字段的具体要求是？"
> 你："枚举类型，值包括 active/inactive/banned，默认 active……"

（这个过程占用了整个对话的一半时间。）

**有了 @database 之后：**

> 你："在 users 表加一个 status 字段（枚举 active/inactive/banned，默认 active），同步改所有查询逻辑"
> AI：通过 @database 直接读到表结构 → 知道 phone/email 有唯一索引 → 知道有哪些查询接口依赖 users 表 → 生成完整的变更方案

**沟通成本直接砍半。**

---

## 二、@database 怎么用——比你想象的简单

支持两种方式连接数据库：

**方式一：IDE 内置数据库工具连接。**

在 VS Code 左侧的数据库面板里连上你的开发数据库（MySQL / PostgreSQL / SQLite / MongoDB 都支持）。然后跟 AI 对话时，带上 `@database` 标记，AI 会自动读取连上的数据库结构。

**方式二：直接给 DDL 文件路径。**

如果你不想给 AI 完整的数据库连接权限（这个考虑在上一篇文章的 MCP 部分也提到过），可以只把 DDL 文件加到上下文中：

> @file:db/schema.sql 帮我在这个数据库结构上做以下变更……

**两种方式的对比：**

| | 方式一：数据库连接 | 方式二：DDL 文件 |
|---|---|---|
| 实时性 | AI 能直接查表的实际状态 | 只是文件里写的结构 |
| 安全性 | AI 有数据库访问权限 | AI 只能看文件内容 |
| 方便程度 | 一句话搞定 | 每次要手动加文件 |

我日常工作用方式一（开发环境无所谓），但正式项目代码提交前的变更审查用方式二（减少不必要的数据库访问）。

**TypeORM / MyBatis 用户不需要 @database。**

如果你的项目用 TypeORM（Entity 定义）、MyBatis（XML 映射）或 Prisma（schema 文件），Qoder 直接读这些 ORM 定义就能知道数据库结构——不需要额外连接数据库。这也是为什么 @database 功能对于裸 SQL 项目特别有用，对于 ORM 项目反而没那么必要。

## 三、实操演示——改一个真实需求看看效率差距

**需求：** "用户注册时，邮箱和手机号至少填一个。现在改逻辑，要求必须两个都填。"

### 没有 @database 的工作流：

1. 我："帮我在注册逻辑里加邮箱和手机号都必填的校验"
2. AI："请提供 users 表结构和现有的注册逻辑"（第一轮）
3. 我：粘贴 DDL → 粘贴 register service 代码
4. AI：给了变更方案，但忽略了索引信息——email 字段有 unique 约束，它建议的校验方式会跟 unique 约束冲突（第二轮）
5. 我："email 有 unique 约束，你要考虑并发注册的冲突"
6. AI：重新给了方案，引入了显式锁（第三轮）
7. 我检查通过 → 完成

**4 轮对话，大概 8 分钟。**

### 有 @database 的工作流：

1. 我："@database 帮我改注册逻辑，要求邮箱和手机号都必须填，注意 email 有 unique 索引"
2. AI：通过 @database 查到 users 表的所有字段和索引 → 看到 email 的 unique 约束 → 建议方案包含并发冲突处理
3. 我检查通过 → 完成

**1 轮对话，大概 2 分钟。**

省了 75% 的时间。这不仅仅是"快"，更重要的是——中间少了两轮"我来纠正 AI 的理解偏差"。当你一天要做十几次这样的数据变更时，累计节省的时间非常可观。

## 四、记忆感知——AI 在偷偷学你的编码习惯

说完了 @database，来说一个更隐蔽但更本质的功能：记忆感知。

Qoder 的记忆感知指的是——它会从你的代码库和对话历史中提取模式，在你没明确说的情况下，**按照你的习惯来生成代码。**

举几个实际例子：

**例子一：变量命名风格。**

我的习惯是用 `camelCase`，而且变量名偏长（比如 `userRegistrationStatus` 而不是 `regStatus`）。用 Qoder 第一个星期，它生成的都是短变量名。第二周开始，它自动生成的都是长变量名——跟我的风格一致。

**例子二：错误处理方式。**

我习惯用 `try-catch` + 自定义异常类，而不是返回错误码。Qoder 在记住这个习惯之后，所有的 Agent 生成代码都默认用异常处理——不需要我每次提醒。

**例子三：项目架构偏好。**

我的 NestJS 项目里每个模块都分 controller / service / repository 三层。Qoder 记住了这个结构之后，每次新增功能都会自动在三层里分别创建对应代码——不需要我说"别忘了在 repository 层也加"。

## 五、坏习惯也会被学到——这是记忆感知最大的坑

上面说的都是好事，但记忆感知有一个非常现实的负面效果：**你的坏习惯也会被学到。**

比如我有一个不太好的习惯——异常处理的时候经常忘记写 `finally` 块来释放资源。Qoder 用了两个月之后，我发现它生成的代码也开始缺少 `finally`——因为它"学到"了我不写。

还有一个更严重的——我习惯在 Controller 层做一些轻量的数据转换（应该放在 Service 层做的事）。Qoder 记住之后，生成的新 Controller 代码也越来越臃肿，Service 层越来越薄。这是我自己的坏架构习惯被 AI 放大。

**怎么避免？两招：**

**1. 定期让 AI "忘记"。**

在设置里可以清除记忆感知的数据，重置 AI 对你编码习惯的认知。建议每个月清一次——相当于"格式化"AI 的记忆，防止坏习惯积累。

**2. 给 AI 定规矩。**

不要让 AI 单纯从你的代码里"学"，而是主动告诉它你的编码规范：

> 以下是我的编码规范，请在后续所有生成中遵循：
> 1. Controller 层不能包含业务逻辑，只能做参数校验和响应格式化
> 2. 所有资源操作必须有 finally 释放
> 3. 所有异常使用自定义异常类，不要直接抛 Error

这就把"被动学习"变成了"主动规范"——AI 不是在模仿你的坏习惯，而是在遵循你给的规则。

## 六、这两个功能配在一起，才是完整形态

单独用 @database：AI 能看懂数据库，但不知道你习惯怎么写代码。

单独用记忆感知：AI 知道你的风格，但不知道项目的数据库长什么样。

**两个都开了之后——**

> 你："加一个退款功能"

AI 的反应链路：
1. @database → 看到数据库有 orders / payments / refunds / stock 四张表 → 知道退款涉及哪几张
2. 记忆感知 → 知道你习惯三层架构（controller / service / repository）→ 三层都生成对应代码
3. 记忆感知 → 知道你用自定义异常 + 长变量名 → 生成的代码风格跟你完全一致
4. Repowiki → 知道退款逻辑要跟支付模块和库存模块通信 → 生成的跨模块调用路径全是正确的

**这不是"AI 帮你写代码"，这是"AI 帮你实现了一个功能，你只需要检查。"**

---

## 写在最后

对刚开始用 Qoder 的人，我有一个建议：**别在第一个星期就对 AI 的生成质量下定论。**

第一周，AI 不了解你的项目（没开 Repowiki）、不了解你的数据库（没开 @database）、不了解你的习惯（记忆感知还没攒够数据）。这时候 AI 的产出质量跟一个刚入职的实习生差不多——看着像那么回事，但细节全是坑。

一个月之后——Repowiki 建好了、@database 连好了、AI 学够你的习惯了——这时候再评价，感受会完全不同。

下一篇是这一章的"彩蛋"篇——QoderVoice。2026 年 7 月 28 号刚上线的全双工语音功能，我用了一周的真实体验。说实话，比我想的有用，但也比我想的有限。
