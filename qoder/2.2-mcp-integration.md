# 有人说 Qoder 没有 MCP ——3000 个工具就在菜单里，只是藏得有点深

**写在前面：**

在写 CodeBuddy 系列的时候，MCP 是我重点讲的能力——可以用 Claude 风格的工具调用做任何事，查数据库、操作浏览器、读写文件，像一个瑞士军刀。当时我心里想的是："这个能力太爽了，其他工具没有。"

后来开始用 Qoder，我第一反应是找 MCP 配置在哪。找了十分钟，没找到。

我开始怀疑："Qoder 没有 MCP。"

然后我在设置里翻到了一个叫"集成"的菜单项。点开一看——好家伙，不是没有，是藏起来了。

---

## 一、Qoder 的 MCP 哲学：帮你挑好，而不是等你来配

先说一个我这几个月下来的感受——**Qoder 和 CodeBuddy 对 MCP 的思路完全不一样。**

CodeBuddy 的 MCP 是"给你一扇大门，里面什么都有"——你自己去找 MCP Server，自己配 JSON 配置文件，自己解决版本兼容问题。自由度极高，但门槛也不低。你至少要懂 JSON 格式、懂 MCP 协议、能处理不同 Server 之间的冲突。

Qoder 的 MCP 是"给你一个工具箱，里面已经放好了最好用的"——它把常见的 MCP Server 做成了预置插件，点一下就能装。目前大概有 3000+ 个扩展，覆盖数据库、云服务、文档、项目管理、浏览器控制等大部分场景。

这两种思路谁更好？我的判断是：**对 90% 的开发者来说，Qoder 的方式更好。** 你不用花时间研究 MCP 协议、翻 GitHub 找 Server、解决路径问题。你要做的就是"我想连数据库"→ 找到数据库插件 → 一键安装。

但另外 10% 的场景——公司自研的内部工具、小众的 MCP Server、高度定制化的流水线——CodeBuddy 的手动配置方式仍然不可替代。

**一句话总结：Qoder 给你一台能开箱即用的轿车，CodeBuddy 给你零件让你自己组装。大多数人是需要那台轿车。**

## 二、在哪找——藏得不深，但也不显眼

路径：VS Code 左下角 → Qoder 图标 → 右键 → Settings → 在侧边栏找到"集成"。

或者在聊天框输入 `/tools` 也能直接跳到插件管理页面。

进去之后会看到一个分类列表——数据库、云服务、浏览器控制、项目管理、知识库、API 集成……每个分类下面有对应的 MCP 插件。装完之后 AI 就能调用它们了。

说实话，这个菜单的入口设计不太好。写文章的时候我专门去试了一下，问了一个从来没用过 Qoder 的同事："找一下 MCP 配置在哪。"他找了五分钟没找到。工具箱是好工具箱，但钥匙藏在地毯底下。

希望后面的版本能把入口放到更显眼的位置。

## 三、三个最实用的场景

我不是那种"把所有插件装一遍"的用户。我装了大概 6 个，真正日常在用的就 3 类。

### 场景一：数据库 MCP —— 让 AI 直接看你的表结构

这是最实用的一类。装了数据库 MCP 之后，你可以说：

> 查一下 users 表里 status = 'pending' 的用户有多少，然后给他们的 email 发一封提醒

AI 会先通过 MCP 查数据库 → 拿到数据 → 再生成代码（或者生成 SQL 给你确认后执行）。

以前做这件事的流程是：手动查 SQL → 把结果粘贴给 AI → 描述需求 → 等代码。现在是一句话搞定中间所有步骤。

支持的数据库：MySQL、PostgreSQL、MongoDB、Redis 都有预置插件。公司内部如果有特殊的数据库（比如自研的 KV 存储），得自己写 MCP Server 接入，这就回到方式一的路径了。

### 场景二：浏览器控制 —— 让 AI 帮你操作网页

装了浏览器 MCP 之后，Agent 可以打开浏览器、导航到网页、填写表单、截图验证。

典型用法：

> 帮我在本地跑的项目里点一遍用户注册流程，抓到所有报错

AI 会打开浏览器 → 导航到 localhost → 走注册流程 → 找到报错 → 定位到对应代码 → 修复。

这个场景对前端开发者特别有用——自动化 E2E 测试的门槛被降到一句话了。

### 场景三：企业知识库 —— 让 AI 读公司内部文档

如果你的公司用飞书、语雀、Notion 存技术文档，有对应的 MCP 插件。装了之后 AI 可以直接搜索内部文档来回答问题。

比如：

> 公司内部的用户认证流程是怎么设计的？帮我查一下飞书文档

AI 会通过 MCP 搜飞书的文档 → 找到对应的设计文档 → 根据文档来写代码或回答问题。

**但这个场景有安全隐患——见第五部分。**

---

## 四、MCP 和 Skills、Automation 的三角关系

Qoder 里 MCP 不是一个孤立的功能。它跟 Skills（技能包）和 Automations（自动化）是打通的。

- **MCP** 负责"能给 AI 什么工具"——是能力层
- **Skills** 负责"AI 遇到什么问题怎么用工具"——是知识层
- **Automations** 负责"什么时候该自动干活"——是调度层

举个例子：你要自动做每日数据库健康检查。

1. 先装数据库 MCP（给 AI 数据库查询能力）
2. 写一个 Skill："数据库健康检查流程"（告诉 AI 该查哪些指标、发现异常怎么处理）
3. 在 Automations 里设一个定时任务：每天早上 7 点跑一遍这个 Skill

这三层配合好之后，AI 从"被你召唤才干活"变成了"到点自动干活"。这也是 Qoder 跟纯代码补全工具（比如早期 Copilot）拉开差距的地方——它不是帮你写一行代码，是帮你跑一个流程。

## 五、安全问题——MCP 用的爽，别把生产库暴露了

MCP 给 AI 的能力越大，安全风险越大。这是不说不行的一节。

**红线一：别给 AI 生产数据库的写权限。**

数据库 MCP 连接的时候，建议配一个**只读账号**。AI 查数据、分析数据都可以，但别让它能写、能删、能改。一旦 Agent 理解错了你的需求——比如你说"把所有 tmp_ 开头的表清理一下"，它把正式表也清了你哭都来不及。

**红线二：MCP 插件看来源。**

Qoder 的插件市场有审核机制，但跟所有应用商店一样，不能保证 100% 安全。装插件之前至少看一眼作者、安装量、最近更新时间。三个都是空白的插件，先别装。

**红线三：企业知识库 MCP 注意数据隔离。**

如果你连了公司飞书文档的 MCP——理论上 AI 可以读到公司所有文档。如果你的 Qoder 账号是个人版（不是企业版），OpenID 链接的阿里云账号也没有公司级别权限控制——那这条路要谨慎。建议公司统一采购企业版，在管理员层面控制 MCP 权限。

**红线四：浏览器 MCP 别跑外网敏感操作。**

让 AI 操作网页做测试是一回事，让它登录公司后台管理系统是另一回事。浏览器 MCP 录制的操作过程会上传到阿里云服务器处理——别在操作里包含密码、Token、生产环境的敏感数据。

---

## 写在最后

Qoder 和 CodeBuddy 的 MCP 之争，说到底不是谁"有"谁"没有"的问题——是两种设计哲学。CodeBuddy 走的是极客路线，给你最大的自由度，但需要你自己研究配置、排错。Qoder 走的是产品路线，帮你把大部分场景的 MCP 预置好了，开箱即用，但自定义程度更低。

现在我用 Qoder 的时间远多于 CodeBuddy，不是因为 Qoder 更"强大"，是因为我不想花时间配置工具——我想花时间用工具。这是 30 岁之后的觉悟。

下一篇聊一个说起来简单但实际用起来很讲究的东西——多模型选择。Qoder 不锁模型，可以随时切 Qwen、DeepSeek、GLM、Kimi。但什么时候该换、换完有什么后果，不是所有人都清楚。
