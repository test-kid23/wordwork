# 用了三个月才发现 AI 一直在"盲写"——打开 Repowiki，它突然就懂我的代码了

**写在前面：**

前几篇我一直在说 Qoder 的 Agent 模式多好用、改 Bug 多快。但说实话，有一个细节我没提——前两个月我让 Agent 改代码，它经常改错地方。

不是功能写错了，是**文件找错了**。我让它改 userService 里的一个方法，它跑去改了一个完全无关的 controller。我让它分析支付模块的依赖，它把订单模块的代码也扯进来瞎分析了一通。

我一开始以为是我描述需求不够清楚。后来发现不是——是 AI 根本不知道我的项目长什么样。每次对话它都在"盲人摸象"，靠搜索关键词碰运气。

直到我开了 Repowiki。

---

## 一、Repowiki 是什么——不是生成文档，是给 AI 装一张项目地图

Repowiki 这个名字听起来像"自动生成 Wiki 文档"，但它做的事比生成文档重要得多。

**Repowiki 的本质是：让 AI 对你的项目结构有一个结构化的、持久的认知。**

没开 Repowiki 的时候，AI 每次对话都是"从零开始认识你的项目"。它的工作方式是——收到一个指令 → 搜索相关文件名 → 读取找到的文件 → 猜这个项目是干嘛的。整个过程靠文件名字符匹配，跟人闭着眼睛摸东西差不多。

开了 Repowiki 之后，区别是这样的：

**没开 Repowiki：**
你："帮我修一下 userService 里的登录验证 Bug"
AI：扫描文件 → 找到 userService.ts → 读内容 → 猜测业务逻辑 → 改代码
（整个过程相当于一个刚进公司的人，连项目目录都没看过，就开始修Bug）

**开了 Repowiki：**
你："帮我修一下 userService 里的登录验证 Bug"
AI：查 Repowiki 索引 → 知道 userService 在哪、依赖谁、被谁调用、跟哪些模块有关联 → 精准定位 → 改代码
（相当于一个看过项目架构文档的同事，知道每个文件是干嘛的）

Repowiki 生成的内容不是给你看的——是给 AI 看的。它会分析你的代码库，生成一份"项目地图"，包含：
- 目录结构和每个目录的职责
- 核心模块的入口和依赖关系
- 数据流的方向（从 controller → service → dao → db）
- 关键接口和类的功能描述

这份地图存在项目本地，Qoder 的每一个 Agent 任务都会先查这份地图，再开始干活。

## 二、实测对比：有 Repowiki 和没有的差距有多大

我用同一个项目、同一个任务，做了一次 AB 对比。

**项目背景：** 一个 NestJS 电商后端，大概 80 个文件，包含用户、商品、订单、支付四个模块。

**测试任务：** "给支付模块加一个退款功能，退款成功后要同时更新订单状态、恢复库存、写入退款记录。"

### 没开 Repowiki（第一次跑）：

1. Agent 先搜了"支付"相关文件——找到了 payment.service.ts 和 payment.controller.ts
2. 但它不知道支付模块跟订单模块、商品模块的关系
3. 它写的退款逻辑里，调用了一个已经废弃的 inventory 旧接口（因为新项目的 inventory 改名叫 stock 了，它搜不到）
4. 改了 3 个文件，但漏了退款记录表的写入

**结果：代码能跑，但有两个 Bug。** 一个是因为调了废弃接口导致运行时 404，一个是退款记录没存下来。得我手工补。

### 开了 Repowiki（重新跑）：

1. Agent 先查了 Repowiki——看到了完整的模块依赖图：支付模块 → 订单模块 → 库存模块
2. 它知道了 stock 模块才是新的库存接口，inventory 已经废弃
3. 它发现退款记录需要写入 refund_log 表（这个文件之前没搜到，但 Repowiki 里有记录）
4. 改了 5 个文件，全部改对

**结果：代码直接能跑，一次通过。** 我只需要检查一下退款逻辑的金额计算有没有问题——这个层面的正确性 Repowiki 帮不上忙，得自己看。

同一个任务，有 Repowiki 省了我大概 15 分钟的手工修 Bug 时间。问题的根源不是 AI 笨，是它"看不见"。

## 三、怎么触发 Repowiki——三种方式，最推荐第三种

Repowiki 不是装了就自动有的。需要主动触发让它生成。

**方式一：手动指令。**

在 Qoder 聊天框输入：

> 请为这个项目生成 Repowiki

AI 会开始逐层扫描项目，分析结构，生成索引。这个过程根据项目大小，几分钟到十几分钟不等。

**方式二：让 Agent 任务自动触发。**

Qoder 在 Agent 模式下，如果检测到项目没有 Repowiki 且任务涉及多文件，它会在任务计划里加一步："先生成 Repowiki 以了解项目结构"。

但说实话——我不推荐靠这种方式。因为 Agent 自动触发的时候，任务已经在排队了，再插一个 Repowiki 生成步骤，整个流程会变慢。而且自动触发的 Repowiki 有时候生成得比较粗糙——它赶时间。

**方式三（推荐）：第一次打开项目时就手动生成。**

我的习惯是：打开一个项目 → 右键项目根目录 → 选"Qoder: Generate Repowiki" → 等它跑完 → 再开始干活。

这个方式的好处是：
- Repowiki 提前生成好，后续所有 Agent 任务都受益
- 生成时可以盯着看——它分析错的地方能当场纠正
- 不用在紧急性任务里等多一步

**生成完之后别扔那不管。** 项目结构变了（加新模块、重构目录）之后，Repowiki 不会自动更新。需要手动让它重新生成，或者告诉它"更新 Repowiki 中跟支付模块相关的部分"。

## 四、什么项目适合——5 个文件以上基本都用得上

这个问题很简单：**文件数超过一只手，Repowiki 就有明显价值。**

文件少于 5 个的小脚本项目——AI 扫一眼目录树就能看明白，Repowiki 的增益不大。但问题是，日常工作里遇到的"小项目"太少了。大部分项目至少有十几个文件，几个模块，几层调用。

换句话说——99% 的情况下，开 Repowiki 比不开好。

**一个反例：** 如果你在做一个纯练习项目，或者写一个一次性脚本（今天写完明天删），那就别开。Repowiki 生成需要几分钟，这几分钟省下来自己多写几行代码更值。

但对任何"需要维护超过一周"的项目，Repowiki 是必开的。

---

## 五、局限性：超大项目的 Repowiki 会丢信息，怎么补救

Repowiki 不是完美的。我用它分析过一个大概 5 万行的 Java 项目，生成的 Repowiki 漏掉了一些细节——它把几个子模块的依赖关系简化了，导致 Agent 在处理跨模块调用时偶尔找不到正确的文件。

官方数据说 Repowiki 能处理十万级代码库，但根据我的经验，超过 3 万行之后，一些非核心的工具类和边缘模块的覆盖率会下降。

**补救办法：**

**1. 告诉 AI 重点补哪些模块。**

如果知道 Repowiki 在某个模块上的分析不够细，直接让 AI 拓展：

> 请深入分析 stock 模块的内部结构，更新 Repowiki

**2. 把项目拆成多个子项目。**

对微服务项目，每个服务单独建一个 VS Code 窗口，每个窗口独立生成 Repowiki。这样每个 Repowiki 的粒度更细。

**3. 配合手动上下文。**

Agent 任务执行前，手动把 Repowiki 没覆盖到的重要文件加到上下文中（右键文件 → Add to Context）。

## 六、知识引擎：一个被低估的更新

Qoder 在 2026 年 6 月推出了一个叫"知识引擎"的能力——它本质上是 Repowiki 的升级版。官方给的数据是：知识引擎上线后，**代码保留率提升 11%，输入 Token 消耗下降 40%，对话轮次减少。**

翻译成人话就是：
- AI 写的代码，需要改的部分减少了 11%
- 每次对话 AI 扫描上下文消耗的 Token 少了 40%（因为不需要每次重新"看"整个项目）
- 完成同一个任务的对话轮次变少了（因为 AI 第一次就更准）

这个更新不显眼——没有新按钮、没有新界面。但它对日常使用的影响很大。Token 消耗少了意味着同样的 Credits 能干更多活。代码更准意味着反复修改的时间少了。

说实话，Repowiki 不是那种"用了就哇塞"的功能——没有专家团那种炫酷，没有语音交互那种新鲜感。但它是那些让你"怎么越来越顺"的底层改进——你不会注意到它，直到有一天你不用它。

## 写在最后

如果你现在用 Qoder 但还没开 Repowiki——先别往下读了，去开一下。

打开你的项目，右键根目录 → Generate Repowiki，等几分钟。然后随便找一个 Agent 任务试一下——你会感觉到区别。不是说 AI 突然变聪明了，是它终于知道东西在哪了。

Repowiki 是那种"沉默的杀手级功能"——不炫，但用和不用的体验差距非常真实。上一篇文章说过，80% 的活在 Agent 模式里做。那开了 Repowiki 之后，Agent 模式那 80% 的活的完成质量，能再提一个档。

下一篇聊聊 MCP——一个比 Repowiki 更"看不见"的能力。它让 AI 的手从你的代码库伸出去，伸到数据库、浏览器、公司内部文档。但这双手伸出去之后，安全性就是一个绕不开的话题了。
