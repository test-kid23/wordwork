## 第9篇 · ✍️ 写YAML就能测接口？没错！零代码写自动化测试真的来了

家人们谁懂啊😭
我刚入行写接口测试
一个接口先 import requests
再发请求 再 print 结果
最后手动贴进 Excel

一个接口 30 行打底
十个接口就是 300 行
改一个字段 所有文件里大海捞针💀

直到我撞见"声明式测试"这玩意👇

📌 今天说三件事：
✅ 命令式跟声明式差在哪
✅ 为啥 YAML 能零代码
✅ 三步工作流长啥样

🧠 命令式 vs 声明式

❌ 命令式（你现在的写法）
→ 手把手教框架"怎么做"
→ 导库 发请求 解析 JSON 挨个判断
→ 30 行 Python 起步

✅ 声明式（建议你试的）
→ 你只告诉框架"要什么"
→ 定义 URL 定义断言 跑
→ 10 行配置搞定

打个比方🌮
命令式像教人做菜：
"去冰箱拿蛋 打散 热油 下锅"
声明式就一句：
"来份番茄炒蛋"

💡 那 YAML 凭啥零代码

你不用 import 任何东西
不用写一行 Python
把"要测谁 验什么"写清楚
剩下的活框架干

🆚 差距一目了然：

写一个接口
🔸 Python：30+ 行
🔸 YAML：10 行

加个断言字段
🔸 Python：改 N 个文件
🔸 YAML：改 1 行

换测试环境
🔸 Python：动代码
🔸 YAML：换一个参数

团队协作
🔸 Python：只有开发看得懂
🔸 YAML：产品经理都能瞅明白

🎯 我的偏见先摆这

测试人的核心价值
是设计测试场景
不是写代码

你把命搭在"怎么写代码测"
而不是"怎么把接口测透"
这活就干歪了

⚠️ 不推荐的写法

网上有人教你
"先把 requests 封装一套"
"再写个 base_test 继承"
听着专业 实际是挖坑
你维护的是框架不是测试
新手千万别跟着卷

📌 下篇预告
直接解剖一个真实 YAML 文件
看一个文件怎么测完整个 API

💬 你现在写接口测试用啥？
试过声明式没？评论区唠唠～
有用的话 ⭐ 收藏不迷路

## 第10篇 · 📝 一个YAML文件=一个完整的测试套件？解剖一个真实案例

上篇我说了"写 YAML 能测接口"
评论区一堆人问
"一个 YAML 文件到底长啥样？"

今天直接扒一个真实的👇
就拿用户管理接口开刀

📌 一个 YAML 就四块

1️⃣ name
写套件名字
告诉别人这套测什么

2️⃣ base_url
写基础地址
所有接口共用前缀
不用每个 case 重复写

3️⃣ variables
写全局变量
username password 全文件共用

4️⃣ cases
写用例列表
一个 case = 一次请求 + 断言

就这四块
没 import 没 class 没 def

🔍 扒一个真实 case

拿"创建用户"举例：

🔸 name 给它起个名
"创建新用户"

🔸 request 发 POST
路径到 /api/v1/users
参数用双花括号引全局变量

🔸 extract 抠返回值
从返回体里把 user_id 抠出来
存着 后面接着用

🔸 assert 验两样
状态码是 201
返回的用户名跟发的一致

没有一句 Python
但该干的活一样没少

🆚 同一个功能 两种写法

用户管理增删改查
❌ Python 要写：
→ conftest 做公共配置
→ test_create/query/update/delete
→ 五六个文件 一百多行

✅ YAML 只要：
→ 一个 users.yaml
→ 四个 case 排好队
→ 一个文件 五十来行

差的不是行数
是"五个文件来回跳"
跟"一个文件看完"的体验

🎯 一个文件能干啥

创建 → 自动测能不能注册
查询 → 用刚建的 id 去查
更新 → 改邮箱看接口灵不灵
删除 → 删掉测试用户 库里干净

四个操作一条链
变量自动传递
不用手动复制 user_id
跑完还不留脏数据

⚠️ 我踩过的坑

最早我把 base_url 写死在每个 case
后来环境一换 全崩
改了八处才救回来
现在 base_url 只写一次
这就是变量的意义

你更看得懂哪个？

## 第11篇 · ⚡ 10分钟写一套完整CRUD测试用例，隔壁测试小哥看傻了

说真的 我以前写 CRUD 测试
光一个用户模块
就能耗掉我一下午

后来用 YAML 重写
从 0 到跑通 没超 10 分钟
隔壁小哥探头看了眼 懵了😂

📌 四步写完一套

1️⃣ 创建用户
POST 到 /api/users
把返回 id 抠出来存着

2️⃣ 查询用户
GET 到 /api/users/{id}
这个 id 就是上一步抠的

3️⃣ 更新用户
PUT 到 /api/users/{id}
改个邮箱 验改没改成功

4️⃣ 删除用户
DELETE 到 /api/users/{id}
删完再查 应该查不到

🔑 最爽的一点

第 1 步抠出来的 id
自动传给后面三步
你完全不用手动复制粘贴

我跟你讲
以前最烦的就是这个
创建完去数据库抄 id
粘到下一个脚本
粘错了 后面全废

🆚 写法对比

❌ 传统脚本：
→ 每个步骤一个函数
→ id 当参数传来传去
→ 一处传错 全链路崩

✅ YAML 写法：
→ 一步 extract 抠出来
→ 后面用双花括号直接引
→ 链路自动串

💡 关键技巧

extract 那行一定要写对路径
我第一次写 路径写错
抠出来是个 None
后面三步全报"用户不存在"
查了半小时才发现
是路径多打了个点

所以断言失败先别慌
十有八九是变量没传过来

⚠️ 不推荐的写法

有人喜欢把 CRUD 拆四个文件
说"职责单一"
听着很工程化对吧
实际你跨四个文件找 id 传递
脑子比代码还累
一个文件一条链 它不香吗

🎯 一句话

CRUD 这种标准流程
就该十分钟搞定
把时间省下来想边界场景

## 第12篇 · 🔄 数据驱动测试：一条用例模板 × N组数据 = N个用例

先讲个丢人的事
有次我用同一套查询接口
拿三个 user_id 各测一遍
我居然复制了三份 case
改 id 改到手抖

结果第二个 id 改漏了
测试过了 其实压根没测到
被 leader 拎去谈话 尴尬死😑

后来才知道有 data_driven

📌 它是啥

一句话：
一条用例模板
配一组数据列表
框架帮你渲染成 N 条

🔹 场景

同一个查询接口
用不同 user_id 测三遍

❌ 以前做法：
→ 复制三个 case
→ 改三处 id
→ 维护噩梦

✅ data_driven 做法：
→ 定义 parameters 列表
→ 一个模板自动渲染

🆚 差距

50 个测试数据
🔸 以前：复制 50 份
🔸 现在：一行配置

不是省复制粘贴
是省"改漏了还不知道"的坑

🎯 真实能用在哪

分页参数批量测
搜索关键词轮着测
用户 ID 批量测

只要"同一逻辑不同输入"
全都可以这么玩

💡 我的用法

我现在连边界值都塞进去
正常值 最大值 最小值 空值
一组 parameters 全覆盖
比手写好十个 case 踏实

⚠️ 注意

别把 data_driven 当万能
逻辑本身不同的用例
硬塞一个模板 反而看不懂
那种就老老实实分开写

## 第13篇 · 🏷️ 给测试用例打标签：比文件夹分类聪明10倍

我以前管用例 全靠文件夹
smoke 一个文件夹
regression 一个文件夹
integration 又一个

直到有个 case
既想跑 smoke 又想跑 P0
我愣是复制了两份
一份丢 smoke 一份丢 P0

后来改了接口
只改了 smoke 那份
P0 那份还是旧的
线上出问题 锅我背😭

📌 标签系统咋回事

不搞文件夹了
每个 case 打几个标签
一个 case 能打多个

🔹 比如

某个登录用例
打上 smoke 和 P0
两个标签都打到

想跑 smoke 就跑 smoke
想跑 P0 就跑 P0
想跑"既是 smoke 又是 P0"
一条命令筛出来

🆚 对比

❌ 文件夹分类：
→ 一个 case 只能待一个坑
→ 跨类就复制
→ 复制就容易漏改

✅ 标签分类：
→ 一个 case 多个标签
→ 交叉筛选
→ 一份文件不复制

🎯 进阶玩法

标签 + 环境 + 优先级
三维一起筛

比如只跑"生产环境 P0 的冒烟"
以前得建个新文件夹
现在一行筛选搞定

💡 我的立场

文件夹那套
是给机器看的
标签这套
是给人脑子用的

用例一多
你绝对会感谢当初打标签的自己

⚠️ 不推荐

别一上来打二十个标签
"重要""紧急""测试"这种
等于没打
标签要能直接当筛选条件
不能当笔记贴纸用

## 第14篇 · 🚦 聪明的测试知道什么时候不跑！条件跳过

说个真事 把我吓出冷汗
有次我在生产环境
手滑跑了一套带"清库"的用例
好在 skip 拦住了
不然用户数据当场没一半

从那以后我信一句话：
不跑 比跑错 高级多了

📌 skip 是啥

给用例加个条件
条件满足就跳过
不满足才跑

🔹 场景一

生产环境跳过破坏性测试
生产库你敢随便删？
skip 写：环境是生产就跳过

🔹 场景二

第三方服务挂了
依赖它的用例跳过
别因为别人崩 你跟着红

🔹 场景三

按版本号跳过
老版本不支持的功能
不兼容的用例直接跳过

🎯 YAML 里长这样

每个 case 加个 skip
写明条件和原因
跑的时候框架自动判断

跳过不是失败
是"这环境不该跑这个"
报告里看得清清楚楚

🆚 心态对比

❌ 硬跑：
→ 生产清库（我差点干的）
→ 第三方挂了全红
→ 版本不对报错一堆

✅ 智能跳过：
→ 该跑的跑
→ 不该跑的安静跳过
→ 报告干净聚焦

💡 我的教训

skip 的原因一定要写清楚
别光写"跳过"
哪天新人看你报告
一堆跳过没原因
他敢信才怪

⚠️ 反面教材

有人把所有用例都加 skip
"怕出错"
那你这测试等于没写
跳过是精挑细选
不是无脑全关

## 第15篇 · 🏗️ 一个文件测完一个业务模块！用例组织哲学

我见过最离谱的测试仓库
一个登录功能
散在七个文件里
改个密码规则
七个文件挨个翻
改完还漏了两个

后来我定了条铁律：
一个 YAML 文件
测完一个业务模块

📌 我的目录结构

smoke 文件夹：冒烟用例
regression 文件夹：回归用例
local 文件夹：本地随手测的

每个业务模块一个文件
用户管理一个
订单一个
支付一个

🔹 好处一：一眼看清

打开 users.yaml
这个模块测啥 全在这
不用七个文件拼拼凑凑

🔹 好处二：版本清楚

每个 YAML 独立版本
改了啥 git diff 一看就懂
"改了哪个接口哪个测试"
清清楚楚

🆚 两种放法

❌ 跟开发代码混一起：
→ 开发改接口顺手改测试
→ 但测试文件被业务提交淹没

✅ 独立仓库：
→ 测试资产自己管
→ 但跟代码容易不同步

我的选择？
小项目混一起
大项目独立仓库
别听那些"必须怎样"的

🎯 一句话哲学

用例要像乐高
一块一块能拼能拆
别像浆糊 搅一起分不开

💡 踩坑提醒

别一个文件塞五百个 case
美其名曰"完整"
实际你找个用例要翻半天
一个模块一个文件
超了就拆

⚠️ 不推荐

别按"请求类型"分文件
get.yaml post.yaml 这种
你测业务还是测动词？
按业务分 永远比按动词分合理

## 第16篇 · ✅ YAML写测试比Python好在哪？8年测试开发的真心话

干测试八年 两头都深耕过
YAML 跟 Python 我都写
今天不端水 直接说观点

先泼盆冷水：
YAML 不是银弹
别信那些"零代码取代一切"的鬼话

但 90% 的接口测试场景
YAML 真比 Python 舒服

📌 五点实在对比

1️⃣ 学习成本
Python 要懂编程
YAML 只要懂接口协议
新人当天就能上手

2️⃣ 可读性
YAML 一眼看清测什么
Python 得读逻辑
业务同学也能 review

3️⃣ 维护性
改接口
Python 改好几处
YAML 改一个配置

4️⃣ 协作
YAML 产品都能看懂
Python 只能开发改

5️⃣ 局限性（老实说）
特别绕的逻辑
还是得写代码
YAML 搞不定

🆚 我的立场

小团队 业务常变
YAML 优先 没悬念

大厂复杂流程
Python 打底 YAML 补上层
别二选一 叠加着用

⚠️ 不推荐的执念

有人非说"纯 YAML 才是真零代码"
为了不用 Python
把逻辑硬塞进配置
配置文件写得比代码还难懂
这就本末倒置了

我见过最惨的
一个 YAML 八百行
全是嵌套判断
改的人哭了

🎯 一句话记住

YAML 是让你少写代码
不是让你不思考
测试思维省不掉

## 第18篇 · 🧩 YAML测试用例也能版本管理？Git协作的正确姿势

以前我们测用例
全扔在共享文件夹
谁改了啥 全靠口头说
"我好像改了登录那个"
结果两个人改冲突

血泪教训换来的认知：
YAML 是纯文本
Git 天生就爱吃这口

📌 为啥 YAML 适合 Git

纯文本 → Git 原生支持
改了啥 自动 diff
