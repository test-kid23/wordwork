# xhs-08 · Prompt 工程：写好 5 句话，AI 测试质量翻倍

> 认知升级类 · 约 950 字

## 📋 直接复制区（以下内容可直接粘贴到小红书发布）

同样的 AI，为什么别人生成的测试用例比你好？

答案就藏在 Prompt 里。多写这 5 句话，质量直接翻倍👇

━━━━━━━━━━━━━━━━━━

📝 第 1 句：告诉 AI 你的技术栈

❌ 烂 Prompt："帮我写接口测试"
→ AI 不知道你要 Python 还是 Java，pytest 还是 JUnit，乱写一通

✅ 好 Prompt："用 Python + pytest + requests 写接口测试"
→ AI 精确到框架，生成的代码能直接跑

🔑 公式：用 [语言] + [测试框架] + [工具库] 写

━━━━━━━━━━━━━━━━━━

📝 第 2 句：指定覆盖范围

❌ 烂 Prompt："测试登录功能"
→ AI 只给你 2 个用例——正常登录 + 密码错误，敷衍你

✅ 好 Prompt：
"""
覆盖以下场景：
- 正常场景（正确用户名+密码 → 成功返回 token）
- 异常场景（参数缺失、类型错误、错误密码、过期 token）
- 边界场景（空输入、超长输入、特殊字符、SQL 注入）
"""
→ AI 吐出来 15+ 条用例，面面俱到

🔑 关键字：覆盖正常、异常、边界三类场景

━━━━━━━━━━━━━━━━━━

📝 第 3 句：给一个示例

AI 靠示例对齐格式，比靠描述靠谱👇

"""
用例格式参考：
def test_login_success():
    '''正常登录：正确凭据返回 token'''
    resp = client.post("/login", json={"user":"admin","pwd":"123"})
    assert resp.status_code == 200
    assert resp.json()["token"] is not None
"""

给了示例，AI 生成的 20 条用例格式全部统一，不用你调👌

🔑 一个示例顶十句描述

━━━━━━━━━━━━━━━━━━

📝 第 4 句：指定断言风格

❌ 烂 Prompt 输出的断言："断言返回成功"
→ 什么叫成功？AI 乱写 assert True

✅ 好 Prompt：
"""
断言要求：
- 状态码精确判断（200 / 400 / 401 / 500）
- 返回体字段类型验证（token 是 string、code 是 int）
- 错误信息包含指定文案
"""
→ AI 写出来的 assert 有鼻子有眼

🔑 不说"成功"，说"状态码 200 + token 字段非空"

━━━━━━━━━━━━━━━━━━

📝 第 5 句：让 AI 解释自己

"""
每个用例上方用注释说明：
# WHY: 为什么要测这个场景
# WHAT: 验证什么行为
# RISK: 线上出问题的后果
"""

加了这三行注释，AI 生成的不只是代码，是"有思路的测试用例"。

Review 的时候不再一脸懵——AI 告诉你它为什么这么设计💡

━━━━━━━━━━━━━━━━━━

🎯 五句话总结

1️⃣ 指定技术栈 → Python + pytest + requests
2️⃣ 三类场景全要 → 正常 + 异常 + 边界
3️⃣ 给一个示例 → 对齐格式，省调参时间
4️⃣ 断言写清楚 → 不要"成功"，要"状态码 200"
5️⃣ 让它解释自己 → WHY + WHAT + RISK

就这 5 句，你的 Prompt 直接从"能用"升级到"好用"🔥

━━━━━━━━━━━━━━━━━━

📋 完整的黄金 Prompt 模板

"""
你是资深测试工程师。用 [语言] + [框架] 写测试。

覆盖正常场景、异常场景、边界场景。

用例格式参考：
[粘贴一个示例用例]

断言要求：[详细断言规则]

每个用例注释说明 WHY / WHAT / RISK。

接口文档 / 需求：
[粘贴内容]
"""

拿走直接用，质量保证翻倍😎

# xhs-09 · 用 AI 做代码 Review：从测试视角找 Bug

> 进阶教程类 · 约 900 字

## 📋 直接复制区（以下内容可直接粘贴到小红书发布）

代码 Review 不光要看代码规范。从测试视角扫一遍，能多找出 30% 的 bug。

关键是——让 AI 帮你扫👇

━━━━━━━━━━━━━━━━━━

🔍 为什么要从测试视角 Review

开发看代码：逻辑对不对？命名好不好？

测试看代码：这段会崩吗？异常处理了吗？边界想到了吗？

举个例子，一段登录代码👇

```python
def login(username, password):
    user = db.query("SELECT * FROM users WHERE name=? AND pwd=?", username, password)
    if user:
        return {"token": user.token}
    return {"error": "login failed"}
```

开发觉得没问题，测试看一眼就想问：
→ username 是空的会怎样？null 呢？
→ 密码明文对比？没有哈希？
→ 没有登录失败次数限制？暴力破解怎么办？
→ SQL 拼接，注入风险？

这就是"测试视角"。AI 能帮你做这件事👇

━━━━━━━━━━━━━━━━━━

📋 代码 Review Prompt

"""
你是一个资深测试工程师，正在进行代码 Review。

请从以下角度审查这段代码：

1. 🔴 安全漏洞
   - SQL 注入、XSS、未授权访问
   - 敏感信息泄露（密码、密钥）

2. 🟡 健壮性缺陷
   - 空指针 / None 未处理
   - 异常未捕获或吞掉
   - 边界条件缺失
   - 并发安全问题

3. 🟢 可测试性问题
   - 硬编码依赖，无法 mock
   - 函数职责过多，难以单测
   - 全局状态污染

输出格式：
⚠️ [等级] 问题描述
   影响：实际危害
   建议：修复方案
   对应测试用例：应该测什么

代码：
[粘贴需要 Review 的代码]
"""

━━━━━━━━━━━━━━━━━━

🔬 实操演示

贴一段真实的生产代码给 AI——

```python
def transfer_money(from_id, to_id, amount):
    from_acc = Account.get(from_id)
    to_acc = Account.get(to_id)
    from_acc.balance -= amount
    to_acc.balance += amount
    from_acc.save()
    to_acc.save()
```

AI 瞬间输出：

⚠️ 🔴 并发安全问题
→ 影响：两个请求同时转账，余额扣两次但只加一次（race condition）
→ 建议：加数据库行锁或乐观锁
→ 测试用例：并发转账压测，验证总金额守恒

⚠️ 🔴 边界值未校验
→ 影响：转负数 = 偷钱；转超大值 = 溢出
→ 建议：amount <= 0 抛异常，amount > balance 抛异常
→ 测试用例：负数、0、余额+1、Long.MAX_VALUE

⚠️ 🟡 N+1 查询
→ 影响：转账 1000 笔，save() 逐条刷 = 2000 次数据库调用
→ 建议：批量更新

这些 bug 上线就是事故，AI 全扫出来了💀

━━━━━━━━━━━━━━━━━━

🔄 Review 结果 → 直接转测试用例

AI Review 输出的"对应测试用例"怎么用？再问一次：

"根据上面的 Review 结果，用 pytest 生成对应的测试用例代码"

一次对话，Review + 用例全有了，一条龙👌

━━━━━━━━━━━━━━━━━━

🎯 一句话记住：

开发 Review 看"对不对"，测试 Review 看"怎么崩"。

AI 同时做这两件事，你负责做决策。

# xhs-10 · 测试左移：AI 帮你在需求阶段就守住质量

> 进阶教程类 · 约 880 字

## 📋 直接复制区（以下内容可直接粘贴到小红书发布）

需求评审还能这么玩？

把 PRD 贴给 AI，让它当场生成验收标准 + 测试点 + 歧义清单。

开发再也不敢糊弄测试了👇

━━━━━━━━━━━━━━━━━━

🤔 什么是测试左移

一句话：把测试活动从"代码写完再测"挪到"需求阶段就开始"。

问题越早发现，修的成本越低——

🔹 需求阶段发现 → 改文档，0 成本
🔹 开发阶段发现 → 改代码，1x 成本
🔹 测试阶段发现 → 修 bug + 回归，5x 成本
🔹 线上发现 → 事故复盘 + 紧急修复，50x 成本

所以越左移，越省钱💰

━━━━━━━━━━━━━━━━━━

📋 需求评审 Prompt

下次开需求评审，把这个 Prompt 准备好👇

"""
你是一个经验丰富的 QA 专家。

请分析以下 PRD / 需求文档，输出：

1. 📌 验收标准（Acceptance Criteria）
   - 每条标准用 Given/When/Then 格式
   - 标记优先级 P0/P1/P2

2. 🔍 需求歧义 & 遗漏
   - 列出描述模糊的地方（"尽量""尽可能""一般"）
   - 列出未覆盖的场景（并发、异常、回滚）

3. 🧪 测试点清单
   - 功能测试点
   - 异常测试点
   - 性能关注点
   - 安全关注点

4. 💬 需要向产品经理确认的问题
   - 整理成可以直接发群的提问列表

需求文档：
[粘贴 PRD 内容]
"""

━━━━━━━━━━━━━━━━━━

💀 实操：AI 从一段需求里挖出了什么

贴一段看起来很"正常"的 PRD——

"""
用户下单功能：
用户选择商品 → 填写收货地址 → 点击支付 → 系统扣款并生成订单
支付成功后 30 分钟内用户可以取消订单，全额退款
"""

AI 分析后输出——

📌 验收标准：8 条，含 Given/When/Then

🔍 歧义清单：
⚠️ "选择商品"→ 没写数量上限？买个 99999 件？
⚠️ "扣款"→ 扣款失败怎么办？订单状态是什么？钱扣了但库存没了怎么回滚？
⚠️ "支付成功"→ 第三方回调超时怎么处理？幂等性怎么保证？
⚠️ "30 分钟"→ 30 分钟后到底能不能取消？部分退款怎么算？

💬 需向产品确认：
1. 扣款失败时，用户看到的提示是什么？
2. 取消订单后库存怎么恢复？立即恢复还是异步？
3. 支付中用户关闭页面再打开，订单是什么状态？
4. 红包/优惠券分摊到每个商品的逻辑是什么？

开发在场，脸色都变了😅 这些不提前问清楚，上线就是事故。

━━━━━━━━━━━━━━━━━━

🎯 评审会上的正确姿势

1️⃣ 会前：把 PRD 喂给 AI，拿到分析报告
2️⃣ 会中：逐条提问，逼产品经理想清楚
3️⃣ 会后：验收标准直接转成测试计划，开发按标准开发

从此你再也不是"需求评审的听众"，你是"质量防线的守门人"💪

━━━━━━━━━━━━━━━━━━

🔁 测试左移的终极形态

需求评审 → AI 出验收标准 → 开发写代码（同时你写测试）→ AI Review 代码 → 自动化测试 → 上线

整个链路测试全程参与，不是最后才介入。

AI 让你一个人干以前三个人的活——不是更累，是更有掌控感。
