🏗️ 一个文件测完一个业务模块！组织哲学


我见过最离谱的测试仓库
一个登录功能
散在七个文件里

改个密码规则
七个文件挨个翻
改完还漏了两个😤

后来我定了条铁律：
一个 YAML 文件
测完一个业务模块


📌 我的目录结构

smoke 文件夹：冒烟用例
regression 文件夹：回归用例
local 文件夹：本地随手测

每个业务模块一个文件
用户管理一个
订单一个
支付一个


🔹 好处一：一眼看清

打开 users.yaml
这个模块测啥 全在这
不用七个文件拼拼凑凑

新人接手
看文件名就知道测哪个模块
不用问你三天😎


🔹 好处二：版本清楚

每个 YAML 独立版本
改了啥 git diff 一看就懂
"改了哪个接口哪个测试"
清清楚楚


🆚 两种放法

❌ 跟开发代码混一起：
→ 开发改接口顺手改测试
→ 但测试文件被业务提交淹没

✅ 独立仓库：
→ 测试资产自己管
→ 但跟代码容易不同步

我的选择？
小项目混一起
大项目独立仓库
别听那些"必须怎样"的🙄


⚠️ 不推荐

别一个文件塞五百个 case
美其名曰"完整"
实际你找个用例要翻半天
一个模块一个文件
超了就拆

更别按"请求类型"分文件
get.yaml post.yaml 这种
你测业务还是测动词？

按业务分 永远比按动词分合理


🎯 一句话记住：

用例要像乐高
一块一块能拼能拆
别像浆糊 搅一起分不开🧩
