## 第34篇 · 🧲 6种变量提取方式，一个比一个好用！第6种很多人不知道

先把上两章串一下😏

前面讲了变量
讲了断言
那变量从哪来？

答案是：提取

接口跑完
从响应里
把你要的值抠出来
存成变量
后面随便用

我整理出 6 种提取方式
最后一种
真有很多人不知道

📌 今天一次讲全：

---

📦 ① JSONPath 提取

最常用
也是默认

响应是 JSON
用路径一把定位
把目标字段抠出来

比如取 data 下的 id
一行路径搞定

九成场景
它就够了

---

📨 ② 响应头提取

头里也有宝

比如请求 ID
种下的 Cookie
重定向地址

这些藏在头里
用"头+字段名"抠出来

（这个下一篇细讲）

---

🔤 ③ 正则提取

返回不是 JSON
是一段文本
但里面夹着你要的值

比如一段 HTML 里
code=12345

正则一把捞出来
非结构化也能提

---

🔢 ④ 状态码提取

有些场景
你就要那个状态码

比如创建成功是 201
提取出来存着
后面断言用

别小看它
状态码比对
经常是第一个断言

---

⏱️ ⑤ 耗时提取

每个请求的响应时间
也能存成变量

性能监控全靠它
（这个第38篇细讲）

---

🗄️ ⑥ 数据库列提取

这个很多人不知道❗

在数据库断言的同时
把查出来的某一列
直接存成变量

然后传给后续用例

接口 + 数据库
双管齐下
闭环了

---

🆚 怎么选

🔸 普通 JSON 字段 → JSONPath
🔸 头里的值 → 响应头
🔸 文本里的值 → 正则
🔸 性能场景 → 耗时
🔸 要拿库里的数据 → 数据库列

选对了提取方式
数据流转才顺

---

⚠️ 一个不推荐

别啥都上正则
明明是 JSON
偏要用正则抠

能结构化的
就别非结构化
正则出错率
高得离谱

---

🎯 一句话记住

提取是数据流转的起点
方式选对
后面一顺百顺

💬 大家最常用哪种提取？
评论区报到～

⭐ 收藏这张对照表
写用例前先想清
从哪提、提到哪

## 第35篇 · 🔐 登录token自动传递！不用手动复制粘贴

这篇是高频刚需😤

先问你：
登录拿到的 token
你是怎么给后面用的？

我见过最原始的：
手动跑一次登录
把 token 复制出来
粘到后续每个用例里

token 一过期
全部重来💀

我当时还觉得
"这样也行吧"
直到接入 CI
没人手动跑
整个链路崩了

📌 自动传递才是正解：

---

🤖 全自动流程

登录请求跑完
用提取
把 token 抠出来

后续所有用例
直接引用这个变量
拼成认证头

框架自动填值
你一个字不复制

token 过期？
重新跑登录
自动更新
不用人插手

---

📤 提取这一步

登录成功后
指定字段路径
比如 data 下的 token
给它起个名 token

这一步做完
token 就是变量了

---

📥 引用这一步

后续请求要认证
请求头里引用 token
拼成 Bearer 加 token

真实值
框架自己填进去
零手动

---

🧩 进阶玩法

有些框架
有专门的认证管理

token 快过期
自动触发刷新
刷新失败记日志

你甚至不用管
token 生命周期

我接了这个之后
定时任务再也没
因为 token 过期断过

---

⚠️ 一个坑

提取路径写错
下游拿到空 token
请求带着空认证出去
返回 401

你还以为是权限问题
排查半天
其实是提取挂了

🔸 先确认提取到了
🔸 再查下游

---

🎯 一句话记住

token 该自动流
不是手动搬

你搬一次
就多一个出错点

💬 你还在手动复制 token 吗？
评论区坦白～

⭐ 收藏
下次接登录链路
直接照这个来

## 第36篇 · 🗄️ 从数据库查数据反向验证！这个闭环太稳了

说个让我惊艳的😌

接口返回 200
就一定能信吗？

我吃过亏：
接口说创建成功
结果数据库没写进去
用户刷新
数据全没了

从那以后
我养成一个习惯：
接口验完
再去库里查一遍

这个闭环
叫"数据库反向验证"

📌 今天讲怎么玩：

---

🔄 接口 + 数据库 双验

场景：
调用创建用户接口

接口返回成功
这只是第一关

再去用户表查
刚创建的那条
是不是真在库里

两关都过
才算真成功

---

🧲 提取也能联动

数据库查出来的值
可以再提取成变量

比如查到的新用户 ID
存起来
传给后面的查询用例

接口提的
库里提的
同一个变量池
随便串

---

🧪 典型三连

🔸 创建后查库
确认真的 insert 了

🔸 修改后查库
确认 update 生效

🔸 删除后查库
注意很多是软删
库里还在
只是状态变了

三连打完
数据真相
逃不掉

---

🛡️ 终极形态

接口返回对
数据库状态对
两个都对

这才是
测试的终极形态

只看接口
永远有盲区
库才是最后真相

我现在的回归用例
核心链路必带数据库验证

---

⚠️ 我不推荐

别为了省事
只验接口返回

看着快
实则埋雷
生产炸的时候
你都不知道为啥

🔸 核心数据
🔸 必走库验

---

🎯 一句话记住

接口说成功
不一定真成功
数据库说有
才是真有

💬 你被"接口200但库里没写"坑过吗？
评论区讲讲那次事故～

⭐ 收藏
核心用例记得加库验

#数据库测试 #接口验证 #自动化测试 #数据校验 #测试闭环

## 第37篇 · 📨 从响应头提取隐藏信息：不止有body可以挖数据

接着第34篇的②😏

很多人不知道
响应头里
藏着不少能用的数据

只盯着 body
等于把一半信息
扔了

我整理几个
实战高频的：

---

🆔 X-Request-Id

每个请求的唯一 ID

提出来存成变量
丢给日志系统

出问题顺着 ID 查
一查一个准

没有它
日志里大海捞针

---

📍 Location

重定向地址
藏在头里

有些创建接口
返回 201 + Location
新资源的地址就在那

提取出来
直接拿去测下一步

我做过一个
"创建后跳转"的链路
全靠它串

---

🍪 Set-Cookie

登录种下的 Cookie

提取出来
传给后续请求
维持会话

不提取
你只能手动复制
cookie 一长串
复制错一个字符
就白忙活

---

📊 X-RateLimit-Remaining

API 限额余量

提出来监控
快超限了
提前报警

限流类接口
这个特别香

---

🧩 配合 body 一起

同一个请求
body 提一个值
头里提一个值

一次请求
多种提取
数据全进变量池

我现在的习惯：
凡是头里有的关键信息
一律提取
不浪费

---

⚠️ 一个提醒

头里的字段名
大小写敏感

有时候文档写 Content-Type
实际返回 content-type
提取时写错
拿到空值

🔸 提取前先抓个真实响应
🔸 照着真实字段名写

---

🎯 一句话记住

body 是明面上的菜
响应头是桌下的菜单
两样都得端

💬 大家还从响应头里
抠出过啥好用的？
评论区补充～

⭐ 收藏
头里这4个值
下次别漏提

## 第38篇 · ⏱️ 响应耗时也能当变量用！性能监控的偷懒技巧

最后一篇😎
讲个被低估的能力

你跑接口测试
有没有注意过
每个接口
花了多少毫秒？

没注意就亏了

响应耗时
本身就能提取成变量
然后拿去做断言

这招
是日常性能监控的
穷人版神器

📌 今天讲透：

---

⏱️ 提取耗时

每个请求跑完
把响应时间
存成变量

就是一行的事
框架会自动记录

---

🚨 下一步断言

拿到耗时变量
直接断言：
必须小于某个毫秒数

比如要求 3 秒内响应
超时就算失败

慢接口
第一时间被你揪出来

---

📊 批量收集

一批用例跑完
把每个接口的耗时
都收集起来

哪些快
哪些慢
一目了然

配合并行测试
最慢的那个接口
再也藏不住

---

🧩 和专业压测的区别

说句实话：
这不是压测

压测要加压
要测吞吐
这个做不到

它做的是：
日常监控
每个接口别突然变慢

属于"轻量预警"
不是"压力测试"

---

⚠️ 我不推荐

别拿它当压测用

有人想：
我循环跑 100 遍
测性能

错了
这不是压测
这是把测试跑慢了

🔸 日常监控 → 用它
🔸 真压测 → 上专业工具

---

🎯 一句话记住

耗时不只是数字
是能当变量的信号

监控它
慢接口就逃不掉

💬 大家见过最慢的接口
响应多少秒？
评论区比惨～

⭐ 收藏
给核心接口
加个耗时断言
