# 对象存储协议深度拆解：S3 API 比你想象的能打

> 前面拆了块存储和文件存储，这篇轮到对象存储。很多人以为 S3 就是"存图片的 HTTP 网盘"，实际上它的设计思路和前面两种完全不同，能干的事也比存图片多得多。

---

## 一、对象存储不是什么

先说三个常见误解：

**误解一：对象存储 = 有文件夹的网盘。** 不对。你以为 `photos/2026/vacation/img001.jpg` 是一个路径，实际上整个字符串就是一个 Key，没有文件夹这回事。控制台里看到的"目录"是 API 用分隔符 `/` 模拟出来的视觉效果。

**误解二：对象存储能当数据库盘的平替。** 不行。对象是不可变的（immutable），修改一个对象的任何一个字节 = 上传整个新版本覆盖旧版本。没有原地修改能力，没有 POSIX 语义，数据库文件放上来第一时间就炸。

**误解三：对象存储比文件存储慢。** 不一定。大文件顺序读写场景下，对象存储可以并行从多个节点拉数据，吞吐反而可能比单机 NFS 高。慢的是小文件元数据操作和对延迟敏感的随机读写。

---

## 二、对象存储的核心模型

对象存储的数据模型就三个东西：

**对象（Object）**：数据本身。可以是图片、视频、日志、Parquet 文件、二进制文件、任何东西。

**元数据（Metadata）**：键值对形式的标签。系统元数据（Content-Type、Content-Length、ETag）和自定义元数据（`x-amz-meta-` 前缀）。你能自定义任意标签，比如 `x-amz-meta-camera: Sony A7M4`，不用建表。

**Bucket**：对象的容器。命名全局唯一（在同一个服务商下），权限在 Bucket 级别控制。

访问方式就是一个 HTTP RESTful API：

- `PUT /bucket/object` → 上传
- `GET /bucket/object` → 下载
- `DELETE /bucket/object` → 删除
- `HEAD /bucket/object` → 只拿元数据，不下载
- `GET /bucket?prefix=xxx&delimiter=/` → 列举

没有 `open()`、没有 `seek()`、没有 `append()`。对象存储不是文件系统，别用文件系统的思维去套。

## 三、S3 协议：AWS 定义的事实标准

2006 年 AWS 发布了 S3，到现在快二十年，它定义的 REST API 成了整个行业的统一标准。阿里云 OSS、腾讯云 COS、华为云 OBS、MinIO、Ceph RGW——全部兼容 S3 API。

这意味着你写一遍 S3 的 SDK 代码，换个服务商只要改 Endpoint 和密钥，代码不动。

### S3 API 核心操作

这六个是最常用的，其余几十个操作不做展开：

| 操作 | 用途 | 备注 |
|------|------|------|
| `PutObject` | 上传对象 | 单次最大 5GB，超过用分片上传 |
| `GetObject` | 下载对象 | 支持 Range 请求只下载文件的一部分 |
| `DeleteObject` | 删除对象 | 单个删除，批量删除用 `DeleteObjects` |
| `HeadObject` | 查对象元数据 | 不下载数据，只拿大小、类型、ETag |
| `ListObjectsV2` | 列举 Bucket 中的对象 | 分页返回，最多 1000 个/页 |
| `CreateMultipartUpload` | 初始化分片上传 | 大文件分片上传：初始化→逐片上传→完成 |

### 分片上传（Multipart Upload）

这个机制值得单独讲一下，因为它是对象存储"能打"的关键能力之一。

超过 100MB 的文件不建议用单次 PutObject。分片上传把大文件切成多块（每块 5MB-5GB），并行上传，最后合并。三个好处：

1. **并行上传，快**。一块 10GB 的文件切成 20 个 512MB 的片，20 个连接同时传，吞吐达到单连接的理论上限
2. **断点续传**。上传到第 15 片断网了，重试只需上传后 5 片，前面完成的片已经持久化了
3. **先上传后知道大小**。流式数据不知道最终多大，可以先起一个 MultipartUpload，边生成边上传分片，最后 Complete

### 一致性问题

S3 的一致性模型经过多次变化：

- **最初**：写入后"读后写"一致性（对新建对象）但覆盖旧对象是最终一致
- **2020 年后**：AWS S3 在所有区域对所有操作提供强一致性。PUT 之后立刻 GET，保证拿到最新版本
- **第三方实现**：MinIO 是强一致；Ceph RGW 视配置而定，默认最终一致

选型的时候如果依赖强一致读写，别只看"S3 兼容"，要确认你用的具体实现是否支持。

### 版本控制

Bucket 级别开版本控制后，每个对象的历史版本都会被保留。删除操作不会真正删除数据，而是加一个"删除标记"。列表默认不显示历史版本。

版本控制打开后**永远别关**——不是功能不能用，是关了之后历史版本不会自动清理，相当于数据只增不减，账单会慢慢涨。

## 四、对象存储适合什么、不适合什么

### 适合

| 场景 | 原因 |
|------|------|
| 图片/视频/CDN 源站 | 一次上传 CDN 分发，HTTP 原生 |
| 日志归档 | 只追加不修改，S3 对象不可变属性天然匹配 |
| 备份 | 便宜、无限容量、跨区域复制 |
| 大数据数据湖 | Spark/Hive/Presto 可以直接查 S3 上的 Parquet/ORC |
| 静态网站托管 | 设置 Bucket 为静态网站模式，CloudFront 做 CDN |
| 容器镜像仓库 | Harbor 等镜像仓库后端用 S3 存 blob |

### 不适合

| 场景 | 原因 |
|------|------|
| 数据库文件 | 不支持原地修改，不支持文件锁 |
| 频繁小文件覆盖更新 | 每次覆盖 = 上传整个新版本，IOPS 和成本都扛不住 |
| 需要 POSIX 语义的应用 | 不支持 `rename`、`lock`、`append` |
| 低延迟随机读写 | HTTP 往返延迟在毫秒级，NVMe 本地盘在微秒级 |

一个反例：如果把日志采集程序配成每秒往 S3 PUT 一个 100 字节的小日志对象，一个月的 PUT 请求费用比存储费用高几十倍。这种情况应该先批量聚合再上传。

## 五、S3 兼容的开源实现对比

如果想自建对象存储，三个主流选择：

| 维度 | MinIO | Ceph RGW | SeaweedFS |
|------|-------|----------|-----------|
| **部署复杂度** | 极简，单二进制 | 需要 Ceph 集群 | 中等 |
| **性能特征** | 小对象极快，单机千万 IOPS | 大集群均衡好 | PB 级小文件治理强 |
| **S3 兼容度** | 高，基本完整 | 高，基本完整 | 高，社区活跃 |
| **多租户** | 原生支持 | 支持 | 支持 |
| **纠删码** | 服务端 EC | Ceph 原生 EC | 支持 |
| **适合规模** | 中小规模 | 大规模统一存储 | 小文件海量场景 |
| **运维门槛** | 极低 | 最高 | 中等 |

MinIO 这几年在国内很火，部署一条命令起来，API 兼容度也够。但如果团队已经上了 Ceph 集群做块存储，直接用 Ceph RGW 提供对象存储入口就行，不需要另起一套独立存储集群。

## 六、几个实战配置要点

### Bucket 命名和域名

S3 API 的请求路径有两种风格：
- **Path-Style**：`https://s3.amazonaws.com/bucket-name/object-key`
- **Virtual Hosted-Style**：`https://bucket-name.s3.amazonaws.com/object-key`

现代 S3 兼容服务默认用 Virtual Hosted-Style，意味着 Bucket 名必须是有效的 DNS 子域名：全小写、不能有下划线、长度 3-63 个字符。起名的时候注意这个限制，不然配 SSL 证书会炸。

### 访问控制

三层权限：
1. **IAM/Bucket Policy**：基于资源/用户的策略控制
2. **ACL**：旧版权限控制，现在基本不推荐用
3. **Pre-signed URL**：生成带签名的临时下载/上传链接，限定有效期。分享文件的最佳方案——不用开放公开读，也不用量身定做一个账号

Pre-signed URL 的典型用法：

```python
# 生成一个 1 小时内有效的下载链接
url = s3_client.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'report.pdf'},
    ExpiresIn=3600
)
```

### 生命周期策略

设置规则让对象在指定时间后自动转换存储类型或删除。通用的分层思路：

```
上传 → 标准存储（30天）→ 低频存储（60天）→ 归档存储（365天）→ 自动删除
```

每个阶段的单价递减，但取回成本递增。生命周期策略配好了，存储成本能降 50% 以上。

## 七、速查表

**对象存储和其他两种存储的区别：**

| 对比维度 | 对象存储 | 块存储 | 文件存储 |
|---------|---------|--------|----------|
| 接口 | HTTP REST API | SCSI/块设备 | POSIX 文件操作 |
| 数据结构 | 扁平 Key-Value | 块地址 | 目录树 |
| 修改方式 | 覆盖整个对象 | 原地读写任意字节 | 原地读写任意位置 |
| 扩展方式 | 横向无限 | 受阵列/协议限制 | 受目录结构限制 |
| 典型延迟 | 毫秒级 | 微秒级（本地/FC） | 几百微秒 |
| 计费模型 | 按容量+请求+流量 | 按分配的 LUN | 按分配容量 |

**选型一句话：**

| 场景 | 答案 |
|------|------|
| 我需要存海量图片/视频，通过 HTTP 访问 | ✅ 对象存储 |
| 我的应用要随机读写文件某个字节 | ❌ 别用对象存储 |
| 我要一个无限容量的备份目标 | ✅ 对象存储 + 生命周期策略 |
| 我的 Hadoop 集群要换掉 HDFS | ✅ 对象存储做数据湖 |
| 我要跑 PostgreSQL | ❌ 用块存储 |
