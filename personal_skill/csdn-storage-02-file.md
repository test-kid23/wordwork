# 文件存储协议深度拆解：NFS v3/v4、SMB 实战对比

> 块存储是把远程盘给你自己管，文件存储是把管好的目录给你直接用。这篇拆 NFS 和 SMB 两个主流文件存储协议的底层差异和实战选型。

---

## 一、文件存储的工作方式

文件存储的核心逻辑：**存储端管理文件系统，客户端通过协议挂载目录**。你在这台服务器上 `touch a.txt`，另外一台挂着同一个导出的服务器 `ls` 能立刻看到。

跟块存储最大的区别是——**文件系统这件事不是你在管，是存储端在管**。好处是你不用操心格式化、inode 耗尽、fsck；代价是多了一层网络文件协议的开销，性能必然比裸盘直接读写差。

---

## 二、NFS：Linux 世界的共享文件标准

NFS 的历史能追溯到 1984 年 Sun Microsystems。三十多年下来经历了 v2、v3、v4、v4.1、v4.2 五个大版本。目前生产中主要在用的是 v3 和 v4。

### NFS v3：无状态，简单，但不够「现代」

v3 的核心设计理念是**无状态协议**——NFS 服务端不记录客户端的连接状态。每次请求独立处理，客户端挂了服务端完全无感。

**优点：**
- 实现简单。服务端不需要维护会话表
- 客户端断连后重连零成本，不存在"清理残留锁"的问题
- 在 UDP 上也能跑（虽然不推荐）

**缺点：**
- **没有真正的锁机制**。v3 的文件锁靠 NLM（Network Lock Manager）这个独立协议实现，状态由另外的 `lockd`/`statd` 守护进程管理。客户端崩溃后锁恢复靠心跳超时——不可靠
- **弱一致性**：客户端大量使用本地缓存，写入可能还没刷到服务器上。需要 `sync` 挂载选项保证数据安全，但会拖慢性能
- **不支持 ACL**：只有传统的 Unix rwx 权限模型
- **没有安全传输层**：认证依赖 AUTH_SYS（传 UID/GID），在受控内网没问题，跨网段就不够看了

**一个典型的 v3 挂载：**

```bash
mount -t nfs -o vers=3,rsize=1048576,wsize=1048576,hard,intr 192.168.100.10:/data /mnt/nfs
```

`rsize`/`wsize` 在 v3 里很重要。默认值通常只有 64KB，调成 1MB 可以显著提升大文件吞吐。但要注意交换机 MTU，不然包分片反而更慢。

### NFS v4：有状态，更安全，但更复杂

v4 是一次大改版。从无状态变成了**有状态协议**——服务端维护客户端的会话状态。

**v4 带来的关键变化：**

**复合操作（COMPOUND）**：v3 里 LOOKUP + READ + GETATTR 是三个独立 RPC，v4 可以把它们打包成一个 COMPOUND RPC 发过去，减少网络往返。小文件元数据密集场景（`ls -la` 目录里几千个文件）提升明显。

**内置锁机制**：不再依赖外部 NLM。锁状态由服务端管理，支持租约（lease）机制。客户端在规定时间内不续租，服务端自动回收锁——比 v3 的锁恢复靠谱得多。

**Kerberos 认证**：v4 强制支持 RPCSEC_GSS，可以用 Kerberos 做身份认证。AUTH_SYS 在 v4 里变成可选项。

**聚合（Delegation）**：v4 允许服务端把某个文件的读写权"委托"给特定客户端。在这期间其他客户端不能修改该文件，被委托的客户端可以充分本地缓存——大幅减少 RPC 调用。

**v4.1 加了 pNFS（Parallel NFS）**：把元数据服务器（MDS）和数据服务器（DS）分离。客户端从 MDS 拿到文件布局信息后，直接并行读写多个数据服务器。这是 NFS 吞吐从"单机上限"跳到"线速"的关键能力。做 AI 训练数据集的多机读取场景，pNFS 是目前最好的原生方案之一。

### v3 vs v4 选型速查

| 维度 | NFS v3 | NFS v4/4.1 |
|------|--------|-----------|
| 协议类型 | 无状态 | 有状态 |
| 锁机制 | NLM（不可靠） | 内置 Lease（可靠） |
| 安全 | AUTH_SYS | Kerberos |
| 性能特征 | 大文件吞吐好 | 小文件元数据快 |
| 并发写入 | 不支持 | 支持（需要应用配合） |
| 并行吞吐 | 单 MDS 瓶颈 | v4.1 pNFS 多 DS 并行 |
| 兼容性 | 几乎所有系统 | 需 v4 以上客户端 |
| 适合场景 | 简单共享、顺序读写 | 多客户端并发、安全环境 |

## 三、SMB/CIFS：Windows 世界的通用语

SMB 是微软主导的文件共享协议。Windows 文件管理器里 `\\192.168.1.x\share` 背后就是 SMB。

Linux 通过 Samba 实现 SMB 服务端和客户端功能。绝大多数企业混合环境（Windows 客户端 + Linux 服务器）的文件共享都走这条链路。

### SMB 版本演进

| 版本 | 发布时间 | 关键特性 |
|------|---------|---------|
| SMB 1.0/CIFS | Windows NT | 对话式协议，大量广播，极不安全，**应该禁用** |
| SMB 2.0 | Vista/2008 | 请求管道化，效率大幅提升 |
| SMB 2.1 | Win7/2008 R2 | 大 MTU 支持，Lease 机制 |
| SMB 3.0 | Win8/2012 | **多通道、RDMA 直通、透明故障转移** |
| SMB 3.1.1 | Win10/2016 | 预认证完整性、AES-256 加密 |

目前正经生产环境最低也得 SMB 2.1，推荐 SMB 3.0 起步。SMB 1.0 在 2017 年 WannaCry 之后就没人敢用了。

### SMB 3.0 的几个硬核能力

**多通道（Multichannel）**：SMB 3.0 最值钱的功能。服务器插 4 张网卡，客户端也插 4 张，SMB 自动建立 4 条 TCP 连接，数据并行传输。吞吐翻倍、链路冗余、对应用透明。

**RDMA 直通（SMB Direct）**：SMB 3.0 支持 SMB over RDMA（SMB Direct），用 RoCE 或 InfiniBand 直接传输数据，绕过内核 TCP/IP 栈。延迟降到几十微秒，CPU 几乎无感。Windows Hyper-V 挂 SMB 存储跑虚拟机，开 SMB Direct + Multichannel 后的性能不比 iSCSI 差。

**透明故障转移（Continuous Availability）**：配合 Windows 故障转移集群，SMB 客户端连接会话在主节点挂掉后自动切换到备用节点。数据库、虚拟机在 SMB 共享上跑的方案，靠的就是这个。

### SMB vs NFS，同场景实测差异

下面是几种常见场景下 SMB 和 NFS 的实际表现倾向：

| 场景 | NFS v4 | SMB 3.0 | 说明 |
|------|--------|---------|------|
| Linux 客户端读大文件 | ✅ 更好 | 相当 | NFS 生态更原生 |
| Windows 客户端混合访问 | 勉强能用 | ✅ 更好 | Windows 的 NFS 客户端不是一等公民 |
| 小文件大量并发 | 相当 | 相当 | 都靠缓存和复合操作 |
| 域认证/权限控制 | 靠 Kerberos | ✅ 更好 | Active Directory 天然集成 |
| 多通道高吞吐 | pNFS 才支持 | ✅ 原生 Multichannel | SMB 3.0 开箱即用 |
| 跨平台（Mac） | ✅ 原生支持 | 需要配置 | macOS Finder 原生支持 NFS 挂载 |

## 四、分布式文件系统：当单机容量不够用

NFS 和 SMB 本质上是**单机文件存储通过协议暴露出去**。一台 NAS/SAN 的容量和性能有上限，跨过这个上限需要分布式文件系统。

前面汇总篇提过的三个主流方案，这里快速对比：

| 维度 | GlusterFS | CephFS | Lustre |
|------|-----------|--------|--------|
| **架构** | 无中心，弹性哈希 | 中心化 MDS + RADOS | MDS + OSS 分离 |
| **元数据** | 无独立 MDS | MDS 集群 | 1 组 MDS |
| **强项** | 容量线性扩展 | 与 RBD/RGW 统一存储 | 超大规模 HPC |
| **弱项** | 小文件、大量目录操作 | MDS 可能成瓶颈 | 部署复杂，组件多 |
| **典型规模** | PB 级 | PB 级 | EB 级 |
| **适合谁** | 备份、归档、流媒体 | 全栈 Ceph 环境 | 超算中心、AI 训练集群 |

## 五、选型决策路径

```
你的场景是什么？

├── Linux 服务器之间共享文件
│   ├── 简单场景、大文件为主 → NFS v3，够用且简单
│   ├── 多客户端并发、需要可靠锁 → NFS v4
│   └── AI 训练多机读、需要线速吞吐 → NFS v4.1 pNFS 或 Lustre

├── Windows 客户端需要访问
│   ├── 纯 Windows 环境 → SMB 3.0，域控配权限
│   └── 混合环境 → SMB + Linux Samba 服务端

├── 需要高可用、透明故障切换
│   ├── NFS → 需要额外 HA 方案（Keepalived + 共享存储）
│   └── SMB 3.0 → CTDB + 集群文件系统，或直接用 Windows 故障转移集群

└── 单机容量不够、需要横向扩展
    ├── 已经在用 Ceph → CephFS
    ├── HPC/超算场景 → Lustre
    └── 简单大容量存储 → GlusterFS
```

## 六、速查表

**一句话区分：**

| 协议 | 一句话 |
|------|--------|
| NFS v3 | Linux 最简单的文件共享，无状态但锁不可靠 |
| NFS v4 | 有状态，锁靠谱，支持 Kerberos，pNFS 能跑线速 |
| SMB 3.0 | Windows 标配，Multichannel + RDMA 是王炸组合 |
| GlusterFS | 无中心分布式，加节点就扩容 |
| CephFS | 跟 RBD/RGW 共享 Ceph 集群 |
| Lustre | 全地球最快的文件系统之一，TOP500 超算标配 |

**挂载参数避坑：**

| 情况 | 建议 |
|------|------|
| NFS v3 挂载大文件读写 | `rsize=1048576,wsize=1048576` |
| NFS 需要高可靠、支持并发锁 | 上 v4，别用 v3 + NLM |
| NFS 跨公网或不信任网络 | 必须 v4 + Kerberos |
| SMB Linux 挂载 | `mount -t cifs`，加 `vers=3.0` |
| SMB 需要高吞吐 | 开 Multichannel，上 RDMA 网卡 |
