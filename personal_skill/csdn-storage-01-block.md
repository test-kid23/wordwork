# 块存储协议深度拆解：iSCSI、FC、NVMe-oF 怎么选

> 上篇汇总里说了块存储是"给你一块远程硬盘"。这篇拆开讲三种主流块存储协议到底差在哪，以及你在不同场景下该怎么选。

---

## 一、块存储的工作方式：一句话讲清楚

块存储的本质是把远端存储设备上的逻辑卷（LUN），通过网络映射到你的服务器上，操作系统看到的是一块裸盘。

你用 `fdisk -l` 能看到 `/dev/sdb`，可以用 `mkfs.ext4` 格式化，可以 `mount`。跟本地插了一块 SAS 盘体验几乎一样。

关键区别在于**数据怎么从你的服务器飞到存储设备**——这个"飞"的过程，就是协议干的事。

---

## 二、FC：企业级 SAN 的祖宗

FC 全称 Fibre Channel，光纤通道。它不是在以太网上跑存储协议，而是**自成一派——专用 FC 网络、专用 FC HBA 卡、专用 FC 交换机**。

### 工作方式

FC 协议栈分五层（FC-0 到 FC-4），从物理层的光纤信号到上层的 SCSI 命令映射，全栈自己定义。以太网上的 TCP/IP 跟它没关系。

数据传输单元是 FC Frame（约 2148 字节），比以太网帧大，减少了小包碎片。

### 核心优势

- **极低延迟**：专用硬件卸载协议处理，端到端延迟通常在 100μs 以内
- **无损网络**：FC 有 Buffer-to-Buffer Credit 流控机制，不会丢包，没有 TCP 重传那套开销
- **成熟生态**：EMC、Hitachi、IBM 的 SAN 存储，几十年没出过大事

### 代价

- 贵。一台 FC 交换机几万起，一块双口 32Gb FC HBA 卡两三千。还要单独拉光纤布线
- 运维门槛高。FC 网络排障跟以太网不是一个体系，Zoning、WWN、FLOGI 这些概念得另学
- 扩展性不如以太网。加一台新服务器 = 配新卡 + 配 Zoning + 配 LUN Masking，每一步都得手工做

### 什么时候用 FC

金融核心交易系统、电信计费、银行核心账务——对**延迟的稳定性和数据的绝对可靠性**要求极端的场景。其他的，一般来说没必要。

---

## 三、iSCSI：用普通网卡跑 SAN

iSCSI 的思路是**把 SCSI 命令封装在 TCP/IP 包里面，走标准以太网**。不需要专用硬件，你服务器上那块万兆网卡就能跑。

### 工作方式

一个 iSCSI 会话里分两种角色：
- **Initiator**：发起方，你的服务器。通过 iSCSI 软件（Linux 下是 `open-iscsi`）或硬件 iSCSI HBA 连接 Target
- **Target**：目标端，存储设备。暴露 LUN 给 Initiator

数据流：应用 → SCSI 层 → iSCSI 封装 → TCP/IP 栈 → 以太网网卡 → 交换机 → 存储。

因为走标准 TCP/IP，交换机、网线、网卡全用通用件。部署成本比 FC 低一个数量级。

### 性能要点

iSCSI 的瓶颈在 TCP/IP 协议栈的 CPU 开销。纯软件 iSCSI 在小包 IOPS 场景下，CPU 可能先于网卡打满。

解决方案：
- **硬件 iSCSI HBA**：把 TCP 卸载和 iSCSI 协议处理交给专用芯片。性能和 FC 接近，价格也接近
- **iSER（iSCSI Extensions for RDMA）**：用 RDMA 代替 TCP，延迟大幅降低。需要 RoCE 或 InfiniBand 网络
- **巨型帧（Jumbo Frame）**：把 MTU 从 1500 调成 9000，存储流量一次能传更多数据，减少包数量和 CPU 中断

### 配置复杂度

一个 Linux 服务器配 iSCSI Initiator 大概是这几步：

```bash
# 安装
apt install open-iscsi

# 发现 Target
iscsiadm -m discovery -t sendtargets -p 192.168.100.10:3260

# 登录
iscsiadm -m node -T iqn.2026-07.com.example:target1 -p 192.168.100.10:3260 -l

# 之后 fdisk -l 就能看到新盘了
```

### 什么时候用 iSCSI

中小企业虚拟化平台（VMware ESXi 挂 iSCSI datastore、Proxmox 挂 iSCSI 存储）、部门级数据库、不想在 FC 上砸钱的场景。10GbE/25GbE 网络普及后，iSCSI 在中端市场的地位越来越稳。

## 四、NVMe-oF：为闪存时代设计的块协议

上面两个协议的共同祖宗是 **SCSI 命令集**——九十年代为机械硬盘设计的东西。SCSI 的命令队列深度只有 32，而一块 NVMe SSD 的硬件队列深度是 64K 个队列，每队列 64K 条命令。

用 SCSI 命令集去驱动 NVMe SSD，就像一个法拉利引擎接了一根助力车排气管——再好的盘都发挥不出来。

NVMe-oF 就是**把这个瓶颈拆掉**：把 NVMe 的原生命令集直接搬到网络上，不经过 SCSI 翻译层。

### 传输层选项

NVMe-oF 支持多种传输层：

| 传输方式 | 网络要求 | 延迟 | 适用场景 |
|---------|---------|------|---------|
| **NVMe-oF over RDMA（RoCE v2）** | RoCE 网卡 + DCB 交换机 | <10μs | 高性能数据库、AI 训练 |
| **NVMe-oF over TCP** | 标准以太网 | 30-50μs | 通用场景，比 iSCSI 快且不需要专用网卡 |
| **NVMe-oF over FC** | FC 网络 | <10μs | 已有 FC 基础设施升级，FC-NVMe 协议 |

最值得关注的是 **NVMe-oF over TCP**——它不需要 RDMA 网卡，标准以太网就能跑，但协议栈比 iSCSI 短得多，延迟少一大截。对于不想在网络上投入太多的团队，这是块存储升级的性价比路线。

### 为什么比 iSCSI 快

核心是三个层面：

1. **命令集更高效**：NVMe 只需要一个 Doorbell 寄存器写操作就能提交一批命令，SCSI 要走多层 I/O 栈
2. **队列深度碾压**：64K 队列 vs 1 个队列，多核 CPU 并发读写不打架
3. **中断合并**：NVMe 支持 MSI-X 和中断聚合，减少 CPU 打断

实测数据：相同硬件，NVMe-oF over TCP 的 IOPS 是 iSCSI 的 1.5-3 倍，延迟低 40%-60%。

### 什么时候用 NVMe-oF

全闪存储 + 高性能数据库、AI/ML 训练数据读写、高频交易——任何对 IOPS 和延迟有极端要求的场景。有 RDMA 网络就上 NVMe-oF over RDMA，没有就上 NVMe-oF over TCP，都比 iSCSI 强。

## 五、Ceph RBD：软件吃掉硬件

前面三个协议都依赖专用存储硬件（SAN 阵列）。Ceph RBD 反其道而行——**用普通 x86 服务器 + 本地盘拼出一个分布式块存储池**。

### 工作方式

Ceph 集群里有 OSD（负责存数据）和 Monitor（负责管集群状态）。你用 `rbd create` 创建一个块设备镜像，它被切成 4MB 的 Object 均匀分布到所有 OSD 上。

客户端通过 `librbd` 直接跟 OSD 通信，不需要经过中心化网关。数据放哪由 CRUSH 算法计算，所以没有元数据服务器的瓶颈。

### 相比传统 SAN 的差异

| 维度 | 传统 SAN（FC/iSCSI） | Ceph RBD |
|------|---------------------|----------|
| 硬件 | 专用存储阵列 | 通用 x86 服务器 |
| 扩展 | 买新阵列 / 加盘柜 | 加服务器自动 rebalance |
| 成本 | 高 | 低（硬件 + 开源） |
| 性能模型 | 可预测、稳定 | 依赖集群规模和网络 |
| 运维复杂度 | 硬件排障为主 | 软件排障为主 |

Ceph 的问题是**性能调优门槛高**。PG 数量、Crush Map 设计、OSD 内存配置、网络分离——每个参数调错了性能都能打骨折。但如果团队有 Ceph 运维经验，它是云平台块存储的标配方案。

## 六、四者对比速查

| 维度 | FC | iSCSI | NVMe-oF (TCP) | Ceph RBD |
|------|-----|-------|---------------|----------|
| **网络** | 专用 FC SAN | 标准以太网 | 标准以太网 | 标准以太网 |
| **硬件要求** | FC HBA + FC 交换机 | 普通网卡 | 普通网卡 | 普通网卡 |
| **延迟** | ~100μs | 200-500μs | 30-50μs | 视集群而定 |
| **成本** | 极高 | 低 | 低 | 低（硬件）+ 运维人力 |
| **扩展性** | 受阵列限制 | 受阵列限制 | 受阵列限制 | 横向加节点 |
| **运维门槛** | 高（FC 知识体系） | 低（IP 网络通用） | 中 | 高（Ceph 知识体系） |
| **适合谁** | 金融/电信核心 | 中小企业通用 | 高性能场景升级 | 云平台/自建私有云 |

## 七、选型决策路径

按你的条件走决策树：

```
你有专用 SAN 存储硬件吗？
├── 有
│   ├── 是 FC SAN？
│   │   ├── 是 → 继续用 FC，性能敏感场景迁 NVMe-oF over FC
│   │   └── 否（IP SAN）→ 看你追求什么
│   │       ├── 追求最佳性能 → NVMe-oF over TCP
│   │       └── 追求成本/简单 → iSCSI
│   └── 没有专用硬件，想用 x86 攒 → Ceph RBD
│
└── 你在选新方案？
    ├── 预算充足 + 延迟极敏感 → NVMe-oF over RDMA
    ├── 预算中等 + 全闪存储 → NVMe-oF over TCP
    ├── 预算有限 + 混合盘/HDD → iSCSI
    └── 自建云平台 → Ceph RBD
```

## 八、速查表

**一句话区分四种块存储方案：**

| 方案 | 一句话 |
|------|--------|
| FC | 最稳最贵，金融核心在用 |
| iSCSI | 最通用，普通网卡就能跑 SAN |
| NVMe-oF | 最快，把 NVMe SSD 的速度搬到网络上 |
| Ceph RBD | 最灵活，用软件替代专用硬件 |

**如果想进一步了解：**

- NVMe-oF 的 RDMA 模式需要 RoCE v2 网络，交换机要支持 DCB/PFC。网络条件不具备的话先上 NVMe-oF over TCP，别硬上 RDMA。
- Ceph RBD 的性能调优是另一个大话题（PG 规划、OSD 内存、SSD 分层），前面汇总篇提到的 RADOS 协议深度篇会展开。
