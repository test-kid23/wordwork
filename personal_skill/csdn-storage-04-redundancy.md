# 数据冗余完全指南：多副本与纠删码，从原理到选型

> 存储系统的数据冗余就两种思路——多复制几份，或者算个方程存校验块。这篇把两种方案的写入路径、放置策略、重建流程、配比选择全部拆开讲清楚。

---

## 一、两种思路，账先算清

你要存 100TB 有效数据。不管用哪种冗余，本质上都在回答同一个问题：**坏了几块盘 / 几个节点之后，数据还能不能完整读回来？**

两种解法：

- **多副本**：数据存 N 份，每份一模一样。坏了一份，读另一份。
- **纠删码**：把数据切成 M 块，算出 N 个校验块，总共 M+N 块分散存储。只要还剩下至少 M 块，丢哪些都无所谓。

先拉一下成本账：

| 冗余方式 | 实际占用 | 有效利用率 | 100TB 有效数据的月存储成本（假设 3 毛/GB） |
|---------|---------|-----------|--------------------------------------|
| 2 副本 | 200TB | 50% | 6 万 |
| 3 副本 | 300TB | 33% | 9 万 |
| EC 4+2 | 150TB | 67% | 4.5 万 |
| EC 8+3 | 137.5TB | 73% | 4.1 万 |
| EC 16+4 | 125TB | 80% | 3.75 万 |

同样 100TB 有效数据，EC 16+4 比 3 副本每月省一半以上。但省钱不是白送的，往下看你就会知道代价在哪。

## 二、多副本：简单粗暴但可靠

### 写入路径

客户端写数据时，数据流是这个顺序：

```
客户端 → 主副本节点（Primary）→ 从副本节点 1（Secondary）→ 从副本节点 2 → 主副本回复客户端 ACK
```

Ceph 和大多数分布式存储都走这个主从复制模型。客户端只跟主副本打交道，主副本负责把数据同步到从副本。同步完成（或达到一致性要求的最低副本数）后回复写入成功。

### 放置策略：副本不能随便放

多副本的可靠性前提是**副本不能在同一故障域里**。把 3 个副本全放同一台机器的 3 块盘上——机器一挂，3 个副本一起没。

成熟系统都支持分层故障域策略：

| 策略级别 | 副本分布 | 能扛什么故障 |
|---------|---------|------------|
| **OSD 级** | 不同磁盘 | 单盘故障 |
| **Host 级** | 不同服务器 | 整机宕机 |
| **Rack 级** | 不同机架 | 机架断电/交换机故障 |
| **Row 级** | 不同排 | 一排的电源故障 |
| **DC 级** | 不同数据中心 | 整个机房灾难 |

生产环境最少要开 **Host 级**。如果你说"3 副本放同一台机器上"，跟单副本没有本质区别——软件挂了、电源挂了、网卡挂了，三个副本一起死。

Ceph 的 CRUSH Map 里配置 host/rack/dc 层级就是这个目的。数据写入时 CRUSH 算法保证选出的 OSD 来自不同故障域。

### 一致性：是不是写完就能读到？

多副本的写入一致性，取决于你选什么级别：

| 一致性级别 | 含义 | 写入延迟 | 数据安全 |
|-----------|------|---------|---------|
| `one` | 主副本写入确认即返回 | 最低 | 从副本挂可能丢数据 |
| `quorum` | 半数以上副本确认 | 中等 | 标准安全级别 |
| `all` | 全部副本确认 | 最高 | 最安全，任一节点挂写失败 |

`quorum` 是生产环境的标准配置。3 副本 + quorum 写入 = 主副本 + 至少 1 个从副本确认，写入成功。此时数据已经在 2 个物理节点上落盘，单节点故障不影响读写。

一个容易忽略的点：读的时候也有一致性级别。默认读主副本（最强一致），但也可以设置读任意副本（降低延迟、提高吞吐）。**读写一致性级别如果都设成 `one`，你读到的数据可能不是最新的。** 这不是 bug，是分布式系统的设计取舍。

### 副本重建：坏了一块盘之后

节点挂了之后发生的事：

```
1. Monitor 检测到 OSD down（默认超时 300 秒）
2. Monitor 标记该 OSD 为 out（再过 600 秒）
3. CRUSH 算法重新计算受影响 PG 的新 OSD 成员
4. 新 OSD 从健康副本全量复制数据
5. 复制完成 → PG 状态恢复 active+clean
```

重建速度取决于三个因素：
- **数据量**：该 OSD 上的数据总量
- **网络带宽**：重建流量和其他业务流量抢带宽
- **磁盘吞吐**：新 OSD 写的速度

重建期间系统处于降级状态（degraded），此时如果再坏一个副本——3 副本如果只剩 1 个健康副本，数据就危险了。所以**重建速度直接等于数据安全性**，这也是为什么 Ceph 有 `osd_max_backfills` 等参数限制重建并发数——太快会把集群打满，太慢则增加风险窗口。

### 到底要几副本？

| 副本数 | 可用容量 | 最大容忍故障 | 典型场景 |
|--------|---------|-------------|---------|
| 2 副本 | 50% | 1 个节点 | 测试环境、可接受丢数据 |
| 3 副本 | 33% | 2 个节点 | **生产环境标准配置** |
| 4 副本 | 25% | 3 个节点 | 极少数高安全场景 |

3 副本是绝大多数场景的正确选择。2 副本的风险是重构期间只剩 1 个副本——没有任何冗余兜底。4 副本多出来的安全性不如把钱花在 EC 冷数据方案上。

## 三、纠删码：用数学换空间

### 数学直觉

先抛开矩阵不谈，用最简单的方式理解：

你需要记住一个数字 `3847`。直接背三遍（3 副本）是一种办法。更聪明的是准备两条方程：

> X = 3847
> X × 3 = 11541

把 3847 给 A 记住，11541 给 B 记住。A 忘了 → B 手里有 11541，除以 3 得 3847。B 忘了 → A 直接有答案。两条信息，丢任意一条都能恢复。

这就是 EC 的最简模型：1 个数据块 + 1 个校验块，允许丢 1 块。

现实中的 EC 用的是有限域 GF(2^w) 上的矩阵运算，但直觉不变：**M 个数据块算出 N 个校验块，只要还剩下 ≥ M 个块，不管丢了哪些，都能解方程还原。**

### 编码过程：EC(4,2) 为例

第 1 步，把数据切成 M 个等长块：

```
原始数据: [D0][D1][D2][D3]          ← 4 个数据块
```

第 2 步，用编码矩阵生成校验块：

```
编码矩阵 (6×4):          数据向量 (4×1):     结果 (6×1):
[ 1  0  0  0 ]          [ D0 ]           [ D0 ]  ← 直接保留
[ 0  1  0  0 ]          [ D1 ]           [ D1 ]  ← 直接保留
[ 0  0  1  0 ]     ×    [ D2 ]     =     [ D2 ]  ← 直接保留
[ 0  0  0  1 ]          [ D3 ]           [ D3 ]  ← 直接保留
[ a0 a1 a2 a3 ]                           [ P0 ]  ← 校验块 1
[ b0 b1 b2 b3 ]                           [ P1 ]  ← 校验块 2
```

上半部分单位矩阵保证前 4 个输出就是原数据。下半部分是 Reed-Solomon 编码矩阵的核心——**任意 4 行线性无关**，这是丢任意 2 块能恢复的数学保证。

第 3 步，把 6 个块分散到 6 个不同故障域（至少不同节点）：

```
节点 1: D0    节点 3: D2    节点 5: P0
节点 2: D1    节点 4: D3    节点 6: P1

最多 2 个节点同时坏 → 数据不丢
```

### 解码过程：丢了怎么恢复

假设节点 1（D0）和节点 5（P0）挂了，剩下 D1、D2、D3、P1。

从编码矩阵里抽出存活块对应的 4 行，得到一个 4×4 的子矩阵。因为任意 4 行线性无关，这个子矩阵一定可逆。然后：

```python
# 伪代码
survivor_matrix = extract_rows(encoding_matrix, [2, 3, 4, 6])  # 4×4
inverse = invert(survivor_matrix)
original_data = inverse × [D1, D2, D3, P1]                      # 恢复 D0-D3
```

丢的是数据块还是校验块无所谓——校验块在恢复过程中和数据块等价。只要存活块数量 ≥ M，就能完整恢复。

## 四、EC 实战配比选择

EC 不是 M 和 N 越大越好。N 越大存储利用率越高，但重建读放大越严重——EC(16,4) 恢复一个丢失数据块需要读其他 16 个块。

| EC 配比 | 利用率 | 最少节点数 | 容错 | 重建读放大 | 适用场景 |
|---------|--------|-----------|------|-----------|---------|
| 4+2 | 67% | 6 | 2 节点 | 4x | 中小规模通用 |
| 8+2 | 80% | 10 | 2 节点 | 8x | 大容量、故障率可控 |
| 8+3 | 73% | 11 | 3 节点 | 8x | 大容量、高可靠性 |
| 16+4 | 80% | 20 | 4 节点 | 16x | 超大冷数据归档 |

选 N 的一个反直觉经验：**集群不够大的话，N 太大反而降低安全性。** 因为重建时间被读放大拖长，重建期间再坏一块的概率同步上升。Ceph 社区的建议：几十个 OSD 用 4+2，上百 OSD 用 8+3，几百以上考虑 16+4。

## 五、亚节点纠删码：解决传统 EC 的重建痛点

传统 Reed-Solomon EC 有一个绕不开的问题：**恢复一个丢失块需要读取 M 个块**。EC(16,4) 丢了一个数据块，要跨 16 个节点读 16 个块才能重建——网络带宽和 IO 压力全部集中在恢复窗口内。

**亚节点纠删码**就是为解决这个问题而生的。核心思路：**在全局校验之外，再加一层局部校验，让大多数故障在局部范围内就能恢复，不用惊动整个集群。**

### 5.1 亚节点 EC 的表示法

行业里亚节点 EC 统一用 `M+N:L` 表示：

```
M+N:L = M 个数据块 + N 个全局校验块 + L 个本地校验组
```

L 表示**本地校验组的数量**，每组内包含一部分数据块 + 1 个本地校验块。组数和每组数据块数的乘积就是 M。

常见客户部署配比如下：

| 亚节点配比 | 数据块 | 全局校验 | 本地校验组 | 每组数据块数 | 总块数 | 利用率 | 容错 |
|-----------|--------|---------|-----------|------------|--------|--------|------|
| **4+2:1** | 4 | 2 | 1 组 | 4 | 7 | 57% | 丢任意 2 块，或全组丢完 + 1 全局校验 |
| **4+2:2** | 4 | 2 | 2 组 | 2 | 8 | 50% | 丢任意 2 块，不同组各丢 1 块仅需局部恢复 |
| **8+2:1** | 8 | 2 | 1 组 | 8 | 11 | 73% | 丢任意 2 块，单块丢需读 8 块 |
| **8+2:2** | 8 | 2 | 2 组 | 4 | 12 | 67% | 丢任意 2 块，单块丢只需读 4 块 |
| **8+3:2** | 8 | 3 | 2 组 | 4 | 13 | 62% | 丢任意 3 块，兼顾高容错与局部恢复 |
| **12+3:3** | 12 | 3 | 3 组 | 4 | 18 | 67% | 丢任意 3 块，大集群下恢复几乎无全局流量 |

注意 `4+2:1` 和 `4+2:2` 的区别：同样是 4 个数据块 + 2 个全局校验，`4+2:2` 把 4 个数据块拆成 2 组（每组 2 个），每组各多算 1 个本地校验块。多跑了 1 个额外校验块的成本，换来重建时只需读 2 块而不是 4 块。

### 5.2 用 `4+2:2` 拆解 LRC 原理

LRC（Locally Repairable Codes，本地可修复编码）由微软 Azure 团队提出并大规模验证，Ceph、HDFS 3.x 都已支持。

以 `4+2:2` 为例拆解结构——4 个数据块、2 个全局校验块、2 个本地校验组：

```
4+2:2 数据布局

第 1 组（2 数据 + 1 本地校验）：     第 2 组（2 数据 + 1 本地校验）：
D0  D1  L0                          D2  D3  L1

全局校验（覆盖全部 4 个数据块）：
G0  G1

共 8 个块，利用率 50%
```

对比传统 `4+2`（EC(4+2)）：

```
传统 EC(4+2)：共 6 个块，利用率 67%

D0  D1  D2  D3
P0  P1

恢复 D0：需读 D1 D2 D3 P0（4 块，跨 4 节点）
```

`4+2:2` 共 8 个块（多了 L0、L1），利用率 50%：

```
恢复 D0：只需读 D1 L0（2 块，本组 2 节点即可）
```

**校验块生成关系：**

```
全局校验：
G0 = RS(D0, D1, D2, D3)      ← Reed-Solomon，覆盖全部 4 个数据块
G1 = RS(D0, D1, D2, D3)      ← Reed-Solomon

本地校验：
L0 = XOR(D0, D1)             ← 仅覆盖第 1 组
L1 = XOR(D2, D3)             ← 仅覆盖第 2 组
```

本地校验块通常用 XOR 就够了——组内块数少，XOR 计算几乎零开销。全局校验继续用 Reed-Solomon 保证任意 M 块可恢复。

### 5.3 故障恢复的三种路径

拿 `8+2:2`（8 数据、2 全局校验、2 本地组，每组 4 数据 + 1 本地校验）说清楚：

```
8+2:2 数据分布（12 节点）：

第 1 组（4 数据 + 1 本地）：      第 2 组（4 数据 + 1 本地）：
节点 1: D0                       节点 6: D4
节点 2: D1                       节点 7: D5
节点 3: D2                       节点 8: D6
节点 4: D3                       节点 9: D7
节点 5: L0                       节点 10: L1

全局校验（2 个节点）：
节点 11: G0
节点 12: G1
```

**故障恢复的三种情况：**

| 故障情况 | 怎么恢复 | 读块数 | 网络影响 |
|---------|---------|--------|---------|
| 丢 1 个数据块（如 D0） | 读本组内 D1 D2 D3 + L0 | 4 块 | 仅组内 4 节点 |
| 丢 1 个本地校验（如 L0） | 本组内 D0-D3 重新 XOR | 4 块 | 仅组内 4 节点 |
| 丢 2 块且在同一组 | 组内只剩 3 块不够 → 动用 G0 G1 + 全集群幸存数据 | 8 块 | 12 节点全集群 |
| 丢 2 块但在不同组 | 各组独立用本地校验恢复 | 每组 4 块 | 各自组内 |

绝大多数单盘/单节点故障属于第一种情况——**一次只丢一个块**。LRC 在 90% 以上的实际故障场景中只需要读局部数据，避免了跨集群重建风暴。

### 5.4 客户常用配比推荐

以下是生产环境经过验证的常见配比，直接按场景选：

| 配比 | 利用率 | 最少节点 | 容错 | 单故障恢复读 | 适用场景 |
|------|--------|---------|------|-------------|---------|
| **4+2:1** | 57% | 7 | 2 块 | 4x | 小规模、低配比也够用。本地组=1 意味着没有分组，等价于传统 EC(4,2)，但因各厂商实现了 LRC 编码器所以仍用此表示法。实际部署 6-10 节点。 |
| **4+2:2** | 50% | 8 | 2 块 | 2x | 最小规模的真正亚节点。2 个数据块一组，恢复极轻量。适合 10 节点以内、对重建延迟敏感的场景。 |
| **8+2:1** | 73% | 11 | 2 块 | 8x | 等于传统 EC(8,2)，无分组。适合对恢复速度不敏感、优先要利用率的场景。 |
| **8+2:2** | 67% | 12 | 2 块 | 4x | **最热门的客户配比**。平衡利用率（67%）和恢复速度（4x 读）。12 节点起，中型集群首选。 |
| **8+3:2** | 62% | 13 | 3 块 | 4x | 8 数据分 2 组，全局 3 校验。比 `8+2:2` 多一层全局容错，同时保持局部恢复。高可靠性要求场景。 |
| **12+3:3** | 67% | 18 | 3 块 | 4x | 大集群（20+ 节点）。12 数据分 3 组，每组 4 块 + 本地校验。利用率和 `8+2:2` 一样 67%，但容错多 1 块、恢复同样 4x。 |

**选型速判：**

- 10 节点以内、在乎恢复速度 → `4+2:2`
- 12-20 节点、标准需求 → `8+2:2`（最常用）
- 20 节点以上、利用率优先 → `12+3:3`
- 对恢复速度不敏感、纯冷数据 → `8+2:1`（回归传统 EC，省空间）
- 高可靠性要求、容忍 3 块故障 → `8+3:2`

### 5.5 存储开销对比

多存了本地校验块，空间利用率会下降。以下是同等容错能力（能丢 2 块全局校验）下的对比：

| 方案 | 总块数 | 利用率 | 单故障恢复读放大 | 恢复范围 |
|------|--------|--------|----------------|---------|
| 传统 EC `4+2` | 6 | 67% | 4x | 全集群 |
| 亚节点 `4+2:2` | 8 | 50% | 2x | 组内 |
| 传统 EC `8+2` | 10 | 80% | 8x | 全集群 |
| 亚节点 `8+2:2` | 12 | 67% | 4x | 组内 |
| 传统 EC `12+3` | 15 | 80% | 12x | 全集群 |
| 亚节点 `12+3:3` | 18 | 67% | 4x | 组内 |

多付出 10%-17% 的额外存储空间，换来恢复读放大砍半甚至更多。在 PB 级以上集群中，这个交换非常划算。

### 5.6 LRC 之外的亚节点方案

**SHEC（Shingled Erasure Code）**：Ceph 自有的亚节点方案。不同于 LRC 的显式分组，SHEC 用滑动窗口方式生成校验块——每个校验块只覆盖部分数据块，天然形成局部可修复特性。配置更灵活但概念比 LRC 抽象、排障心智成本更高。

**Clay Code（耦合层码）**：把多个 EC 条带"叠"在一起，让不同条带的校验块之间产生关联。单个条带的恢复可以借用相邻条带的数据，减少读取量。理论上是亚节点 EC 的最优解之一，但实现复杂，目前主要在学术界和少数大规模系统（如 Facebook f4）中验证。

**一般选型建议**：亚节点方案首推 LRC。Ceph 从 Luminous 版本开始原生支持，HDFS 3.x 的 HDFS EC 也基于 LRC 思路（用 XOR 做本地校验 + RS 做全局校验）。SHEC 如果团队对 Ceph 有深度运维经验也可以考虑；Clay Code 目前不适合一般生产环境。

## 六、多副本 vs 纠删码：分层用，不二选一

| 维度 | 多副本 | 传统 EC | 亚节点 EC |
|------|--------|---------|-----------------|
| 空间利用率 | 33%-50% | 67%-86% | 50%-73% |
| 写路径 CPU 开销 | 几乎没有 | 编码计算 | 编码计算 + 本地校验 |
| 读路径延迟 | 低（读任意健康副本） | 正常读不加开销 | 正常读不加开销 |
| 数据重建速度 | 快（复制即可） | 慢（读 M 个块） | 较快（读局部组即可） |
| 重建时读放大 | 1x | Mx | ~(M/L)x（L 为组数） |
| 小 IO 写入 | 无感 | 放大严重 | 放大更严重（额外本地校验） |
| 适合数据 | 热数据、高 IOPS | 冷数据、大容量 | 温数据、需兼顾重建速度的冷数据 |

正确用法是分层：

```
热数据（数据库、虚拟机系统盘）→ 3 副本
温数据（近期日志、活跃数据集）→ 8+2:2 或 4+2:2
冷数据（归档、备份）→ EC(8+3) 或 EC(16+4)（单纯 EC 即可，重建慢无所谓）
```

Ceph 的 Cache Tiering、MinIO 按 Bucket 设置 EC 策略，都是这个思路。

## 七、RAID 是 EC 在单机上的特例

单机盘组做 Reed-Solomon 编码就是 RAID 5/6：

| | RAID 5 | RAID 6 | EC(4+2) |
|------|--------|--------|---------|
| 数学本质 | RS 编码，1 校验 | RS 编码，2 校验 | RS 编码，2 校验 |
| 作用范围 | 一组本地磁盘 | 一组本地磁盘 | 跨网络节点 |
| 校验块数 | 1 | 2 | 可配 |
| 粒度 | Stripe | Stripe | Object/Chunk |

分布式 EC 把同样的数学从"一个盘组"扩展到"一组服务器"。但带来的新问题是：RAID 重建读放大局限在 4-12 块盘内，分布式 EC 重建要读整个集群的数据——网络流量和计算压力不是同一个量级。这是分布式 EC 落地的最大工程难点。

### RAID 经典配比快速参考

| RAID 级别 | 最少盘数 | 可用容量 | 允许坏盘 | 一句话 |
|-----------|---------|---------|---------|--------|
| RAID 1 | 2 | 50% | 1 块 | 镜像，最简单 |
| RAID 5 | 3 | (n-1)/n | 1 块 | 大容量盘不推荐，重建风险高 |
| RAID 6 | 4 | (n-2)/n | 2 块 | 大容量机械盘标配 |
| RAID 10 | 4 | 50% | 每组 1 块 | 性能和冗余最均衡 |

额外提醒：16TB 以上的大容量 HDD，**别用 RAID 5**。坏一块重建一整天，重建途中再坏一块数据全没。RAID 6 才是大容量盘的底线。

## 八、速查表

**多副本 vs EC 选型一句话：**

| 你的场景 | 用什么 |
|---------|--------|
| 数据库、高频读写 | 3 副本 |
| 虚拟机系统盘 | 3 副本 |
| 对象存储热数据 | 3 副本 |
| 对象存储冷数据 | EC(8+3) |
| 备份归档 | EC(16+4) |
| 中小规模存储集群 | 多副本 EC(4+2) |
| 大容量单机 | RAID 6，别用 RAID 5 |

**容易踩的坑：**

| 坑 | 说明 |
|----|------|
| 多副本没配故障域 | 3 副本放同一台机器 = 单副本 |
| EC 配太大 M/N | M 太大重建读放大严重，N 太大反而降低安全性 |
| 冷热数据不分层 | 统一 3 副本太贵，统一 EC IOPS 扛不住 |
| 大容量盘用 RAID 5 | 16TB 盘重建超过 24 小时，风险窗口太大 |
| EC 写小 IO | 每次都重新编码，写入放大可观 |
