🧠 Claude Code 实战

你自己写的脚本能直接喂给 AI 当工具？
Claude Code 插件系统让 GPT 程序员变架构师

Claude Code 支持自定义 hooks 和 slash commands。写一段 python 脚本，配个 JSON，它就能调用你的"专属工具"。从此 Claude 不再是只会写代码——它有了你自己的武器库。

📝 写在前面：跟 Claude Code 对话了两个星期之后，你可能会有一个念头："如果它能直接查我的 Jira 任务呢？""如果它能自己写 Kafka 消息来触发部署呢？""如果它能调用我们公司的 eslint 规则来审核规范呢？"

这些都不是 Claude Code 内置的能力。但它的插件系统可以让这些事成为现实。用你自己写的工具，扩展 Claude 能做的事情。这篇不做抽象介绍——直接看怎么配、怎么写、怎么用。

1 hooks 机制：什么时候触发你的代码

Claude Code 的 hooks 是在 AI 的"生命周期事件"上执行你指定的命令。跟 Git hooks 一个逻辑。

📌 可用的事件

PreToolUse：工具调用之前触发 — 可以拦截、验证、阻止
PostToolUse：工具调用之后触发 — 可以记录、校验结果
Notification：AI 发消息时触发 — 可以做格式化、翻译
Stop：对话停止时触发 — 可以做清理、保存日志
UserPromptSubmit：你提交消息时触发 — 可以自动注入上下文

📌 配置文件位置

两种配置方式：

全局配置：~/.claude/settings.json
项目配置：项目根目录/.claude/settings.json（优先级更高）

📌 最简单的一个 hook

在每次文件被写入之后，自动跑 lint：

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{"type": "command", "command": "npx eslint --fix $CLAUDE_PROJECT_DIR"}]
      }
    ]
  }
}

这段配置的意思是：当 Claude 使用 Write 或 Edit 工具修改了文件之后，自动跑 eslint --fix。写完代码 → 自动格式化 → 你少一次手动操作。

📌 hook 可以用来做这三件事

① 质量把关 — 每次写入后自动跑 lint、format、test——保证 AI 生成的代码符合团队规范。你不需要每次手动检查。

② 安全审计 — 拦截包含特定模式的代码。如果 AI 想写 process.env.SECRET 到日志里——PreToolUse hook 可以拒绝。

③ 上下文注入 — UserPromptSubmit 时自动往里面加"当前时间 → 2025-07-29 14:30"。这样 Claude 知道你什么时候在用它。

2 自定义 slash command：写你自己的 / 扩展

除了 hooks，你还可以写自定义的 slash command——让你在对话窗口里直接调自己的工具。

📌 结构

一个 slash command 是 .claude/commands/ 目录下的一个 markdown 文件。

.claude/commands/
├── deploy.md
├── review.md
└── test-coverage.md

文件内容就是一段 prompt——但它可以引用上一个对话上下文、项目文件、甚至环境命令。

举个最简单的 /review 命令：

# review.md

对最近改动的文件做一轮 Code Review。
规则：
- 检查循环复杂度和函数长度
- 列出可能被忽略的 edge case
- 如果有 console.log 或测试代码没清理掉，标出来
- 输出一个 1-10 的改动信心分，低于 6 分的地方单独列出

然后对话里输入：

/review

Claude 会自动加载 review.md 的内容作为 prompt 执行。

📌 传参数

slash command 还可以传参数。在 markdown 里用 $ARGUMENTS 或 $1, $2 来接收：

# jira.md

用以下 Jira ticket 信息创建一个分支：
- Ticket ID: $1
- Title: $2

用 ID 和标题生成 branch name，格式为 feature/TICKET_ID-description

使用：

/jira PAY-421 "修复退款流程的状态机 bug"

3 手把手写第一个插件

写一个 /changelog 命令，自动从 git log 生成 changelog。

📌 第一步：写 markdown prompt

创建 .claude/commands/changelog.md：

# changelog.md

请先执行这个命令来获取 git log：
git --no-pager log $1..HEAD --oneline --no-merges

然后根据 git log 结果，生成 changelog。

规则：
- 按类型分组（feat, fix, refactor, docs）
- 每个 entry 一行
- 格式：- [feat] xxx @作者
- 最后输出一个"上次 tag 到现在的改动简要"
- 不要猜测——没有在 git log 里出现的内容不要加

📌 第二步：用它

/changelog v1.2.0

Claude Code 会执行 git log v1.2.0..HEAD，拿到输出后按你定义的规则整理成 changelog。

📌 为什么要用插件

两个关键的好处：

1. 标准化：团队的 changelog 格式统一。不是你靠嘴说"帮我生成 changelog"——每次格式不一样。现在用 /changelog，格式永远统一。

2. 减少重复：一条命令代替一堆描述。"帮我根据 git log 生成 changelog，类型分组，格式是……"→ 变成 "/changelog"。每天省 30 秒。

4 五个实用的自定义插件示例

📌 /checklist — 上线前检查

做 Pre-deploy 检查：
1. git diff 看最近改动
2. 搜索所有改动文件里的 console.log
3. 检查所有 import 路径是否有效
4. 如果 package.json 里有改动，检查是否存在 peer dependency 冲突
5. 输出一个 OK/FAIL 列表

📌 /story — 从需求生成测试用例

以下是一个用户故事：$ARGUMENTS

请生成 5-8 个测试用例，覆盖：
- Happy path（正常流程）
- Sad path（输入有误）
- Corner case（极端情况）
- State transition（状态变化）

每个用例包含：场景描述、前置条件、操作步骤、期望结果

📌 /deps — 依赖分析

分析 package.json 的依赖：
1. 哪些包版本过时（和最新稳定版对比）
2. 哪些包不是直接依赖（在代码里找不到 import 引用）
3. 哪些包有已知的安全漏洞（如果能访问的话）

输出一个整洁的报告

📌 /unittest — 给指定文件生成测试

给 $ARGUMENTS 里的每个函数生成单元测试。
测试框架：Jest + React Testing Library（如果涉及组件）
要求：
- 每个函数的每个返回路径都覆盖到
- 先写正常输入→输出，再写异常输入→错误处理
- 不要傻测 getter（比如 state = 0, expect(state).toBe(0)）
- 用真实的使用场景而不是"测试像在测试"

📌 /lint-all — 全量代码扫描

全量扫描 src/ 下所有文件：
- 文件中是否有多余的 import（ESLint 报 / unused import）
- 函数超过 50 行是否考虑拆分
- API 请求是否有错误处理
- 任何 window. / document. 直接操作（说明 SSR 可能有问题）

输出一个分文件的问题清单

5 团队共享：统一工具链

Claude Code 的插件是可以共享的。让整个团队用同一套 commands 和 hooks——统一工作流。

📌 推荐的组织方式

把 commands 目录放在项目根目录的 .claude/commands/ 下，跟代码一起版本管理：

项目根目录/
├── .claude/
│ ├── settings.json ← 项目级 hook 配置
│ └── commands/
│ ├── review.md
│ ├── deploy.md
│ ├── changelog.md
│ └── lint-all.md
├── src/
└── package.json

新成员 clone 项目后，自动拿到所有 Claude Code 插件。不用教"你该用什么命令"——所有人用同一套。

📌 共享套路

① Onboarding 新成员：克隆项目 → /setup 自动装依赖→ /init 自动配数据库→ 开始写代码。不需要"传帮带"。

② Code Review 标准化：所有人用 /review 做自审。提交前跑一遍，输出结果贴在 MR 里——不影响 Review 质量，但避免初级问题浪费 Review 时间。

③ 文档自动生成：所有人用 /changelog 和 /story。格式统一，不用手动维护。

写在最后

Claude Code 的插件系统是我觉得最被低估的部分。大家最开始接触这个工具的时候想的是"怎么让它更快地写出更多代码"。后来才明白，真正省力的是"让它能做的事变多"——让它能执行你写好的工具链。

你自己能写。Claude 也能写。但你写完之后给 Claude 配一个快捷键，叫 /deploy，以后你只需要打四个字。

💡 Claude Code 不是一只猴子。它是一个可以装备武器的战士。你给它的武器越好，它打的怪越多。
