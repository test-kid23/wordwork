# 同样一句话，换个说法效率翻 3 倍——Claude Code 提示词工程实战

> 你说了"帮我修这个 Bug"，它改了 3 个不相关的文件。你说了"分析性能瓶颈"，它给了你一篇教科书。问题不在 AI，在你没告诉它"怎么想"。

---

前几篇一直在讲 Claude Code 能做什么——接手项目、写功能、做 Review。但你可能会说："我试了，没你说的那么神。"

大概率不是你用的不对。是你**说的不对**。

同一个 Claude Code，同一段代码，你换一种说法让它干活——从"改这个"变成"检查 A、修改 B、确保 C"——结果天差地别。这一篇不讲功能，只讲一件事：**怎么让它真正听懂你。**

这不是玄学。这是工程。

## 一、好 prompt 和差 prompt 的差距有多大

### 同一个任务，两种说法

**差 prompt：**

> "帮我把用户列表的性能优化一下。"

Claude Code 收到这句话之后会做什么？猜。猜你需要加虚拟滚动、猜你需要分页、猜你需要加缓存。它能猜——但猜错概率很高。结果：改了 5 个文件，3 个改得不对，1 个改出 Bug。

**好 prompt：**

> "用户列表在数据量超过 500 条时渲染明显变慢。用 React DevTools 的 Profiler 分析 client/src/pages/UserList.tsx 的渲染瓶颈，给出 2-3 个优化方案。先不改代码，只出分析报告。"

区别在哪？五件事：

| 维度 | 差 prompt | 好 prompt |
|------|----------|----------|
| 问题范围 | "性能优化"（模糊） | "数据量 >500 条变慢"（具体） |
| 分析工具 | 没说 → 它猜 | "用 React DevTools Profiler"（指定） |
| 限定范围 | 没说 → 全项目 | "client/src/pages/UserList.tsx"（精确文件） |
| 交付形式 | 没说 → 直接改代码 | "先出分析报告，不改代码"（明确边界） |
| 方案数量 | 没说 → 给 1 个 | "2-3 个方案"（约束产出） |

差 prompt 让 Claude Code 在黑暗里摸索。好 prompt 给它手电筒和地图。

## 二、分层结构：把你的需求变成指令

一个好的 prompt 可以分解成四层。分层不是让指令更长——是让 AI 不用猜。

### 第一层：角色设定

告诉它"你是谁"，它在跟谁对话。决定了它的知识范围和语气。

> "你是一个 5 年经验的 React 前端工程师，熟悉 TypeScript 和 Ant Design 组件库。"

不加这层，它可能用初学者的方式解释。加了，它会用更精确的技术术语和更实际的工程判断。

### 第二层：任务目标

说清楚要做什么——不是怎么做，是做成什么样的结果。

> "优化用户列表页面的渲染性能，目标：在 2000 条数据下渲染时间从 1.2 秒降到 200 毫秒以内。"

注意这不是"把代码改成虚拟滚动"。那是方式，不是目标。说你想要什么结果，让它自己选最优方式。

### 第三层：约束条件

这是最关键也最容易被省略的一层。约束条件告诉它边界在哪。

> "约束条件：1）不改变现有组件的外部 props 接口，因为已经被 5 个页面调用 2）不使用新的第三方依赖，审批周期太长 3）保持对 IE11 的兼容（项目硬性要求）4）优先用 useMemo/React.memo，其次才考虑虚拟滚动。"

不加约束条件会出什么事？它可能会引入一个 50KB 的 npm 包，或者改了 props 签名让其他页面炸掉。然后你花 20 分钟把它改回去。这 20 分钟本来可以用 30 秒写约束条件省掉。

### 第四层：输出格式

告诉它你想要什么样的回答。

> "输出格式：1）一句话概述性能瓶颈 2）表格对比 3 个优化方案（方案名、原理、预计提升、风险、实施难度）3）推荐的实施步骤（按 30 分钟可完成拆分）"

有了格式约束，你不会得到一篇 2000 字的分析文章——这在一个终端里没法看。你会得到一个结构化的表格，扫一眼就能做决策。

### 四层模板

把上面的内容拼起来，就是你日常可以用的一句 prompt：

```
[角色] 你是一个有经验的 [技术栈] 工程师。

[目标] [一句话说清楚要达成什么结果，带可测量的指标]。

[约束] 1）[边界1]  2）[边界2]  3）[边界3]

[格式] 输出格式：[描述你想要的回答结构]。
```

不需要每次都四层全写。小改动可能只要目标层就够了。但越复杂的任务，越应该把这四层写全——因为你省的不是写指令的 30 秒，是返工的 20 分钟。

## 三、角色扮演：给它一个身份，它会扮演好它

### 为什么角色扮演有效

Claude Code 的训练数据里有大量的技术文档、代码、论文——这些内容的语气、深度、关注点完全不同。当你指定一个角色，你是在帮它从海量知识里**选出跟当前场景最相关的那部分**。

### 四个你应该知道的角色

**架构师模式：**

> "你现在是一个系统架构师，review 我这次的改动。关注点：架构一致性、模块耦合度、扩展性、技术债务。列出 3-5 个架构层面的问题，按严重程度排序。"

用这个角色审查你的代码，它会关注"这个抽象层次对不对"、"这个模块的边界清不清晰"——不是"变量命名不规范"这种小问题。

**代码审查者模式：**

> "你现在是一个严格的代码审查者，像 Google Code Review 的标准一样。检查：命名规范、错误处理完整性、边界条件、安全问题、代码重复。逐文件列出问题，标注行号和修复建议。"

这个角色的特点是"严格"——它会找你平时觉得"差不多就行"的地方。如果缺了"严格"两个字，它会客气很多。

**测试工程师模式：**

> "你现在是一个测试工程师，对这个模块写测试。覆盖：正常路径、边界条件、异常路径、并发场景。不要只是跑一遍 pass，要找 corner case。"

特点是它会主动想"什么情况下这个代码会出错"——而不仅仅是"写一个够通过的测试"。

**技术作家模式：**

> "你现在是一个技术作家。把这段代码的设计思路写成 500 字以内的说明，让接手的新人能在 10 分钟内理解为什么这么设计。"

这个模式在前一篇技术写作里详细聊过——不再展开。

## 四、多轮对话：不要一次性把话说死

有一个很自然的冲动：把所有要求塞进第一句话，让它一次到位。

**但这个做法往往更慢。**

### 第一轮：定方向

> "用户列表性能不行，帮我分析一下瓶颈在哪。先对 client/src/pages/UserList.tsx 做 Profiler 分析，不改代码。"

它出报告。你看完，确认瓶颈跟你猜的一样（比如确实是 2000 条数据全量渲染的问题）。

### 第二轮：选方案

> "方案 2（虚拟滚动）看起来最合适。但注意项目已经在用 react-window 了，不要引入新的虚拟滚动库。帮我实现，改动限制在 UserList.tsx 和它的直接子组件。"

它实现虚拟滚动，用已有的 react-window，不引入新依赖。

### 第三轮：验证

> "跑一下 UserList 相关的测试，确保没有破坏已有功能。再写一个性能对比：优化前后的渲染时间。"

它跑测试、出对比数据。

### 为什么多轮比一轮好

1. **你可以中途纠偏**——第一轮如果你觉得它分析偏了，改方向就行，不存在"代码已经写了再推翻"
2. **每轮的信息量更可控**——不会一次性给你 500 行改动的 diff，看得眼花
3. **上下文质量更高**——前三轮的分析结果会沉淀在对话历史里，后面的操作基于这些分析，更精准

## 五、CLAUDE.md：把"每次都说的废话"固化下来

写了这么多 prompt 技巧，但如果你每天都跟 Claude Code 协作，每次都要写"你是一个 React 前端工程师"、"项目用 Ant Design 4.x"、"不要用 class component"——这就太蠢了。

### CLAUDE.md 是干嘛的

它是 Claude Code 在你项目里的"长期记忆"。每次打开 Claude Code，它会先读 `CLAUDE.md`，把这些信息带入上下文——不需要你每次说。

### 怎么写

```markdown
# Project Context

## Tech Stack
- React 18 + TypeScript + Vite
- Ant Design 5.x（不要用 4.x 的 API）
- 状态管理用 Zustand，不用 Redux
- HTTP 请求用 axios，已有 src/utils/request.ts 封装的实例

## Code Conventions
- 组件用函数式 + Hooks，不用 class component
- 文件命名：组件用 PascalCase，工具用 camelCase
- import 顺序：第三方包 → 内部模块 → 样式
- 测试用 Vitest + React Testing Library

## Architecture Notes
- src/client/pages/ — 页面组件，一个页面对应路由
- src/client/components/ — 可复用 UI 组件
- src/client/hooks/ — 自定义 Hooks
- src/client/api/ — API 请求函数，一层封装 axios

## Current Focus
正在做用户管理模块的重构。改动涉及：
- UserList.tsx, UserDetail.tsx, UserForm.tsx
- src/client/api/users.ts
- 不要改其他模块的文件，除非明显相关
```

这个文件的价值：
- **技术栈声明**：杜绝了它用 Redux 写一个组件的可能性
- **文件命名规范**：它创建新文件时会用对的命名风格
- **当前焦点**：告诉它"现在在干什么"——减少不必要的文件改动范围
- **不写"废话"**：整个文件是**对它有约束力的事实陈述**，不是"请用 React 写代码"这种大家都知道的话

### CLAUDE.md 和 System Prompt 的配合

一个常被问的问题："CLAUDE.md 和 system prompt 有什么区别？"

- **CLAUDE.md**：跟项目走的。每个项目一个。放项目相关的技术栈、规范、架构信息。
- **System Prompt（.claude/settings.json）**：全局的。放个人偏好——"用中文回复"、"代码注释用英文"、"优先用 pnpm 而不是 npm"。

把"项目的事"放 CLAUDE.md，把"你的事"放 system prompt。不混在一起。

---

## 写在最后

这一篇写的所有技巧——分层 prompt、角色扮演、多轮对话、CLAUDE.md——都有一个共同前提：**你清楚自己要什么。**

AI 是放大器，不是替代品。它能把你"大概想做什么"变成"精准的指令执行"，但它不能猜出你自己都不确定的目标。

所以一个反直觉的真相是：**用好 Claude Code 的前提不是掌握 prompt 技巧，而是你对自己的需求想清楚了。** 花 3 分钟想清楚"我要什么结果、什么约束、什么格式"——这 3 分钟是这一篇所有技巧的前提。

所有的 prompt 技巧，只是在帮你把这 3 分钟想清楚的东西，翻译成它听得懂的话。
