🧠 Claude Code 实战

用 Claude Code 一个月烧 $87？
实测 6 种省钱方法，降到 $12

不是让你少用 AI。是用同样多的任务，花更少的钱。省下的不只是 API 费用——你省下的 context window 空间，还能拿去塞更多有效上下文。

📝 写在前面：Claude Code 按 token 计费，一个没注意，一个中等复杂度的开发任务就能烧掉几美元。一个月下来，账单可能比你的午饭钱还多。

但有意思的是：高消费不等于高产出的任务。很多时候你多花的 token，是因为你的 prompt 太长、文件给它太多、或者忘了清上下文。这篇文章用真实数字，把每一分钱花在哪、怎么省回来，讲清楚。

1 你的钱都花在哪了

📌 Token 是怎么烧掉的

Claude Code 每轮交互的 token 消耗 = 输入 token + 输出 token。输入远比输出贵——大概 3:1 的价格比。

输入 token 包括：

你的 prompt
CLAUDE.md 的内容
它自己读的文件（你每次说"分析这个文件"，它就多读一段）
对话历史（之前的所有交流，每轮都要重新发一遍）
工具调用的结果（跑命令的输出、读文件的返回）

输出 token 包括：它的文本回复、它生成的代码。

📌 一个典型任务的 token 消耗

以"在用户列表加导出功能"为例：

你的 prompt：~150 tokens
CLAUDE.md：~400 tokens
读文件（3 个文件）：~3000 tokens
跑命令（npm test）：~800 tokens
对话历史（前 2 轮）：~2500 tokens
本轮输入总计：~6850 tokens
输出（代码 + 解释）：~2000 tokens
本轮总计：~8850 tokens ≈ $0.13（Claude Sonnet）

这个数字看起来不大。但这是一轮。完成整个功能可能要 8-12 轮。再加上测试修复、前端实现——轻轻松松 10 万 token。

折算成钱：一个中等功能，用 Sonnet，大概 $1.5-$3。如果用了 Opus，翻 5-8 倍。

一月 20 个工作日，每天做 2-3 个这样的交互——保底 $60-$150。如果你还开了 /goal 没加 turn 上限让它跑了一夜——那就是另一回事了。

2 压缩上下文：不必要的东西别喂给它

📌 第一条铁律：别让它读不必要的文件

你可能会觉得"让 Claude Code 多读点背景信息，效果更好"。

不是。上下文越多 → 推理越慢 → 输出质量实际上可能下降 → 你的钱照样烧。

每次你让它读文件，先问自己：它对完成这个具体任务真的有用吗？

❌ "帮我修用户列表的样式，顺便把整个项目的组件结构分析一下。"——前半句就够了，后半句多读了 20 个文件。

✅ "帮我修 UserList.tsx 的样式，当前用的 Ant Design Table 组件，列定义在 UserColumns.tsx 里。"

📌 第二条：清空对话

长对话的 token 消耗是指数级的——因为每轮都要把之前所有轮次的对话重新发给模型。

如果你做了一个分析（比如"分析这个项目结构"），接下来要做开发（比如"改这个功能"），分析的内容对你的开发任务有用吗？大概率没有。但你如果不刷新对话，那段分析会一直在上下文里占着位置、烧着钱。

什么时候该刷新对话：

完成了一个独立任务，要开始新任务

对话超过 15 轮

发现它开始"忘记"你最早说的要求了

刷新之前把关键结论复制出来。比如它给你分析的项目结构、它列的待办清单——这些是"成果"，值得保留。

📌 第三条：用 .claudeignore

有些文件 Claude Code 永远不该读：

node_modules/
dist/
build/
*.min.js
*.lock
package-lock.json
coverage/
.git/
*.png *.jpg *.svg *.woff2

这些文件要么太大（node_modules 动不动几万行），要么对理解代码无意义（build 产物、图片），要么只是元数据（lockfile）。把筛子装上去，Claude Code 的"视野"就更专注——也更省钱。

3 选对模型：不是所有任务都要 Claude

Claude Code 支持多个模型。默认是 Sonnet——性价比最高的。但你可以在 /config 里切换。

📌 各模型的适用场景

Haiku：最便宜 — 简单格式转换、变量改名、commit message 生成、代码注释。不擅长复杂逻辑推理、多文件联动。

Sonnet：中等（默认） — 日常开发的主力模型。写功能、改 Bug、Review。不擅长超大上下文推理。

Opus：最贵 — 超大项目架构推理、复杂重构、需要深度理解的任务。不要天天日常使用。

📌 实战省钱技巧

不要每一个对话都用 Sonnet。

"把这个接口的 3 个字段从 camelCase 改成 snake_case。全项目搜索引用，所有调用点一起改。"

这是纯体力活。Haiku 就够了。一行命令的事，用 Sonnet 多花 3 倍钱。

"分析一下这个支付模块的设计是否合理。它目前有 15 个文件，涉及退款、回调、重复支付检测。列出架构上的问题和改进建议。"

这是需要深度理解的推理任务。用 Sonnet 或 Opus——省了这个钱，结果质量会打折。

在指令里加上 --model haiku 就行：

# 简单任务用便宜的
claude --model haiku "把所有 console.log 注释放到 src/utils/logger.ts 里统一管理"

# 复杂任务用默认的
claude "重构 src/services/order.ts 的退款逻辑，简化状态机"

4 长对话的续接：断了不丢上下文

你正在做一个重构，对话已经进行了 10 轮。上下文里积累了大量的分析——项目结构、问题定位、改了什么。但 token 快用完了，再对话下去效果会变差。

直接刷新对话 → 前功尽弃，Claude Code 不记得你前面做了什么。

📌 方案：手动续接

在第 10 轮左右，让 Claude Code 做一次"状态转储"：

"把到目前为止的分析结果、改动的文件清单、下一步要做什么——整理成一段上下文摘要。我下一个对话会从这段摘要开始。"

它会给你类似：

已分析
- 支付模块架构：路由 → 服务层 → 数据库三层
- 主要问题：退款逻辑散落在 4 个文件里，状态机不清晰

已改动
- src/services/order.ts — 简化了 createOrder 函数
- src/api/orders.ts — 添加了参数校验中间件

待完成
- 统一退款逻辑到 refund.service.ts
- 补充退款的状态机图
- 跑全量测试

新建一个对话，把这段摘要粘进去作为开头，然后继续：

"以下是上一个对话的上下文摘要：[粘进去]。继续做第三点：统一退款逻辑到 refund.service.ts。先分析目前退款逻辑在哪些文件里，然后合并。"

上下文续接了，但历史包袱甩掉了。token 账户从零开始，效率拉满。

Claude Code 也有内置的 /compact 命令，会把对话历史压缩成摘要。但手动转储的好处是你能控制保留什么——关键细节不会丢。

5 大项目的"按需加载"策略

Claude Code 不是代码搜索引擎。它是一个需要有限、高质量上下文才能发挥最好的推理引擎。

📌 第一步：建立索引

先做一次全局扫描，生成一个"项目地图"。这个过程只做一次，不要每次请求都重复。

"扫描 src/ 下所有文件，生成一份索引清单。格式：文件路径 + 一句话职责说明。不要读文件内容，只根据命名、导入导出和注释快速判断。输出为 markdown 列表。"

📌 第二步：按需深入

知道"地图"长什么样之后，每次只让它读跟当前任务相关的文件。

"根据你之前生成的索引，订单退款功能涉及 src/services/order.ts, src/services/refund.ts, src/routes/orders.ts。只读这三个文件，分析退款逻辑。"

关键："只读这三个文件"——不写这一句，它可能把相关目录全扫一遍。省了 80% 的上下文。

📌 第三步：复用分析结果

分析完项目结构之后，把结果存下来。下次同类任务直接引用，不用重新分析。

"根据 CLAUDE_ARCHITECTURE.md 里的架构说明（你已经分析过了），在 src/services/ 下新增一个导出服务。"

这三步走完，一个 15 万行的项目，每次交互只加载几百行的相关代码。Token 消耗从"读整个项目"降到"读当前模块"。

6 成本对照表：同样任务，优化前后差多少

以一个月 20 个工作日、每天 3 个中等复杂度开发任务为基准：

简单任务用 Haiku（占比 ~30%）：省 ~$15

不读不必要的文件（每次少 2000 token）：$90 → $72，省 ~$18

及时刷新/续接对话：$90 → $68，省 ~$22

.claudeignore 排除 node_modules 等：省 ~$5

大项目按需加载（10 万行级项目）：$150 → $65，省 ~$85

综合优化（大项目）：$150 → $45，省 $105
综合优化（小中型项目）：$87 → $28，省 $59

📌 三个不值得省的 token

说完了怎么省钱，也要说说哪些钱不该省：

① CLAUDE.md 的内容不要缩水
这是你的"项目知识库"，省这几百 token 会让每一轮交互的质量下降。

② 关键约束条件不要省略
"不改 test 文件"、"不引入新依赖"这种约束省了，后面返工的代价远大于这几个 token。

③ 安全相关的审查不要省
AI Review 找出的安全漏洞，值回几万倍的 API 费用。

写在最后

写这篇文章的时候我算了一下：按照优化后的策略，加上日常的 token 管理习惯，Claude Code 的月度 API 成本大概是一顿火锅的钱。

但优化 token 的真正意义不只是省钱。是context window 更干净 → 输出质量更高 → 返工更少 → 工作更快 → 你更少被卡住。

Token 管理和代码质量，在这个工具的逻辑里，是同一条线上的事。
