# 它一言不合就删文件？你需要给 Claude Code 戴个「安全带」

> 把终端、文件系统和 Git 交给 AI 操作，怎么不搞出生产事故？不是限制它的能力，而是知道什么能放、什么必须锁。

---

上篇说到了 CLAUDE.md——你给 AI 程序员的入职文档。有了它，Claude Code 写代码不再靠猜。

但你可能还有一个更大的顾虑没说出来：**"它改文件我忍了，但它能跑命令。万一它执行了不该执行的东西怎么办？"**

这个担心太正常了。我第一次让它操作文件系统的时候，全程盯着终端屏，手指悬在 Ctrl+C 上。它每输出一行，我就在想"这行会不会删我东西"。

用了这么久之后，我的结论是：**Claude Code 不会偷偷搞事情，但它会在你不注意的时候，按照你的话做一件你没想到后果的事。**

区别在于——它不是恶意的，它是**听话到有点蠢**。你说"把没用的文件删了"，它可能把配置文件也删了，因为在它的理解里那个文件确实没被引用。

所以安全不是你限制它不让它干活，而是**你给它戴上安全带**——它能干，但有些地方不能碰，有些操作要你确认。

## 一、三层权限：它能碰什么、不能碰什么

Claude Code 对项目文件的操作分三个级别。理解这个分层，你就知道什么操作该放心、什么操作该盯着。

### 读文件

**级别：低风险。默认允许。**

Claude Code 读你项目里的文件，理解代码结构。这个操作只读不改，不会造成破坏。它读什么文件取决于你跟它说什么——你说"分析项目结构"，它会翻目录和入口文件；你说"改 login.py"，它就重点看 login.py 及其依赖。

读文件阶段你可以完全放心。它看得越多，理解越准，后面的操作质量越高。

### 写文件

**级别：中风险。有确认机制。**

Claude Code 会创建新文件、修改已有文件。但它不会偷偷改——每次写操作之前会告诉你："我将修改以下文件：xxx"，等你确认。

你随时可以拒绝。也可以用 Git 追踪每一步变化：`git diff` 看看它改了啥，不对劲就 `git checkout` 回退。

**最重要的习惯：** 让它干活之前先 commit 一次。这样不管它怎么改，你都能精确回到"让它动手之前"的状态。这是最简单的安全网，5 秒钟就能做好。

### 执行命令

**级别：高风险。需要你确认。**

Claude Code 可以跑 shell 命令——装依赖、跑测试、操作 Git。这是它最像"同事"的地方，也是最需要盯的地方。

它执行每一条命令之前都会告诉你"我要执行：xxx"，等你许可。**但是它不知道你这台机器的真实环境是什么样的。** 你的 PATH 配置、权限设置、已安装的工具——它一概不知。所以你需要判断：

- 这条命令在你的环境里会不会有副作用？
- 这条命令的实质是什么？比如"清理没用的文件"——clean 命令具体会删什么？
- 这条命令是否需要 sudo？如果它要求 sudo，停一下，想清楚再确认。

**遇到 sudo 一定要自己过脑子。** Claude Code 不会恶意用 sudo 搞破坏，但它可能在执行"安装依赖"的时候需要 sudo 权限，而你安装的包恰好跟系统其他版本冲突——这个问题它判断不了，但后果你承担。

## 二、白名单目录和敏感文件排除

你可以告诉 Claude Code：**这里随便碰，那里千万别动。**

### .claudeignore：告诉它哪些文件别看

`.claudeignore` 文件放在项目根目录，语法跟 `.gitignore` 一模一样。Claude Code 在分析项目结构和读取代码时会自动跳过这些文件。

```gitignore
# .claudeignore 示例
node_modules/
dist/
build/
*.log
.env
secrets/
credentials/
```

这些文件有两个好处：**一是安全**——敏感文件直接屏蔽，物理隔绝。**二是性能**——Claude Code 不用在这些文件上浪费 Token，聚焦在真正的代码上。

### 项目结构隔离

这个更简单：你让 Claude Code 在哪个目录干活，它就只管那个目录。不会越界。

所以如果你的项目里有"绝对不能碰"的文件，比如生产环境的数据库配置、支付密钥：

- 要么加到 `.claudeignore`
- 要么放在项目之外，用环境变量引用

**Claude Code 不会主动越过你的项目边界。** 它理解自己的操作范围就是项目根目录之内。但这个边界你得设清楚——别把敏感文件放在项目目录里，然后又指望 AI 自己知道"这个不能看"。

## 三、Claude Code 会收集什么数据

聊安全问题，隐私和数据收集绕不开。以下是基于 Anthropic 官方文档的事实：

### 它会收集什么

| 数据类型 | 具体内容 | 用途 |
|----------|----------|------|
| 使用数据 | 功能使用频率、对话次数、命令调用统计 | 产品改进 |
| 对话数据 | 你跟 Claude Code 说的内容、它的回复 | 服务提供 |
| /bug 反馈 | 你主动提交的 bug 报告 | 问题修复 |

### 它不会做什么

- **反馈数据不用于模型训练。** Anthropic 明确承诺：通过 `/bug` 提交的反馈和对话数据，不会用来训练他们的模型。
- **会话数据有有限保留期。** 不是为了训练而永久存储。
- **API 调用的数据有独立的隐私政策。** 如果是通过 API Key 使用，数据使用条款跟 Web 端不同。

### 企业场景特别要注意

如果你的项目涉及商业机密、客户数据、未开源的内部系统，建议：

- 使用 API Key 方式，而不是绑定个人 Anthropic 账户
- 确认你所在组织对 AI 工具的数据政策
- 敏感项目做隔离——别把生产环境和 AI 实验环境混在一起

## 四、企业场景的安全实践

如果你在团队里用 Claude Code，安全要上几个台阶。以下是经验总结。

### 1. 隔离敏感项目

不要在你的生产服务器上跑 Claude Code。用一台开发机或容器，代码从 Git 拉下来，改完、验证完、再推到 Git。AI 碰不到生产环境，没有"误操作删库"的可能性。

开发机上的代码丢了也就当天的工作量。生产环境代码丢了——这事最好别发生。

### 2. 定期审计 AI 操作记录

Git 是最好的审计工具。Claude Code 改的每一行代码都记在 Git 历史里，谁谁谁（其实是 AI）什么时候改了哪个文件，一清二楚。

养成习惯：每次 Claude Code 干完活，用 `git log --stat -1` 看一眼它改了什么。不是不信它，是保持对代码变化的感知。

### 3. 团队共用时的权限策略

如果多人共用同一个 API Key：

- 设置 API 调用上限，防止单个成员用量失控
- 定期查看 API 账单，及时发现异常
- 考虑每人独立 API Key，分别追踪用量

### 4. 代码审查不跳过 AI 的改动

很多人对 AI 写的代码审核标准比人写的低——"AI 写的，应该没问题吧"。反了。

**AI 写的代码应该审核得更仔细。** 它不是你的同事，不懂你的业务上下文。它写的代码功能对、逻辑对，但不一定在边缘情况下对、在你特殊的数据结构下对。

永远不要让 AI 的代码绕过 Code Review 环节。

## 五、日常操作的 5 条安全准则

这些是我用了这么久 Claude Code 总结的铁律。不是建议，是"不做就会后悔"的那种。

**1. 让它干活之前，先 git commit。**

这是最简单也最有效的安全网。5 秒种，保你随便回退。每次让它写代码之前，确保工作区是干净的。

**2. 不要在不干净的目录里让它干活。**

Git 状态有未提交的修改？先 commit 或 stash。否则它改了东西混在你的改动里，你分不清哪行是谁写的。

**3. 涉及删除操作，自己先看一眼。**

"把没用的文件删了"、"清理临时文件"——这些命令 Claude Code 会执行，但它对"没用"的定义可能跟你不一样。删除操作，让它列出来哪些文件会被删，你看一眼，再点头。

**4. sudo 命令必须过你的脑子。**

没有任何例外。Claude Code 要跑 sudo，停下来：它要干什么？为什么需要管理员权限？有没有不用 sudo 的替代方案？

**5. 敏感信息不在代码里、不在项目目录里。**

API Key、数据库密码、支付密钥——要么放在环境变量，要么放在项目目录之外。不要让 Claude Code 有机会读到它们。

## 写在最后

说实话，用了这么久，Claude Code 从没搞出过让我想砸键盘的事。不是因为它在安全方面特别智能，而是因为**它的权限模型很保守**——每次写文件要确认、每次跑命令要确认、操作范围不出项目目录。

它最危险的时刻，不是它自己乱来，是**你麻痹大意**的时候。用得顺手了，确认弹窗一路按 Y，脑子里想着"它上回没出过问题，这回也不会"。

别这样。Claude Code 是你的工具，不是你的替身。最终每一行代码的责任都在你身上。

**给它戴好安全带。让它放开了干，但你的手永远在刹车上。**
