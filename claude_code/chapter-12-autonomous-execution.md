# Claude Code 最被低估的功能：睡前设个 goal，醒来 Bug 全修好

> 以前的 Claude Code 是"你说一句，它干一下"。现在有了 /goal 和 /loop，你只需要说"做成这样"，它自己会一轮一轮干到达标——你可以去睡觉、去开会、去写另一篇文章。

---

写这个系列的前几篇时，一个读者在后台留言："你讲的都很实用，但有一个问题——我在跟 Claude Code 协作的时候，必须一直盯着屏幕。它做完一轮，我看、确认、然后它继续。如果它能自己判断'做完了没有'，自己继续就好了。"

这个问题问到了 Claude Code 在 2026 年最重要的进化。

如果说 Claude Code 1.0 是"代理人"，你说一句它干一下——那 `/goal` 和 `/loop` 就是让这个代理人有了**自主判断力**。你不再需要做它的监工。

## 一、以前的问题：为什么你需要"盯着" Claude Code

回想一下你用 Claude Code 干活的典型场景：

> 你：帮我修一下这个接口的三个测试。
> Claude Code：改好了，跑一下。
> [测试结果：1 个通过，2 个报错]
> Claude Code：看到一个报错，是参数类型不匹配，要修吗？（permission required）
> 你：修。
> Claude Code：改了，再跑。
> [测试结果：还是有一个报错]
> Claude Code：这次是 mock 数据问题……（permission required）
> 你：修。
> ……反复四五轮之后终于全绿了。

从头到尾，你干了什么？**你只是坐在那重复说"修"**。真正干活的是 Claude Code，但它每干一轮就要停一下等你确认。

这个体验，说实话跟"自动"差了十万八千里。

## 二、/goal：把"做到什么程度才算完"交给 AI

### 它解决什么问题

`/goal` 让你**一次性设定目标**，Claude Code 自己多轮执行，直到目标达成或达到轮次上限。

你不用守在屏幕前了。

### 它怎么做到的：双模型架构

`/goal` 的底层设计很有意思——它用了**两个模型**：

1. **主模型（Claude）**：干活的那个。读文件、写代码、跑测试——跟普通对话一样。
2. **评估模型（轻量 Haiku）**：不做任何操作，只看对话历史里的证据，判断"目标达成了没"。它不能读文件、不能跑命令——它就是一个纯裁判。

这个设计很聪明——评估逻辑和执行逻辑完全分离。裁判不下场踢球，踢球的不能自己给自己打分。

执行流程清晰得很：

```
[目标设定] → 主模型执行一轮 → 评估模型检查
    ↓                              ↓
  未达标 → 继续下一轮         已达标 → 通知你
```

### 基础语法

```bash
/goal <条件描述> [or stop after <N> turns]
```

条件的核心要求：**可测量、可验证**。评估模型依赖对话里的输出来判断，所以你的条件必须能通过终端输出或文件内容来验证。

### 实战一：修到测试全绿

最经典的用法——改了一大堆代码之后，测试挂了七八个：

```bash
/goal 运行 npm test，所有测试必须通过，0 failures。可以修改任何 src/ 下的文件，不要动 test/ 目录里的测试用例。stop after 20 turns。
```

然后你就可以去接杯咖啡了。回来的时候要么全绿了，要么它告诉你"跑了 20 轮还没修完，这是我的分析……"

这里的条件设计包含了三个要素：

| 要素 | 内容 | 为什么重要 |
|------|------|-----------|
| 可测量终态 | 所有测试通过，0 failures | 评估模型只看得到这个 |
| 约束范围 | 只能改 src/，不动 test/ | 防止它"改测试凑通过" |
| 轮次上限 | 20 turns | 防止无限烧 token |

### 实战二：把一个 API 从 REST 迁移到 GraphQL

```bash
/goal 把 src/api/users/ 下的 REST 端点迁移到 GraphQL schema。所有现有调用点编译通过且单元测试全部通过。TypeScript 零报错。stop after 30 turns。
```

这种迁移任务的特点是：改一个文件会牵扯到好几个调用方。手动来，改一个，报错了去找，再改，再报——极其磨人。`/goal` 让它自己去串这个改-测-修-再测的循环，你只需要验收最终结果。

### 实战三：前端性能调优

```bash
/goal 优化首页的 Lighthouse Performance 分数到 90 以上。可以调整图片加载策略、代码分割、bundle 大小。不要删除任何用户可见的功能。每次修改后运行 npm run lighthouse。stop after 15 turns。
```

这个任务如果不交给 `/goal`，你的体验会是：改一下 → 跑 lighthouse → 看分数 → 改的不够 → 再来。五六轮之后你就不想动了。`/goal` 没有"不想动了"这个心态。

### 一个血的教训：必须加 turn 上限

社区有真实案例：一个开发者睡前设了个 `/goal` 做大型代码迁移，忘了加 `stop after`。第二天醒来，14 小时过去了，$200 的周额度烧完了，任务还没完成。

**写条件时永远加一句 `stop after <N> turns`。** 这是你给自己上的保险。

## 三、/loop：把"多久检查一次"交给时钟

### /goal 做不到的事

`/goal` 擅长的是"有明确终点"的任务。但有一类任务根本没有终点——"每隔一段时间检查一下"。

比如：
- 提了个 PR，等着 reviewer 给评论
- 部署了一个服务，等着它起来
- CI 在跑，等着它绿
- 监控日志，等着新错误出现

这些场景的共同点：**你不需要"做到什么状态"，你需要"定期看一眼，有变化就处理"**。

这就是 `/loop` 的领地。

### 基础语法

```bash
/loop [间隔时间] <任务描述>
```

- 间隔可以是 `5m`、`30m`、`2h` 等
- 不写间隔，Claude 会自适应选择 1 分钟到 1 小时之间的间隔

### 实战一：PR 守护者

你提了 PR 之后经常发生什么？reviewer 两天后才看，给了 5 条评论。你花半小时改完，push。然后 reviewer 又要两天。一个 PR 拖一周。

`/loop` 是专门对付这种节奏的：

```bash
/loop 15m 检查 PR #512 有没有新的 review 评论或 CI 失败。如果有新评论，按建议修改代码并 push。如果 CI 失败，诊断原因并修复。如果有冲突，尝试解决并 push。
```

设好之后，你去做别的事。每 15 分钟，Claude Code 自动看一眼——有评论就修，有 CI 挂了就改，有冲突就解。你在 PR 里的响应时间从"两天"变成了"15 分钟"。

reviewer 会被你的响应速度吓到——他们不知道你的 AI 在替你值班。

### 实战二：部署后监控

```bash
/loop 2m 用 curl 检查 https://staging.example.com/health。如果返回非 200，分析最近的代码改动，尝试 revert 可疑的改动。如果 5 分钟还修不好，发一句话到 Slack #oncall。
```

### 自适应间隔：你不知道它多久需要检查一次

有一种常见场景：你在等一个构建完成，但你不知道要等 3 分钟还是 30 分钟。固定间隔要么太频繁（浪费），要么太慢（错过）。

不写间隔，让 Claude Code 自己判断：

```bash
/loop 检查 deploy staging 的构建状态。构建完成后跑一遍 E2E 测试。如果测试全绿，在 Slack #deploy 发一条通知。
```

Claude Code 会把间隔从 1 分钟逐步拉长（忙的时候高频率，闲的时候低频率）。构建完成、E2E 通过、通知发了——自动停止。

### /loop 的限制

- **绑定本地会话**。你关了 Claude Code，/loop 就停了。如果需要跨会话的任务，要用 `/schedule`。
- **最多 50 个活跃定时任务**。
- **重复任务 7 天后自动过期**。不是"设了就一辈子"。

## 四、/schedule：关了电脑也照样干活

`/loop` 和 `/goal` 共有一个硬伤：**依赖当前会话**。你关了 Claude Code，它们全停。

`/schedule` 解决了这个问题：它是**云端常驻的定时任务**，跟你的终端会话完全独立。

### 适合 /schedule 的几件事

```bash
# 每天凌晨 2 点跑全量测试，结果发 Slack
/schedule daily 2:00 运行 npm run test:full，如果有失败，发结果到 Slack #nightly-test

# 每周日扫描死代码
/schedule weekly sunday 9:00 扫描项目中未被引用的代码，生成清理建议清单

# 每天早上准备 standup 摘要
/schedule daily 8:00 拉取最近 24 小时的 commits、新开的 issues、失败的 CI，生成一段三句话摘要，发到 Slack #standup
```

这些任务的共性：**你不应该需要记得去做它们**。它们是基础设施层面的自动化。`/schedule` 把 Claude Code 从"你在的时候它才干活"变成了"它自己按时间表干活"。

### /schedule vs /loop 的选择

| 场景 | 用哪个 |
|------|--------|
| 你在电脑前，等着 PR review | /loop |
| 你关电脑睡觉了，凌晨要跑测试 | /schedule |
| 一个小时内的事情 | /loop |
| 每天/每周的例行公事 | /schedule |

## 五、/workflows：多路同时开工，结果自动汇总

`/goal` 和 `/loop` 解决的是"多轮"的问题——同一个 Agent 反复干活。但还有一类需求是"多头"——把一个任务拆成多个子任务，同时让多个 Agent 并行处理。

这就是 `/workflows`。它是 2026 年 6 月才推出的新功能。

### 它能做什么

一个典型场景：代码库健康检查。你可以让 Claude Code 同时检查 5 个方面：

- Agent 1：扫描未使用的依赖
- Agent 2：检查安全问题（密钥泄露、SQL 注入风险）
- Agent 3：分析测试覆盖率最低的模块
- Agent 4：检查 TypeScript 严格模式违规
- Agent 5：分析性能热点（大文件、深嵌套）

5 个 Agent 同时开工，各扫一摊，最后汇总成一份报告。如果串行跑，5 个任务可能要 15 分钟。并行跑，3 分钟出结果。

### 怎么触发

在 prompt 里自然描述即可，Claude Code 会自动识别并拆分：

```bash
> 对 src/ 做一次全面的代码健康检查：1. 找未使用的依赖 2. 安全漏洞检查 3. 测试覆盖率低的模块 4. 代码重复检测 5. 复杂度过高的函数。把这些并行检查，最后汇总成一份健康报告。
```

Claude Code 会自动把这 5 个检查项分给 5 个并行 Agent，各自搜索、分析，最后汇总。

### 技术规格与限制

| 项目 | 限制 |
|------|------|
| 单次最大并发 Agent 数 | 16 |
| 单次 run 总 Agent 上限 | 1000 |
| 需要版本 | Claude Code ≥ v2.1.154 |
| Pro 用户 | 需在 /config 中手动开启 Dynamic workflows |
| 子 Agent 权限 | 文件修改自动放行，但 shell 命令仍需 allowlist |

### 适合 /workflows 的场景

- 全仓库代码扫描（安全 + 质量 + 性能）
- 多个数据源的调研（比如对比 3 个 npm 包的优劣）
- 大规模重构前的影响分析（"这个接口被多少地方调用了"交给一个 Agent，"数据库 schema 变更影响"交给另一个）
- 生成项目文档时多个章节并行撰写

### 不适合 /workflows 的场景

- 单文件的小改动——杀鸡用牛刀
- 有严格先后顺序的任务——并行不能保证执行顺序
- 简单的"帮我写个函数"——普通对话就够了

## 六、选型决策：这张表就够了

| 你的需求 | 用什么 | 一句话原因 |
|---------|--------|-----------|
| "做到测试全绿为止" | `/goal` | 有明确终态，需要评估模型判停 |
| "每隔 15 分钟检查一下 PR" | `/loop` | 时间驱动，没有终态，周期检查 |
| "每晚凌晨跑全量测试" | `/schedule` | 跨会话，你不开电脑也要跑 |
| "同时检查代码的安全/性能/质量" | `/workflows` | 多 Agent 并行，各管一摊 |
| "睡前让它把代码迁移完 + 测试通过" | `/goal` | 条件驱动，醒了验收 |
| "不知道构建要多久，好了通知我" | `/loop`(自适应) | 不写间隔，它自己判断 |
| "先定位问题再修复" | `/goal` | 两个阶段：定位 + 修复，全部达标才停 |
| "普通的帮我改个函数" | 正常对话 | 不需要循环 |

### 组合拳：1+1 > 2

最强大的用法不是单用一个，是把它们串起来：

```bash
# 在 /loop 里嵌套 /goal
/loop 30m /goal 检查 PR #{current} 的新评论，按建议修改代码直到 reviewer 满意，stop after 10 turns
```

每一轮 /loop 触发时，内部的 /goal 会自己干到"reviewer 满意"为止。外层周期检查，内层盯着一个目标干到底。

## 写在最后

这篇文章写完后，我自己回头看了一遍——说实话，Claude Code 这些新功能最让我感慨的不是技术有多强，而是**它改变了"用 AI 写代码"的体验边界**。

以前的体验是"对话"——你说，它干，你看，你说，它再干。本质上是一种"对话式编程"。

有了 `/goal` 和 `/loop` 之后，体验变成了"委托"——你说一句目标，可以转身走人。回来的时候要么做好了，要么它告诉你卡在哪了。

这不是效率的线性提升。这是**你从"操作员"变成了"导演"**。

但有两件事始终不变：
1. **你的判断力不可替代。** /goal 能修测试，但它不知道"这个测试本身写错了应该改测试"。那个判断只能你来。
2. **记得加 turn 上限。** 信任 AI，但别把钱包的命交出去。
