Claude Code 自主执行模式实测

/goal 和 /loop 是 Claude Code 最被低估的功能。你定目标、设约束，它自己循环执行"改 → 测 → 修"，直到全绿。很多人不敢用——怕它跑飞、怕烧钱。这篇实测告诉你什么时候该开、什么时候千万别碰。

📝 写在前面：你让 Claude Code 修一个 Bug。它改了 3 行代码。你点运行——测试挂了。你告诉它："测试挂了，修一下。"它改了 5 行代码。你又点运行——另一个测试挂了。你告诉它："还是挂了，再修。"它又改了 3 行……

这个循环重复了 5 次，花了你 10 分钟——你像个 relay runner，来回跑。而 Claude Code 明明可以自己跑完全程。/goal 和 /loop 就是干这个的。

但很多人不敢用。怕它跑飞了、怕烧钱、怕改了不该改的。这篇把自主执行讲透：什么时候开，什么时候千万别碰，以及怎么设护栏保证安全。

1 /goal 到底是什么

/goal 是 Claude Code 的一个命令。它可以开启一个"目标模式"，让 AI 自己循环执行，直到目标达成或者达到回合限制。

核心公式：

目标（goal） + 迭代（loop） + 约束

📌 用一个实例理解 /goal

/goal "写 8 个测试用例，覆盖订单退款的所有场景，跑完之后确保全绿"

调用后发生了什么：

第 1 轮：读 src/services/order.ts → 设计 8 个测试场景 → 生成测试代码 → 运行测试 → 12 个测试通过，3 个失败

第 2 轮：分析失败原因 → 发现 mock 没覆盖回调函数 → 补 mock → 再跑 → 15 个全绿

第 3 轮：全项目搜退款相关逻辑 → 发现 user/refunds 页面也有退款逻辑 → 补齐缺失的测试 → 跑 → 全绿

第 4 轮：无新发现 → 输出报告 → 目标达成，退出。

✅ 全程不需要你插手。你只需在最后看一眼报告，确认改动没超出边界。

2 /loop 的"试错 → 修 → 再试"机制

如果 /goal 是"给你一个目标，你去实现"，/loop 就是"做完测试 → 看哪些挂了 → 修 → 再跑 → 全绿才停"。

📌 /loop 的执行过程

相当于自带了一个 TDD 闭环：

写代码 → 跑测试 → 全部通过了吗？ → 没有 → 分析失败原因 → 修代码 → 再跑测试 → 直到全绿 → 退出

这个过程可以用一个命令触发：

/loop "跑 npm test，任何失败的测试都要修到通过。最多 10 轮。不建新文件，不删已有的测试。"

跟你手动 relay 的区别是：你不需要做中间那个"看日志→告诉它问题→等结果→再看日志"的循环。AI 自己做完了整个过程。

📌 /goal vs /loop 的区别

/goal：有创意性任务。比如"给我实现一个用户导出功能，跑完测试全绿"——因为实现路径不固定，它需要自己决策。

/loop：更适合"修到全绿"这种机械流程——目标明确（测试全过），唯一不确定的是要修几轮。

3 安全护栏：不让它跑飞

给 /goal 一个白名单，和 5 公里半径的天空——然后放手。

📌 护栏一：设定回合数上限

永远不要不加 turn 上限。

/goal "修好这 5 个失败的测试" --max-turns 10

5 个失败→设 10 轮上限。如果 10 轮都没修好，说明问题比你预想的复杂——该你介入看了。

经验值：N 个测试失败→设 N*2 轮上限。中等功能实现→设 15-20 轮上限。

📌 护栏二：限定操作范围

❌ "/goal '改完这个模块'"——无范围约束，太危险

✅ "/goal '给 src/services/order.ts 和 src/api/orders.ts 加测试，只动这两个文件和 test/ 目录。不改任何已有逻辑。最多 12 轮。'"

好指令的三个特征：角色限定、范围限定、行为限定。把它像 GPS 地图一样标清楚边界——里面随便跑，出了边界就停。

📌 护栏三：加验证步骤

每轮跑完之后再加一个显式验证：

/goal "修所有测试到全绿。每轮之后输出'当前通过/失败数'。如果 5 轮后仍有两项以上失败，中止并输出失败原因汇总。"

输出格式要求让你能在日志里快速浏览每一轮的状态，不需要逐行看。

4 适用场景：什么时候值得开

✅ 推荐用 /goal 或 /loop 的场景

🙆 修测试"修到全绿" — 目标非常明确，有一个二值化的判定（全过 or 不）。AI 不需要做创意决策，只是"找到了→修→再试→直到"。

🙆 代码修复后，补相关测试 — "给刚才改的 3 个函数加测试，保证全过，顺便测一下边界值"

🙆 写完功能后做完整性检查 — "检查以下 checklist：变量命名一致性、注释完整性、无 console.log。发现问题就自动修复。最多 5 轮。"

🙆 代码迁移/格式转换 — "把 src/utils/ 下 8 个文件的 CommonJS require 都改成 ES module import，确保能跑"

❌ 不要用 /goal 或 /loop 的场景

🙅 架构决策 — "从 Redux 迁到 Zustand"——这是需要你每步确认的事，不要让它自己跑

🙅 大范围修改 — "重写整个支付模块"——范围太大，一次出错可能导致连锁反应

🙅 无测试的项目 — 没测试就没有判定标准。AI 不知道什么是"做好"——最后就是你第二天醒来，面对一个被改得面目全非的代码库

🙅 涉及数据库迁移 — "把所有表里的字段名改了"——AI 不会考虑数据的完整性。迁移让人类审

5 翻车现场：一次跑飞的值几美元

📌 事故回放

我有一次给了这个指令：

❌ /goal "补齐 src/ 下面所有缺少的测试。"

没加 turn 上限。没限定范围。没说"不改逻辑"。

AI 的行为：读 63 个文件——发现 37 个没有测试——给 37 个文件都写了测试——其中 12 个测试挂了——它去修失败的测试——改到第 6 个测试时，它改了源码里的一个函数签名——然后所有调用这个函数的地方都报错了——它又去修那些报错的地方——循环往复。

整个过程花了 34 轮，烧了不到 $4。

但问题不是钱。问题是它改了一些不该改的地方——它把 src/utils/logger.ts 里的 logger 函数签名改了，导致所有 import 了这个函数的地方全在报错。如果我不仔细审查日志，这个改动被提交上去，会在 CI 里炸掉。

📌 教训

这 $4 的教训值 $400。从那以后我用 /goal 的三条铁律：

1. card: never 不加 turn 上限 — 除非你的任务是"审计"这个开源项目的架构（纯读不写），否则必须有上限

2. card: always 限定"只读 + 只写"的文件清单 — "/goal 加测试，只动 src/servives/order.ts 和 test/orders.test.ts"

3. card: always 加"不改已有逻辑"的约束 — 这条规则可以防止上述的"为了修测试改了源码"的问题

💡 核心心法：/goal 和 /loop 是"确定性好"的任务才用。确定性 = 有测试判定成功/失败 + 有明确的文件范围 + 不需要创意决策。

━━━━━━━━━━━━━━

写在最后

Claude Code 最好玩的地方是 /goal 模式——它会把"你可能要改两三天"的活变成"设置好参数然后去喝杯咖啡再回来看结果"的事情。

但不是所有任务都适合。回到这篇文章的核心：确定性是好自主执行的前提。没测试的项目里不要开 /goal。没限定文件范围不要开 /goal。在不确定 AI 会改哪的时候不要开 /goal。

护栏设好了，那就是你睡觉的时候 AI 在干活。
