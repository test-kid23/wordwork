🧠 Claude Code 实战

10 万行代码也不虚！
大项目里用 Claude Code 的精准导航策略

大项目里 Claude Code 最怕的不是代码多——是"找不到路"。读太多→ token 爆炸→迷糊。读太少→缺上下文→瞎改。这篇给出一套确定性的导航策略，让它在大项目里也精准如 GPS。

📝 写在前面：15 篇文章快写完了，这篇把"大项目"这个问题单独拎出来讲。因为这才是 Claude Code 的真实战场。小项目里 AI 怎么写都对。大项目里，AI 写的代码要跟 10 万行已有的逻辑共存——这需要一套完全不同的策略。

这篇不讲"怎么 prompt Claude Code"，讲的是：当项目大到 Claude Code 一次读不完的时候，你该给什么、不给什么，以及怎么让它"像人手导航一样找到正确位置后再操作"。

1 大项目的核心问题不是"代码多"

是 上下文和精度之间的矛盾。

给太多上下文 → token 爆了 → Claude Code 开始"忘掉"最初的约束 → 质量下降。

给太少上下文 → 它只看到一个文件 → 不知道改了这行会影响什么 → 改完崩了。

这不只是钱的问题——这是 Claude Code 在大项目里"不可用"的根本原因。

📌 一个真实的翻车案例

10 万行的电商项目。我让 Claude Code：

"在我们的结账流程里加一个收货地址验证。读所有相关文件。"

它读了 38 个文件——包括支付、购物车、用户信息、地址管理、订单历史。
总上下文：约 7.2 万 token。
结果：生成的代码把验证逻辑写在了支付模块里——但正确的做法是写在地址管理模块里。
为什么？信息太多，它失去了对"哪一层负责什么"的判断力。

💡 核心心法：大项目里的 Claude Code 不能用传统方式工作。你不能再"给一段需求、让它自己找代码"。你要像在黑暗中用手电筒——只照亮需要看的东西。多余的光反而让你看不清。

2 索引先行：生成项目地图

不要一上来就让 Claude Code 读代码。先让它在"不读内容"的情况下生成一个层级地图。

📌 生成架构索引

"分析 src/ 下的目录结构。每个目录给一个一句话职责描述。不要读文件内容——只看目录命名、入口文件（index.ts, main.ts 等）的 import 结构、package.json 的 scripts。输出为两层目录树。"

这会产生类似：

src/
├── api/ ← HTTP 请求封装、拦截器、错误处理
├── components/ ← React 组件（表单、卡片、导航）
├── hooks/ ← 自定义 hooks（useAuth、useCart）
├── services/ ← 业务逻辑（支付、用户、订单）
├── store/ ← Redux store、reducers、actions
└── utils/ ← 工具函数（格式化、校验、常量）

把它存成 ARCHITECTURE_INDEX.md。

📌 生成依赖图（可选）

在第二步，如果有 madge 或其他依赖分析工具：

madge --image depgraph.png src/

这张图很有用——它告诉你哪些模块相互依赖，哪些是孤岛。

但关键是：索引生成只做一次。每次新对话不要重新生成。索引存到文件里，新对话从读 ARCHITECTURE_INDEX.md 开始。

3 按需深入：三层加载法

有了地图之后，采用三层加载策略：

📌 第 1 层：地图（索引）

让 Claude Code 加载 ARCHITECTURE_INDEX.md。它只需要知道："哪里有什么"。这几百个 token 告诉它整个项目的骨架。

📌 第 2 层：相关模块的文件结构

告诉它具体读哪个模块：

"我在 src/services/payment/ 里加一个退款功能。根据架构索引，这个目录下有 payment.ts、gateway.ts、webhook.ts。先扫描这些文件的函数签名和 export 清单。"

这类似"飞到街区上空，看一眼楼顶的样子"——还没进楼，但知道每栋楼叫什么、几层。

📌 第 3 层：目标文件的内容

最后再深入到具体文件的内容：

"读 src/services/payment/gateway.ts 的完整内容。这个文件包含三个支付渠道的接口定义。"

三层加载的优势：
第 1 层：500 tokens → 知道项目骨架
第 2 层：2000 tokens → 知道支付模块有哪些文件、什么结构
第 3 层：3000 tokens → 知道具体逻辑

总计 ~5500 tokens — 完成了"找到正确位置→理解结构→实施改动"的全流程

对比"读所有相关文件"：70000 tokens → 丢失关键信息 → 改错地方

4 用 CLAUDE.md 降低每次的加载成本

CLAUDE.md 是大项目导航的核心。它相当于一个永久加载的"导航指令"。

📌 CLAUDE.md 里应该有什么

# ARCHITECTURE
分层架构：API 层 → Services 层 → Data 层
每层之间通过 interface 通信，不跨层调用

# KEY RULES
- 前端状态全在 Zustand store 里，不用 Context
- API response 格式统一：{ data, error, meta }
- 禁止在组件里直接调 API——必须走 services 层

# FILE MAPPING
- src/api/ ← HTTP 请求封装
- src/services/ ← 所有业务逻辑（唯一改文件）
- src/components/ ← UI 组件（不允许有业务逻辑）
- src/store/ ← Zustand stores
- src/utils/ ← 纯函数工具

# COMMON PATTERNS
- 新增功能：先在 services 加函数 → 再暴露 API → 最后做 UI
- 错误处理：services 层统一截获，API 层只负责 transport
- 测试：.test.ts 放在同级目录下

CLAUDE.md 的内容控制在 500-800 token 内。它应该是"最浓缩的知识"——不是教程。

📌 关键：CLAUDE.md 要持续更新

每次重构、每次加新模块、每次改了架构约定——同步更新 CLAUDE.md。过期了三周没更新 = 误导 Claude Code = 帮你生成不符合新规范的代码。

5 金字塔式文件加载

有一个关键问题：

"Claude Code 自己会读文件。为什么需要我来规划它该读什么？"

因为 Claude Code 在读文件时是"看见什么读什么"——默认的搜索范围是全局。在大项目里，一个搜索可能返回 50 个文件，它全读了。

你的 CLAUDE.md + 架构索引 + 显式文件约束 = 给它的"地图+导航指令"。

📌 金字塔加载法

金字塔尖：CLAUDE.md（500 token，永久加载，每次对话都有）
  ↓
金字塔中：架构索引（800 token，读到"哪里有什么"）
  ↓
金字塔底：目标文件（3000 token，真正要改的代码）

📌 例子：在 10 万行项目中加一个"用户头像上传"功能

传统方式："在 src/ 下相关的文件里加一个用户头像上传功能"
→ 读 40 个文件 → 读了用户列表、评论、通知……→ token：65000 → 生成代码质量：中

金字塔方式："读 ARCHITECTURE_INDEX.md → 确认涉及 avatars 模块 → 只读 src/services/users/ 下 avatars 相关的文件 → 在 avatars 服务层加功能"
→ 读 5 个文件 → 精确定位 avatars → token：4800 → 生成代码质量：高

💡 核心心法：不是让 Claude Code"自己探索"——是你指定它"读什么"。每次对话给的上下文越小、越精确——AI 在目标代码上的推理就越深、越准。

6 实战案例：一个中等复杂度的功能

完整走一遍。需求：在 10 万行的电商项目里，加订单取消通知。

📌 第 1 步：确认入口（仅地图级）

"根据 ARCHITECTURE_INDEX.md，订单取消通知涉及哪些模块？"

Claude："orders（订单逻辑）、notifications（通知发送）、email（邮件模板）。orders 在 src/services/orders/，notifications 在 src/services/notifications/，email 在 src/utils/email/。"

📌 第 2 步：扫描相关模块（文件结构级）

"扫描 src/services/orders/ 和 src/services/notifications/ 的文件结构——只看函数签名和 export 清单。"

Claude 给出了 8 个文件的函数签名。它注意到 orders/cancel.ts 里有一个 cancelOrder() 函数——这是我们要加通知的地方。notifications/sender.ts 里有一个 sendNotification() ——这是用来发送通知的。

📌 第 3 步：深入目标文件

"读 orders/cancel.ts 和 notifications/sender.ts 的完整内容。在 cancelOrder() 函数执行后插入通知发送逻辑。"

Claude：读了 2 个文件（约 180 行）→ 理解了 cancelOrder 的返回值结构 → 理解了 sendNotification 需要的参数格式 → 写了 5 行映射代码 → 完成。

📌 数据总结

读文件数：3 个（架构索引 → 函数签名扫描 → 目标文件）
总 token：~4800
耗时：约 40 秒
质量：一条通知逻辑正确插入，无多余改动

对比全量扫描方式：读 30+ 文件、85000 token、花费 $1.20、生成的代码放错了文件。

写在最后

大项目里的 Claude Code 不是自动模式。它需要你在第一次把"地图"画好，之后变成自动驾驶。这个设置成本大概 15-20 分钟（生成架构索引 + 写 CLAUDE.md），但之后每次任务都能少走弯路。

如果要用一句话总结这 15 篇文章：Claude Code 不是一个人类程序员——它是一个有强大推理引擎但需要精准导航的工具。给它太多context = 迷失方向。不给够 context = 瞎指挥。精准给 = 它才会变成你最有效率的队友。

AI 时代，写代码的速度不再是最主要的速度瓶颈。最慢的环节是 "搞清楚该在哪写什么"。这篇文章的策略就是为此设计的。
