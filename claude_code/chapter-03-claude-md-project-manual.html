1 CLAUDE.md 是什么

文档里管它叫「项目级记忆文件」——说白了，放项目根目录，Claude Code 启动时自动加载。

说人话：

💡 一句话记住：它就是你给 AI 程序员写的入职文档。

跟新同事聊项目，你会告诉他：代码这么结构的、命名这么规范的、测试这么跑的。CLAUDE.md 就是把这些话写成文件，Claude Code 每次启动都会读一遍。

它长什么样？就是一个普通的 Markdown 文件，放在项目根目录：

your-project/
├── CLAUDE.md ← 这个
├── src/
├── tests/
└── ...

内容完全由你决定——你想让 AI 知道什么，就往里写什么。

2 没有它的时候，Claude Code 在猜什么

我用同一个真实需求做对比，看差距有多明显。

📝 需求："给用户模块加一个修改密码的接口"

🔹 没有 CLAUDE.md 时

它看你是 Python 项目，用了 Flask 风格——但你的项目是 FastAPI。
它看文件都在 src/ 下，就在 src/ 新建了——但你的 API 约定放 src/api/。
它写了 unittest.TestCase——但你的测试框架是 pytest + fixture。
它 import 了 from src.models.user——但你的路径是 from app.models.user。

代码能跑，功能对。但要并入主分支，需手动调整 4 处。

🔹 有 CLAUDE.md 时

它知道项目用 FastAPI，直接用 APIRouter，文件放 src/api/。
它知道代码风格要过 ruff format，格式跟你项目完全一致。
它知道测试框架是 pytest，自动创建 fixture，放 tests/api/ 下。
它知道 import 路径是 app.xxx，所有引用都对。
写完代码后，还自动跑了一遍 pytest。

零返工。

🎯 同一个需求。没有 CLAUDE.md 返工 4 处，有它零返工。
不是 AI 变聪明了，是你把规矩告诉它了。

3 一份好 CLAUDE.md 的骨架（附模板）

下面是一份可以直接复用的模板。前几项必须写，后面的按你项目情况来。

# 项目名称

## 项目简介
一句话说清楚这个项目是干什么的。比如：
"这是一个电商后台管理系统，负责商品管理、订单处理和用户管理。"

## 技术栈
- 后端：Python 3.11 + FastAPI
- 数据库：PostgreSQL + SQLAlchemy
- 测试：pytest + httpx
- 前端：React + TypeScript

## 项目结构
src/
├── api/ # API 路由层
├── models/ # 数据模型
├── services/ # 业务逻辑层
├── schemas/ # Pydantic 模型
└── utils/ # 工具函数

## 编码规范
- 使用 ruff 进行代码格式化和 lint
- 类型注解：所有函数必须注明参数类型和返回值
- 命名：文件名小写下划线，类名大驼峰
- import 路径：使用 app.xxx 格式

## 命令
- 启动：uvicorn app.main:app --reload
- 测试：pytest tests/ -v
- 检查：ruff check .

## 注意事项
- 敏感信息从环境变量读取
- 新增接口必须在 tests/api/ 下写测试
- commit 前必须 run ruff check 和 pytest

📌 模板里每一项，我多聊两句

项目简介，一句话就行。Claude Code 需要知道"这个项目是卖货的还是做社交的"，这决定了代码的整体倾向。我见过有人在这写了三段的项目背景介绍，其实没必要——AI 不需要知道你公司的创业故事。

技术栈要写到版本号。不同版本的 API 差异很大，比如 Python 3.10 的 Union 写法和 3.11 的 X | Y 完全不一样。你写 3.11，它就按 3.11 的语法来，不会给你产出过时的代码。我自己的项目里技术栈这一块是最常更新的，每次升级依赖都会改一下。

项目结构是这套模板里最值钱的部分。Claude Code 能自己翻目录，但它不知道你的命名约定——到底是 src/api/ 还是 src/routes/？utils/ 还是 helpers/？我踩过这个坑：项目里明明约定 API 文件放 src/api/，但 Claude Code 看别人用 src/routes/ 的多，就给我新建到 routes 里去了。写明白了就没这事。

编码规范告诉它 lint 工具和命名风格。这不仅省了你手动调格式的时间，更重要的是——代码 review 的时候 diff 只显示你真正改的逻辑，不是满屏的格式调整。

常用命令写上去，Claude Code 跑测试、装依赖的时候自动用，不用每次手敲一遍。

注意事项那部分，把项目"潜规则"写进去："数据库密码从环境变量读"、"commit 前跑测试"。这些是新同事最容易翻车的点，AI 也一样，不写它真不知道。

❌ 别往 CLAUDE.md 里塞什么

网上有些教程会让你把整个 API 文档、所有数据库表结构、完整的部署流程全塞进去。别学。

CLAUDE.md 是入职文档，不是 wiki。它每次启动都加载一遍——文件越大，加载越慢，上下文窗口也越挤。我有一次塞了将近 2000 行进去，结果 Claude Code 启动慢了好几秒，而且经常"忘掉"关键指令，因为被后面那些不重要的信息稀释了。

简单原则：如果一条信息只在你做特定任务时有用，它不该进 CLAUDE.md。 比如"部署到 K8s 的详细步骤"——你应该新建一个 DEPLOY.md，做部署任务时 @ 给它就行。

4 上下文管理的三个层次

有了 CLAUDE.md 之后，Claude Code 的知识来源有三个层次。分层搞对了，它找信息才精准：

第 1 层：会话内临时说明 → 当前对话 → 说完就忘 → 比如"这次重构别动 user 模块"

第 2 层：CLAUDE.md → 整个项目 → 永久 → 上面模板里的所有内容

第 3 层：工作区文件 → AI 实时读取 → 实时 → 你 @ 引用的文件、AI 自己翻到的代码

这三层搞混了，CLAUDE.md 就容易又长又杂。比如：

你要重构订单模块的代码，但特别嘱咐它"别碰 login.py，那个文件有坑"。

✅ 会话里说一句就行。"这次别动 login.py"——这就够了。
❌ 不用写到 CLAUDE.md 里。"别动 login.py" 是临时约束，不是项目级规则。
✅ CLAUDE.md 放的是通用的、持久的规则，比如"所有 API 路由放在 src/api/ 下"。

很多人 CLAUDE.md 写得又长又杂，是把会话级的约束也塞进去了。保持精简，只放长期有效的信息。

我自己的 CLAUDE.md 大概 50 行。写多了反而没人看——AI 也一样。

5 Hook 机制：让它自动做规矩

这是 CLAUDE.md 里一个被严重低估的功能。Hook 就是在特定事件发生时，Claude Code 自动执行你设定好的行为。

✅ 每次写完代码，自动跑 ruff 格式化一遍。

✅ 每次 commit 之前，自动跑一遍全部测试。

✅ 每次启动对话，自动检查当前分支是否是最新的。

这些行为你不用每次都手动提醒它。写在 CLAUDE.md 的 Hook 区域里，它自己到点就执行。说实话我第一次配 Hook 的时候还不太信——以前习惯了每次手动喊它"跑一下测试"，突然不用喊了反而有点不习惯。

📌 基础 Hook 写法

## Hooks

### 保存文件时
- 自动执行：ruff format {file_path}

### commit 之前
- 自动执行：pytest tests/ -v
- 自动执行：ruff check .

Hook 写好了之后，你不用再每次说"格式化一下代码"或"跑一下测试"。它到点自动干活，跟请了个真助理似的。

📌 一个很实用的进阶配置

## Hooks

### 启动对话时
- 自动执行：git status # 先告诉我当前分支状态

### 每次修改文件后
- 如果没有对应测试文件，提醒我是否要创建

### 准备 commit 时
- 自动跑一次项目全部测试
- 如果有失败，禁止 commit

💡 这个配置的效果：你再也不会说"糟了忘跑测试就 push 了"——AI 替你记住了。

至于要不要写、写多详细，随你。我自己的 CLAUDE.md 到现在也就 50 行，够用了。
