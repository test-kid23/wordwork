1 三层权限：它能碰什么、不能碰什么

Claude Code 对项目文件的操作分三个级别。理解这个分层，你就知道什么该放心、什么该盯着。

📖 第一层：读文件

低风险 · 默认允许

Claude Code 读你项目里的文件，理解代码结构。只读不改，不会造成破坏。读文件阶段你可以完全放心。它看得越多，理解越准，后面的操作质量越高。

✏️ 第二层：写文件

中风险 · 有确认机制

Claude Code 会创建新文件、修改已有文件。但它不会偷偷改——每次写操作之前会告诉你"我将修改以下文件"，等你确认。你随时可以拒绝。也可以用 git diff 看变化，不对劲就 git checkout 回退。

💡 最重要的习惯：让它干活之前先 git commit 一次。这样不管它怎么改，你都能精确回到"动手之前"的状态。5 秒种就能做好的安全网。

⚡ 第三层：执行命令

高风险 · 必须你确认

Claude Code 可以跑 shell 命令——装依赖、跑测试、操作 Git。它执行每一条命令之前都会告诉你"我要执行 xxx"，等你许可。但它不知道你这台机器的真实环境。你的判断才是最后一道防线。

⚠️ 遇到 sudo 一定要自己过脑子。
它可能在执行"安装依赖"时需要 sudo，而你装的包恰巧跟系统其他版本冲突——这个问题它判断不了，但后果你承担。

2 白名单目录和敏感文件排除

🎯 核心原则：让它知道——这里随便碰，那里千万别动。

📌 .claudeignore：告诉它哪些文件别看

.claudeignore 文件放在项目根目录，语法跟 .gitignore 一模一样。Claude Code 在分析项目结构和读取代码时会自动跳过这些文件。

# .claudeignore 示例
node_modules/
dist/
build/
*.log
.env
secrets/
credentials/

这有两个好处：

① 安全——敏感文件直接屏蔽，物理隔绝，AI 读都读不到。

② 性能——Claude Code 不用在这些文件上浪费 Token，聚焦在真正的代码上。

📌 项目结构隔离

这个更简单：你让 Claude Code 在哪个目录干活，它就只管那个目录。不会越界。

✅ 一句话记住：别把敏感文件放在项目目录里，然后又指望 AI 自己知道"这个不能看"。该放 .claudeignore 的放 .claudeignore，该移出项目目录的移出去。

3 Claude Code 会收集什么数据

聊安全问题，隐私和数据收集绕不开。以下是基于 Anthropic 官方文档的事实：

📌 它会收集什么

📊 使用数据 — 功能使用频率、对话次数、命令调用统计 → 用于产品改进

💬 对话数据 — 你跟 Claude Code 说的内容、它的回复 → 用于服务提供

🐛 /bug 反馈 — 你主动提交的 bug 报告 → 用于问题修复

📌 它不会做什么

✅ 反馈数据不用于模型训练——Anthropic 明确承诺：/bug 提交的反馈和对话数据不会用来训练模型
✅ 会话数据有有限保留期——不是为了训练而永久存储
✅ API 调用的数据有独立隐私政策——通过 API Key 使用，条款跟 Web 端不同

⚠️ 如果你的项目涉及商业机密或客户数据：
✅ 使用 API Key 方式，而非绑定个人 Anthropic 账户
✅ 确认组织对 AI 工具的数据政策
✅ 敏感项目做隔离——别把生产环境跟 AI 实验环境混在一起

4 企业场景的安全实践

如果你在团队里用 Claude Code，安全要多上几个台阶。

① 隔离敏感项目
不要在生产服务器上跑 Claude Code。用开发机或容器，代码从 Git 拉下来，改完、验证完、再推到 Git。AI 碰不到生产环境，就不存在"误操作删库"。

② 定期审计 AI 操作记录
Git 是最好的审计工具。Claude Code 改的每一行代码都记在 Git 历史里。养成习惯：每次它干完活，用 git log --stat -1 看一眼它改了什么。

③ 团队共用时的权限策略
如果多人共用同一个 API Key：设置调用上限防止用量失控、定期查看账单及时发现异常、考虑每人独立 Key 分别追踪。

④ 代码审查不跳过 AI 的改动
很多人对 AI 写的代码审核标准比人写的低——"AI 写的，应该没问题吧"。

💡 事实正相反——AI 写的代码应该审核得更仔细。它不是你的同事，不懂你的业务上下文。功能对、逻辑对，但不一定在边缘情况下对。永远不要让 AI 的代码绕过 Code Review。

5 日常操作的 5 条安全铁律

这些是我用了这么久总结的——不是建议，是"不做就会后悔"的那种。

🔒 铁律 1
让它干活之前，先 git commit。5 秒钟的安全网，保你随便回退。确保工作区是干净的。

🔒 铁律 2
不要在不干净的目录里让它干活。Git 有未提交的修改？先 commit 或 stash。否则它改了东西混在你的改动里，你分不清谁写的。

🔒 铁律 3
涉及删除操作，自己先看一眼。"清理没用的文件"——它对"没用"的定义可能跟你不一样。先让它列出会被删的文件，你看一眼，再点头。

🔒 铁律 4
sudo 命令必须过你的脑子。没有任何例外。它要跑 sudo，停下来问三个问题：要干什么？为什么需要管理员权限？有没有不用 sudo 的方案？

🔒 铁律 5
敏感信息不在代码里、不在项目目录里。API Key、数据库密码、支付密钥——放环境变量，或放项目目录之外。不要让 AI 有机会读到它们。

写在最后

说实话，用了这么久，Claude Code 从没搞出过让我想砸键盘的事。不是因为它在安全方面特别智能，而是因为它的权限模型很保守——每次写文件要确认、每次跑命令要确认、操作范围不出项目目录。

它最危险的时刻，不是它自己乱来，是你麻痹大意的时候。用得顺手了，确认弹窗一路按 Y，脑子里想着"上回没出过问题，这回也不会"。

别这样。Claude Code 是你的工具，不是你的替身。
最终每一行代码的责任都在你身上。

🚀 给它戴好安全带。
让它放开了干，但你的手永远在刹车上。
