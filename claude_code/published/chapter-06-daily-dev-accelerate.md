# 加一个接口要半天？我用 Claude Code 从需求到 PR 只花了 25 分钟

> 不是让你把代码全丢给 AI 写。而是教你怎么把"想清楚要什么"的 3 分钟，变成"已经写完了"的 25 分钟。

---

上篇聊了怎么用 Claude Code 快速接手一个陌生项目——别自己翻文件，让它先把地图画出来。

这篇更实战：**日常开发里最频繁的场景——接一个新需求，把它从"想法"变成"可以合并的 PR"。**

这个过程每一个开发者每天都在做。但你想过没有：你写代码的时间，有多少是在打字，有多少是在"查一下这个函数签名是啥"、"测试怎么跑来着"、"上次那个 util 叫啥名字来着"？

Claude Code 解决的不是打字问题，是这些**打断你心流的琐碎劳动**。

## 一、需求拆解：把一句话变成可执行的任务清单

大多数需求的原始形态长这样：

> "加一个导出功能，把用户列表导成 Excel。"

那个跟你说这句话的产品经理或 mentor，觉得这个需求很"清楚"。但实际上它有多少隐含问题？

- 导出哪些字段？全字段还是选择字段？
- 权限呢？谁能导出所有用户，谁只能导出自己团队？
- 数据量呢？100 条用户还是 10 万条？影响导出方式吗？
- Excel 格式有什么要求？要不要带样式？
- 前端是点按钮触发还是调接口？

你当然可以自己坐在那想半个小时，把所有可能的情况列出来，然后去追问。但 Claude Code 可以让这个过程快 10 倍。

### 实操：让 Claude Code 帮你拆需求

把需求描述丢给它，加上一句关键指令：

> "用户列表导出 Excel 功能。帮我把这个需求拆解成可执行的开发任务，用 checklist 格式。包含前端、后端、数据库（如果涉及）。列出需要澄清的模糊点，标注每个任务的风险等级。"

Claude Code 会给你类似这样的输出：

```
## 需求拆解：用户列表导出 Excel

### 需要澄清
1. 导出字段范围：用户基础字段 / 包含关联数据？
2. 权限策略：管理员全量导出 / 普通用户仅导出自己团队？
3. 数据量预估：<1000 条（直接生成） / >10000 条（异步任务）？

### 开发任务清单

前端：
[ ] 1. 在用户列表页添加"导出"按钮 [低风险]
[ ] 2. 前端调用导出 API，处理文件下载 [低风险]
[ ] 3. 导出进度提示与错误处理 [低风险]

后端：
[ ] 4. 创建 /api/users/export 接口 [中风险]
[ ] 5. 实现 Excel 生成逻辑（用 exceljs/excelize）[中风险]
[ ] 6. 接入权限校验——管理员 vs 普通用户 [高风险]
[ ] 7. 大数据量场景：异步导出 + 通知机制 [高风险]

测试：
[ ] 8. 接口单元测试：正常导出、空数据、无权限 [中风险]
[ ] 9. 前端组件测试：按钮状态、下载回调 [低风险]
```

### 为什么"拆需求"这一步值钱

你可能觉得"我自己也能想啊"。对，你能。但 Claude Code 是在**你还没开始想的时候**就列好了——而且它会结合对你项目的理解（读了 `package.json`、读了现有的路由结构），列出跟你项目实际情况相关的子任务。

你拿到这个清单去跟需求方确认 3 个问题，回来就能直接开写。比自己干想半小时再拿不确定的结论去问人，效率高太多了。

## 二、AI 写代码的正确打开方式

说清楚了要做什么，现在动手写。

### 最大的误区：把整个需求丢给它

见过很多人这样用 AI：

> "帮我实现用户列表导出 Excel 的功能。"

然后等它吐出一大堆代码，复制粘贴，跑一下——报错。再修。再报错。再修。最后发现还不如自己手写。

**这条命令的问题在哪？** 它没有上下文约束。Claude Code 不知道你的技术栈偏好、代码风格、现有组件——它只能猜。猜对了是运气，猜错了是常态。

### 正确的做法：分层写，逐步验收

别把一个复杂需求当成一个提示词。把它拆成**小块**，每一块写完之后验证通过、再写下一块。

**第一步：写后端接口**

> "在 server/src/routes/v1/users.ts 里新增 GET /users/export 接口。参考现有的 GET /users/list 接口的写法——包括权限校验方式和查询参数处理。返回值是 Excel 文件流，用 exceljs 包生成。只导出 id、name、email、role、created_at 五个字段，查询条件跟 /users/list 保持一致。"

注意这条指令里包含了什么：
- **精确位置**：`server/src/routes/v1/users.ts`——不让它猜
- **参考示例**：`/users/list`——它自己会去读那个接口的实现
- **技术约束**：用 exceljs——不给选择空间
- **字段范围**：只导出 5 个字段——不是"导出所有"

**第二步：写完就跑测试**

代码写完了，但不是"看着对"就行了：

> "跑一下这个新接口的测试。用项目里已有的测试框架（Jest/Vitest），参考 server/src/__tests__/users.list.test.ts 的结构来写。"

Claude Code 会自动：
1. 找到你的测试框架
2. 读一个已有的测试文件学结构
3. 生成新接口的测试
4. **自动跑一遍**，如果失败就修

**第三步：写前端调用**

> "在 client/src/pages/UserList.tsx 的表头工具栏区域增加一个导出按钮。点击按钮调用 GET /api/users/export 接口，触发浏览器文件下载。按钮样式参考页面已有的'批量操作'按钮。"

再次注意指令里的**位置约束**：

- 在哪个文件：`UserList.tsx`
- 在哪个位置：表头工具栏区域
- 参考什么：已有的按钮样式
- 行为定义：调接口、触发下载

---

### 关键心法：精准不等于啰嗦

你可能觉得这样写指令太长了。但对比一下：

| 方式 | 提示词长度 | 返工次数 | 总时间 |
|------|-----------|---------|--------|
| 模糊指令："帮我写导出功能" | 短 | 3-5 次 | 40 分钟+ |
| 精准指令：指定文件、参考、约束 | 长 | 0-1 次 | 5-10 分钟 |

**写指令的 30 秒，省的是返工和排查的 20 分钟。** 不是"少说点省时间"，是"说清楚省时间"。

## 三、写功能顺手写好测试

测试是"我知道该写，但就是不写"排行榜第一名。

不是因为懒，是因为写完功能已经很累了，再写测试——要 mock 数据、要模拟场景、要覆盖边界条件——心理阻力巨大。

### Claude Code 怎么帮你写测试

写完功能之后，只用说一句话：

> "为刚才的改动写测试。覆盖正常场景、权限拒绝场景、空数据场景。用项目已有测试框架和 mock 方式。"

它自己会去：
- 检查项目用的是 Jest 还是 Vitest
- 读已有的测试文件了解 mock 写法
- 生成测试覆盖你指定的场景
- 跑一遍确认通过

### 一个很实在的场景

你在写一个对外的 API，改了参数验证逻辑。按理说你要把相关的测试全跑一遍，但你"感觉应该没问题"——就没跑。

上线之后，之前的一个参数格式从 camelCase 变成了 snake_case，前端调用炸了。排查半小时，修一行代码。但损失的不只是这半小时——是线上用户实际受到了影响。

**Claude Code 不会累，不会"懒得跑"。** 你让它跑测试它就跑，跑完报错它自己修，修完再说一声"刚才 3 个测试有问题，我改了，现在全绿了"。

### 更进一步：用 /goal 让它修到全绿为止

上面说的还是"你说修，它修"的模式。Claude Code 2026 年推出的 `/goal` 命令（详见本系列进阶篇）可以更进一步——你设一个目标，它自己循环干到达标：

```bash
/goal 运行 npm test，所有测试通过，0 failures。可以改 src/ 下的文件，不要动 test/。stop after 20 turns。
```

设完之后你就可以切走干别的了。它会一轮一轮自己修——改代码、跑测试、看报错、再改——直到全绿或者达到轮次上限。你回来的时候要么全部测试绿灯，要么它告诉你卡在哪了。

## 四、让 AI 帮你 Review 你自己的代码

在提 PR 之前，你通常会：
1. 自己扫一眼 diff
2. 觉得"差不多"
3. 提 PR
4. Reviewer 指出 5 个问题
5. 改，再提

### 加了 Claude Code 之后

流程变成：

> "Review 我这次的改动。检查：边界条件有没有遗漏、错误处理是否完整、有没有可能的安全问题（比如 SQL 注入、XSS）、代码风格是否跟项目一致。不用改，只列问题和建议。"

它会给你类似这样的输出：

```
### Code Review: 用户导出功能

1. [中等] server/src/routes/v1/users.ts:145
   导出时未限制最大数量。如果数据库有 10 万条用户，
   一次性加载会 OOM。建议加 LIMIT 或改异步。

2. [低] server/src/services/export.service.ts:32
   创建日期格式用了 toLocaleString()，在不同时区
   可能不一致。建议用 dayjs.utc().format()。

3. [信息] client/src/pages/UserList.tsx:88
   导出按钮未加 loading 态。点击后到文件开始下载之间
   有 1-3 秒空白，用户可能重复点击。建议加 disabled+loading。

4. [通过] 错误处理完整，权限校验正确使用了已有的 hasPermission 中间件。
5. [通过] Excel 字段顺序与产品文档一致，数值格式正确。
```

然后你修掉 1、2、3，再自己看一眼 diff——这时候大概率只有"是真的没问题了"的改动，不会有 Reviewer 一眼看穿的低级疏漏。

**把 AI Review 作为一个前置环节，不是替代人工 Review，而是减少人工 Review 的返工次数。** 你的 Reviewer 同事会感谢你的。

## 五、一气呵成：从需求到 PR 的完整时间线

以一个中等复杂度的功能——"用户列表导出 Excel"为例：

| 环节 | 纯手动 | 有 Claude Code |
|------|--------|---------------|
| 需求拆解 + 确认 | 30 min | 5 min（AI 拆解 + 确认 3 个点） |
| 后端接口开发 | 45 min | 8 min（指令 + 跑通 + 修正） |
| 测试编写 | 30 min | 3 min（自动生成 + 跑绿） |
| 前端联调 | 40 min | 8 min（接口调用 + 文件下载） |
| 自测 Review | 20 min | 5 min（AI Review + 修问题） |
| PR 文案 | 10 min | 1 min（下期讲） |
| **总计** | **2h 55min** | **30 min** |

这个对比数字可能会让你觉得"太夸张了"。实话是——经验越少的开发者、越不熟悉的项目，AI 提效越明显。因为 AI 擅长补的是"我不知道这个函数的签名是啥"、"我不知道现有代码怎么写"这类信息差，而这恰恰是消耗最多时间的地方。

**但同时要说一句不太中听的话：** 这些数字的前提是你**知道每一步该让 AI 干什么**。如果你不知道后端接口应该放在哪个目录、不知道测试框架怎么用，AI 也能帮你——但你需要多花时间确认它做出来的东西对不对。

AI 最大的提效不是替你干活，是**替你消化那些无聊的上下文切换**——查文档、查函数签名、查已有的代码风格。你的脑子留给"这个功能到底应该怎么设计"。

## 写在最后

这一篇全程在讲"开发怎么加速"。但我说一个可能让你不舒服的观点：

**如果你只是让 AI 写得更快，却不改自己的开发习惯，你的效率提升可能只有 20%。**

习惯的力量太大了。写一个功能之前——你会习惯性地先打开两个文件看看参考。测试你会习惯性地往后拖。Review 你会习惯性地扫一眼就觉得"还好"。然后一天就过去了，回想起来，真正创造代码的时间可能不到 3 小时。

Claude Code 的好处不是它写代码有多快。是它让你不需要被打断——不需要切出去查 API 文档、不需要翻老代码找写法、不需要为了写测试先搞明白 mock 怎么配。

**你的心流是宝贵的。跟 AI 协作的关键，是让它吞掉所有打断心流的事。**
