🧠 Claude Code 实战

Claude 不是万能的
聪明人都在用多模型流水线，省钱又提速

Claude 擅长推理但贵、本地模型便宜但笨、GPT 写文档强但代码弱——干嘛非选一个？把任务拆开，分给最合适的模型。架构师不扫地，扫地工不设计架构。

📝 写在前面：你在用 Claude Code 的时候，有没有想过一个问题："去 console.log"这个操作，值得让 Claude 来做吗？

Claude 擅长的是复杂推理、多文件联动、长代码重构。但在另一些场景——"批量格式化代码"、"翻译字段名"、"生成 commit message"——你让它做这些，就像让一个架构师去扫地。这篇讲的是怎么把几个 AI 组合起来，用多模型流水线——便宜模型干简单活，Claude 干重活。总成本降一半，速度还更快。

1 Claude Code 的甜区在哪里

📌 它最擅长的事

用一句话总结：需要"理解关系"的任务。

什么是"理解关系"？

你改了数据库 Schema，需要找到所有受影响的后端接口、前端调用、测试 mock、SQL 语句——这是关系（schema → api → ui → test）

一个 Bug 出现在登录流程，但你不知道前端还是后端的问题——这是关系（请求链路追踪）

Code Review 发现一处写法不规范，想知道全项目还有没有类似问题——这是关系（代码模式搜索）

重构一个状态管理逻辑，从 Redux 迁到 Zustand——这是关系（全局状态 → 组件 → selector → dispatch）

这些任务的共同特征：不是改一行代码的问题，是搞清楚代码之间怎么连接的。

📌 甜区之外：它的"性价比低谷"

以下任务让 Claude 做，效果一样好——但价格是你多付的：

批量格式化代码 → 纯规则操作，0 推理 → 用 Prettier
去 console.log → 纯正则搜索替换 → Haiku / 本地模型
翻译字段名 → 单词级翻译 → Haiku
生成样板代码 → 模板化，不需要决策 → 本地模型 / Snippet
写单元测试框架 → 固定结构，填充数据 → Haiku
生成 commit message → 读 diff → 总结 → Haiku / 本地模型
答简单 API 问题 → "这个函数参数是什么" → 本地模型 / grep

💡 决策公式：这个任务需要理解至少 3 个文件之间的关系吗？→ 是：Claude。否：便宜模型或工具。

2 什么时候该换模型

📌 实时性要求高的场景

Claude 的推理需要时间——有时候要 10-30 秒出一段复杂代码。对开发来说还好，但如果是"用户在等"的场景——比如 IDE 里的自动补全——你等不了。这类场景更适合用本地部署的轻量模型或者更快的云 API。

📌 批量处理场景

"把这 50 个 markdown 文件里的 API 文档格式统一一下"。逐个处理，不需要跨文件理解——每篇都是独立任务。这种"量大但不复杂"的场景是最适合用便宜模型的。

📌 成本敏感的大团队

一个 20 人的团队都用 Claude Code，每人每月烧 $80。技术负责人说"我们要省点"——但你没法要求大家"少用 AI"，那等于要求大家"干活慢点"。多模型策略在这种场景下是唯一解法：保留 Claude 用于核心任务，简单任务路由到便宜模型。质量不打折，成本降 60%。

3 本地模型入局：Ollama 做简单任务

用一个事实开头：本地模型在复杂推理上跟 Claude 不是一个量级。

但另一个事实：简单任务占总交互量的 40-50%。

你可以用 Claude Code 的 CLI 参数指定模型。如果本地跑了 Ollama：

# Claude 做复杂推理
claude "重构 src/services/order.ts 的退款逻辑"

# 本地模型做简单事
claude --model ollama/qwen2.5-coder:7b "去掉 src/ 下所有 tsx 文件里的 console.log"

📌 本地模型的三个最佳场景

① 代码格式化 / 批量替换
"把 src/api/ 下所有文件的导入语句按项目规范重排"——本地模型做到 90 分，Claude 做到 95 分。多花 8 倍钱换 5 分——不值。

② 生成 commit message / PR 描述
读 diff、总结、套规范——不需要深度推理，给便宜的做。

③ 代码注释和文档生成
"给 src/utils/helpers.ts 里每个函数加 JSDoc 注释"——纯格式化的活。让本地模型出一个草稿，你再审。

📌 硬件门槛参考

Qwen2.5-Coder 7B — 最低 6GB 显存 — 简单格式化、注释
Qwen2.5-Coder 14B — 最低 10GB 显存 — 中等复杂度的代码变更
DeepSeek-Coder 33B — 最低 20GB 显存 — 接近 Sonnet 水平的推理

MacBook Pro M1 Max 32GB 可以轻松跑 14B 级别的模型。普通笔记本可能只能跑 7B——够用，别期望太高。

4 构建你的第一条多模型流水线

多模型流水线的核心逻辑：用户请求 → 任务路由器 → 简单任务 → 本地模型 / Haiku；复杂任务 → Sonnet / Opus。

📌 一个典型工作日的任务分配

假设你今天要做以下 5 件事：

1. 去掉 src/components/ 下所有 console.log ← → 本地模型
2. 重构 src/services/order.ts 的退款状态机 ← → Claude Sonnet
3. 写完代码后跑 14 个测试，修到全绿 ← → /goal + Sonnet
4. 把 3 个英文字段名翻译成中文注释 ← → Haiku
5. Review 重构之后的架构改动 ← → Claude Opus

如果用 Claude Sonnet 做全部 5 件事：约 $4.5。用多模型策略：约 $1.8。

💡 每天省 $2.7。一个月 20 个工作日 = $54。一年约 $600。

📌 进阶：让 Claude Code 自己路由

"分析以下任务清单，把每个任务标上'复杂度：低/中/高'和'推荐模型：Haiku/Sonnet/Opus'，给出原因。"

每次花 150 个 token 做一次路由判断，省的是几百倍的 token。

📌 一个完整的流水线实例

假设你做一次"为 PayService 加单元测试"的流程：

第 1 步：分析 PayService 源码，确定测试范围
→ 模型：Haiku（只读代码、提取函数签名和分支——纯体力活）
→ 时间：5 秒 → 成本：~$0.01

第 2 步：生成测试代码
→ 模型：Sonnet（需要理解业务逻辑，设计测试用例）
→ 时间：15 秒 → 成本：~$0.08

第 3 步：运行测试，修复失败
→ 模型：/goal + Sonnet（自动迭代修到全绿）
→ 时间：2 分钟 → 成本：~$0.15

第 4 步：Review 测试覆盖率和质量
→ 模型：Opus（深度审查，一次性的——值得花这个钱）
→ 时间：10 秒 → 成本：~$0.30

总时间：约 2.5 分钟 | 总成本：~$0.54

如果全用 Sonnet 做，成本约 $1.2。如果全用 Opus，成本轻松破 $5。

5 多模型协作的避坑指南

📌 坑一：不同模型对同一份代码的理解可能不一样

本地模型的推理能力弱，你对它的指令需要更具体、更模板化。

❌ 对本地模型："优化这个函数的性能"

✅ 对本地模型："把 users.map(user => user.name) 里的 for 循环改成数组方法，不要动其他逻辑"

给本地模型的指令要像给新手的指令——每一步都写清楚。

📌 坑二：不要在同一个对话里切换模型

Claude Code 的对话上下文是模型绑定的。你在 Claude 的对话里生成的东西，如果切到本地模型，历史上下文可能格式不兼容。不同模型用不同对话窗口。简单任务的输出复制过来当参考就行。

📌 坑三：过度优化

看了这篇文章之后，你可能会想"先把所有任务归类，再逐个分配模型"。这就过头了。

💡 记住核心原则：任务需要"理解多个文件之间的关系"→ Claude。否则 → 便宜模型或工具。花在"该用哪个模型"上的决策时间不要超过 5 秒。

写在最后

这篇文章其实不是一个"省钱教程"。它的核心观点是：把 AI 当作一个工具箱，而不是一把万能钥匙。

Claude 是把好螺丝刀，但不是锤子。你要钉钉子，找便宜模型——或者直接用 Prettier，它免费。

用多模型策略的时候，你是架构师——不只是写代码的架构师，也是"把工作分给谁做"的架构师。这个角色跟传统的程序员相比，多了一层决策权。用好它。
