# 第四章：落地实战 —— 3 套通用 AI 工作流

> **本章定位**：第三章给了你团队架构，本章给你"怎么让它们跑起来"。不讲原理、不讲选型——直接给三套可复用的工作流，覆盖内容创作、编程开发和综合自动化三大场景。每个工作流都标注了触发器、流转步骤、配置要点和落地避坑。

---

## 引言：架构是骨架，工作流是血液

上一章你搭好了 AI 团队——策略洞察、内容写作、视觉设计、渠道发布四个 Agent 各就各位。但它们是散着的。

**工作流要解决三个问题**：
1. **谁先谁后** —— Agent 之间的执行顺序和依赖关系
2. **怎么触发** —— 定时自动、事件驱动、还是手动启动
3. **出错了怎么办** —— 异常处理、重试机制、人工兜底

本章的三套工作流分别对应第三章的三种团队形态——但你不必全看。**找到你的场景，拿走现成的流程。**

## 场景 1：内容创作全流程

> 对应第三章 **形态一**：个人纯虚拟 AI 团队。
> 一条内容生产线的完整自动化，从"早上打开电脑"到"晚上文章发布"。

### 1.1 业务画像

| 维度 | 详情 |
|------|------|
| **使用者** | 公众号/博客/小红书创作者、个人 IP |
| **AI 团队** | 4 个 Agent：策略洞察 → 内容写作 → 视觉设计 ∥ 渠道发布 |
| **人的角色** | 3 次决策（选选题、审初稿、定封面），≤20 分钟 |
| **输出物** | 1 篇长文 + 多平台版本 + 封面配图，每日 |
| **核心工具** | Make.com（编排）+ Claude API（写作）+ DALL·E（配图） |

### 1.3 逐步拆解

#### Step 1：策略 Agent 扫描热点（自动）

| 属性 | 内容 |
|------|------|
| **触发方式** | Make.com 定时触发器，每日 08:00 |
| **输入** | 品牌定位文档（Dify 知识库）、历史爆款数据 |
| **处理** | Claude API 调用，Prompt 含「热点 × 痛点 × 专业壁垒」三维模型 |
| **输出** | 5 个选题候选，每个带：目标人群匹配度 / 预期阅读量级 / 差异化角度 |
| **输出格式** | 结构化 Markdown，通过 Make.com 推送到你的飞书/微信/邮件 |

**Prompt 核心片段**（放进 Dify 知识库作为 System Prompt）：

```
你是专注[领域]的新媒体主编。基于以下信息，输出5个今日选题候选：

【品牌定位】
{从知识库自动注入}

【近期爆款模式】
{策略Agent 上次周报中的模式总结}

【今日热点】
{通过 RSS/API 自动抓取}

【输出格式】
1. 选题标题 + 一句话概述
2. 目标人群匹配度（高/中/低）
3. 差异化角度（为什么读者要看你的版本而不是别人的）
4. 参考素材链接（至少2个）
```

#### Step 2：人工确认选题

- 你从 5 个候选里选 1 个，**3 分钟内搞定**
- 确认后 Make.com 自动将选中的 Brief 推送给写作 Agent
- Make.com 配置要点：用 **Webhook 响应** 或 **即时通讯 Bot 按钮** 收集你的选择

#### Step 3：写作 Agent 生成初稿（自动）

| 属性 | 内容 |
|------|------|
| **触发** | Make.com 收到你的选题确认后自动调用 |
| **模型** | Claude 3.5 Sonnet（长文质量最优） |
| **处理** | 根据 Brief 撰写 1500-3000 字初稿 + 5-10 个标题候选 + 配图需求描述 |
| **输出** | 一份结构化交付物（Markdown），包含：标题库、正文、配图需求、多平台改写建议 |

**写作 Agent System Prompt 核心**（放 Dify 知识库）：

```
你是资深商业写作者。基于选题 Brief 产出初稿。

写作原则：
- "认知差写作法"：每篇文章至少给读者1个"原来如此"的时刻
- 开头用具体场景/数据/反常识观点钩住读者
- 正文至少3个小标题，每个小标题下不超过500字
- 数据必须标注来源，不编造案例

输出结构：
1. 【标题候选】5-10个，每个标注心理学钩子类型（好奇缺口/损失厌恶/社会认同）
2. 【正文】1500-3000字结构化 Markdown
3. 【配图需求】位置、描述、建议尺寸
4. 【多平台改写建议】小红书300字版 / 微博140字版 / 知乎导语
```

#### Step 4A & 4B：并行处理（自动）

审核通过后，Make.com 同时触发两个分支：

| 分支 | Agent | 任务 | 模型/工具 | 预计耗时 |
|------|-------|------|----------|---------|
| **4A** | 设计 Agent | 封面（2.35:1 + 3:4 双尺寸）+ 信息图 | DALL·E 3 / Midjourney | 5-8 分钟 |
| **4B** | 渠道 Agent | 多平台改写 + 话题标签 + 自动排期 | Claude 3.5 Haiku | 3-5 分钟 |

**渠道 Agent 多平台输出模板**：

```
【小红书版】
- 标题：{从标题库选最吸睛的1个，限制20字}
- 正文：{300字以内，带emoji分段}
- 标签：{#话题1 #话题2 #话题3}
- 封面建议：{3:4竖版}

【知乎版】
- 问题式标题：{转化为知乎体提问}
- 导语：{100字钩子}
- 正文：{完整长文}
- 话题标签：{知乎话题}

【微博版】
- 正文：{140字以内，提炼最核心观点}
- 配图：{1张信息图或封面}
- 话题：#话题#

【排期建议】
- 公众号：今日 21:00
- 小红书：明日 12:00
- 知乎：明日 10:00
```

#### Step 5：发布（半自动）

Make.com 通过各平台 API 填充发布草稿，你最终确认后发布：

| 平台 | 发布方式 | 说明 |
|------|---------|------|
| **公众号** | 微信公众号 API | 填充草稿箱，你手动确认发送 |
| **小红书** | 小红书开放平台 | 填充笔记草稿，你手动发布 |
| **知乎** | 知乎 API | 自动发布文章（信任度高，可全自动） |

> **为什么不一键全自动发布？** 公众号和小红书的封号风险高，留一道人工确认是最低成本的保险。

#### Step 6：数据回流（次日自动）

策略 Agent 的第二个职责——数据复盘：

```
次日 08:00（在当日选题扫描之前）

1. 调用各平台 API 拉取昨日文章数据
2. 生成数据复盘卡片：
   - 阅读量 vs 近7日均值
   - 分享率（最重要指标）
   - 收藏率（深度价值指标）
   - 标题点击率（标题质量信号）
3. 对比本次标题预测 vs 实际表现
4. 更新「爆款模式库」，作为次日选题的参考
```

### 1.4 Make.com 落地配置要点

整个 Pipeline 的核心编排工具是 Make.com（前身 Integromat）。

**关键配置节点**：

| Make 模块 | 用途 | 配置要点 |
|-----------|------|---------|
| **Schedule Trigger** | 每日 08:00 自动启动 | 设置时区为 Asia/Shanghai |
| **HTTP > Make a Request** | 调用 Claude API | 请求体含 System Prompt + User Message |
| **Webhook Response** | 接收你的选题确认 | 配合飞书 Bot / Telegram Bot 做交互 |
| **Router** | 审核后分流：设计 + 渠道并行 | 用 Router 模块实现并行分支 |
| **Error Handler** | API 调用失败重试 | 设置重试 3 次，间隔 30 秒 |

**成本控制要点**：
- 渠道改写用 Claude Haiku（比 Sonnet 便宜 10 倍，格式转换足够）
- 图片用 DALL·E 3 而非 Midjourney（成本低 60%）
- Make.com 免费额度每月 1000 次操作，日更创作者完全够用

### 1.5 避坑指南

| 坑 | 表现 | 解法 |
|----|------|------|
| **选题越来越窄** | 数据闭环导致"只做验证过有效的选题" | 每月手动注入 3 个「跨领域」选题，刻意打破信息茧房 |
| **写作风格同质化** | 所有文章读起来一个味儿 | 每 10 篇文章微调一次 System Prompt 中的风格参数 |
| **封面审美疲劳** | 读者对固定风格免疫 | 设计 Agent 维护 3 套视觉模板，轮换使用 |
| **依赖单点 API** | Claude 挂了整条线停摆 | 配置 Fallback：Claude API 超时 → 自动切 DeepSeek |

### 2.3 逐步拆解

#### Step 1：触发机制

**方式 A：GitHub Issue 触发（推荐）**

在 GitHub Actions 中配置 Issue 事件监听：

```yaml
# .github/workflows/ai-dev-pipeline.yml
name: AI Development Pipeline

on:
  issues:
    types: [opened, labeled]

jobs:
  ai-coding:
    if: contains(github.event.issue.labels.*.name, 'ai-dev')
    runs-on: self-hosted  # 跑在你有 GPU 的本地机器上
    steps:
      - name: Parse Issue
        id: parse
        run: |
          echo "REQUIREMENT<<EOF" >> $GITHUB_ENV
          echo "${{ github.event.issue.body }}" >> $GITHUB_ENV
          echo "EOF" >> $GITHUB_ENV

      - name: Call Coding Agent (Ollama)
        run: |
          curl -X POST http://localhost:11434/api/generate \
            -H "Content-Type: application/json" \
            -d '{
              "model": "qwen2.5-coder:14b",
              "prompt": "$REQUIREMENT",
              "stream": false
            }' > /tmp/code_output.json

      - name: Create Pull Request
        run: |
          # 解析 Agent 输出, 创建 feature 分支和 PR
          python3 .github/scripts/create_pr.py /tmp/code_output.json
```

**方式 B：Cursor 内 /command 指令（快速原型）**

在 Cursor 中配置自定义命令，直接在 IDE 里触发编码 Agent：

```
# .cursor/commands/codegen.md
你是全栈工程师。基于以下需求生成代码：
{用户输入}

遵循项目规范（从 .cursorrules 自动加载）。
输出：完整代码文件 + 关键逻辑注释。
```

#### Step 2：编码 Agent（核心）

**本地推理配置**（Ollama Modelfile）：

```dockerfile
# Modelfile for Coding Agent
FROM qwen2.5-coder:14b

SYSTEM """
你是一名资深全栈工程师，精通 TypeScript/Python/Go。

工作流程：
1. 理解需求描述
2. 从项目知识库（ChromaDB）检索相关代码上下文
3. 遵循现有架构模式和编码规范
4. 生成代码 + 关键逻辑注释
5. 标注不确定的决策点为 // TODO: DECISION - xxx

输出格式：
- 代码文件路径 + 完整内容
- 关键设计决策说明
- 需要人工确认的部分（TODO 标记）
"""
```

**RAG 增强**（ChromaDB 集成）：

```
编码 Agent 生成代码前，自动执行的 RAG 管线：

1. 将需求描述 Embedding 化（BGE-M3 本地模型）
2. 在 ChromaDB 中搜索相似代码片段（Top 5）
3. 将检索结果拼入 System Prompt 的「相关上下文」区块
4. Agent 生成的代码能自动遵循已有命名规范、目录结构、API 调用模式
```

#### Step 3：并行检查（三个 Agent 同时跑）

PR 创建后，GitHub Actions Webhook 同时触发三个检查 Job：

**审查 Agent 的输出模板**：


### 2.4 GitHub Actions 完整配置

```yaml
# .github/workflows/ai-review.yml
name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  ai-review:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Get PR diff
        run: |
          git diff origin/${{ github.base_ref }} > pr_diff.txt

      - name: AI Code Review
        run: |
          DIFF=$(cat pr_diff.txt | head -c 8000)  # 截断防止超 token
          curl -s -X POST http://localhost:11434/api/generate \
            -H "Content-Type: application/json" \
            -d "{
              \"model\": \"qwen2.5-coder:14b\",
              \"prompt\": \"$(cat .github/prompts/code-review.md)\n\n${DIFF}\",
              \"stream\": false
            }" | jq -r '.response' > review_report.md

      - name: Post Review as PR Comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = fs.readFileSync('review_report.md', 'utf8');
            await github.rest.issues.createComment({
              ...context.repo,
              issue_number: context.issue.number,
              body: report
            });
```

### 2.6 避坑指南

| 坑 | 表现 | 解法 |
|----|------|------|
| **Agent 过度设计** | 简单需求生成出三层继承 + 工厂模式 | System Prompt 中强调"遵循项目现有复杂度，不过度工程化" |
| **RAG 检索漂移** | 检索到的代码和实际需求不相关 | 用需求标题做第一次过滤，再用 Embedding 做精排（两阶段检索） |
| **测试 Agent 生成无用测试** | `assert 1+1==2` 这种无效用例 | System Prompt 要求"每个测试必须覆盖一个业务逻辑分支" |
| **本地模型 OOM** | 上下文太长导致显存溢出 | 截断 PR diff 到 8000 字符，只送变更部分而非全文 |
| **安全 Agent 误报过多** | 把 `console.log` 也标为安全漏洞 | 维护白名单规则库，排除已知安全模式 |

## 场景 3：综合自动化工作流

> 对应第三章 **形态二**：人机混合团队。
> 多 Agent 协作、任务分发与编排、异常处理——让 AI 团队真正像一个团队那样工作。

### 3.1 业务画像

| 维度 | 详情 |
|------|------|
| **使用者** | 小微工作室、SaaS 创业团队、电商运营 |
| **AI 团队** | 8-12 个 Agent，分属内容线/商务线/运营线/技术线 |
| **人的角色** | 任务分派 + 关键节点审批 + 客户关系 |
| **核心工具** | Dify（工作流编排）+ Make.com（跨系统连接） |
| **核心挑战** | 不是单个 Agent 的能力，而是多个 Agent 之间的协调 |

### 3.2 多 Agent 协作模式

在工作室体量下，Agent 之间的协作有三种经典模式：

```
模式 A：串行流水线（Pipeline）
Agent 1 ──→ Agent 2 ──→ Agent 3 ──→ 人工审批 ──→ 输出
适用：内容生产、方案撰写等有明确先后顺序的任务

模式 B：并行分发（Fan-out / Fan-in）
           ┌─→ Agent A ─┐
任务分发 ──┼─→ Agent B ─┼─→ 结果聚合 ──→ 人工审批
           └─→ Agent C ─┘
适用：竞品分析、多维度调研等可同时进行的任务

模式 C：辩论式（Debate）
Agent A 观点 ──→ Agent B 反驳 ──→ Agent C 裁决 ──→ 给出分歧点 → 人最终决策
适用：战略决策、方向选择等需要多视角碰撞的任务
```

#### 场景 B：多 Agent 协作的关键设计原则

| 原则 | 说明 | 反面例子 |
|------|------|---------|
| **Agent 不调 Agent** | Agent A 不能直接调用 Agent B，统一由编排层调度 | Agent A prompt 里写"你去调用 Agent B"——幻觉风险极高 |
| **每次交接设检查点** | Agent 之间的输出必须经过校验节点（可以是自动规则，也可以是人工） | 上游 Agent 的错误一路传递到最终输出才发现 |
| **结果需标注来源** | 每个 Agent 的输出标注"我是谁、我做了什么、不确定什么" | 多个 Agent 的输出混在一起，出问题无法追溯 |
| **设置超时和熔断** | 单个 Agent 超过 60 秒未返回 → 自动降级到备选方案 | 一个 Agent 卡住，整条链路堵死 |

**Dify 工作流中的人工审批配置**：

在 Dify Chatflow 中，人工审批通过**「等待回复」节点**实现：

```
1. 在需要审批的位置插入「等待回复」节点
2. 配置审批提示：「提案已生成，请审核后回复『通过』或『驳回 + 修改意见』」
3. 后续用条件分支判断回复内容：
   - 包含「通过」→ 继续下一步（合同生成）
   - 包含「驳回」→ 回到方案框架节点，将修改意见作为额外输入重新生成
```

### 3.5 异常处理与熔断机制

多 Agent 协作中，最致命的问题不是单个 Agent 出错，而是**错误在 Agent 之间传播放大**。

**三层防护设计**：

```
第一层：单 Agent 超时熔断
├─ 每个 LLM 节点设置 60 秒超时
├─ 超时自动重试 1 次（部分 LLM 调用偶发超时是正常的）
├─ 重试仍超时 → 降级输出："{Agent名称}处理超时，请人工介入"
└─ 关键节点超时（如方案框架）→ 整条链路暂停，推送告警

第二层：输出格式校验
├─ 关键 Agent（如合同生成）配置输出校验规则
├─ 规则示例：合同必须包含「甲方、乙方、金额、服务内容、违约责任」
├─ 校验不通过 → 自动追加一次 LLM 调用：「你的输出缺少{缺失项}，请补充」
└─ 二次校验仍不通过 → 标记为需人工审查

第三层：全链路兜底
├─ Dify 配置全局 Error Handler
├─ 任何未捕获异常 → 输出「工作流异常：{错误摘要}」
├─ 同时通过飞书/钉钉 Bot 推送告警消息
└─ 保留中间产物（每个节点的输出都缓存），方便人工接手排查
```

### 3.6 避坑指南

| 坑 | 表现 | 解法 |
|----|------|------|
| **Agent 自由度过高** | Agent A 写了一篇完全不搭边的方案 | System Prompt 中加「边界约束」：输出范围、禁止天马行空 |
| **并行结果互相矛盾** | 竞品 Agent 说市场在增长，数据 Agent 说在萎缩 | 聚合节点加「矛盾检测」：如矛盾则标红推给人裁决 |
| **审批节点成为瓶颈** | 等待人工审批 2 小时，工作流卡住 | 设定审批超时：30 分钟不回 → 自动推送提醒 → 1 小时仍未回 → 标记为「需后续处理」，不阻塞非依赖节点 |
| **知识库过期** | 竞品 Agent 引用半年前的竞品数据 | 知识库加时间戳标签，Agent Prompt 要求「只引用最近 30 天数据」 |
| **工作流版本混乱** | 改了 Prompt 但旧版工作流还在跑 | 所有工作流加入版本号（v1.2.3），变更记录写入 Git |

## 本章小结

三套工作流不是让你选一套就万事大吉，而是给你一个**可运行的起点**：

- **场景 1 的关键**：不是 Make.com 的配置，是**人的审核节点卡在最需要判断力的地方**（选题方向、内容质量、视觉审美）
- **场景 2 的关键**：不是本地模型跑多快，是**审查 Agent + 测试 Agent + 安全 Agent 三道防线让你的每一次 Merge 都心中有底**
- **场景 3 的关键**：不是 Agent 数量多，是**编排层对异常的处理和人工审批的节奏设计**——一个卡住的审批节点可以堵死整条链路

工作流搭好之后，你会发现一个新的问题：**Agent 们跑起来了，但你不知道怎么管它们——怎么衡量产出质量？怎么持续优化？怎么防止能力退化？**
