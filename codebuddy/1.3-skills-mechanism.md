# 用了三个月才发现一直在「裸奔」——打开这个开关，AI 突然专业了 10 倍

> 系列：CodeBuddy 入门教程 · 第 3 篇
>
> 读完这篇你能：理解 Skills 是什么、知道怎么加载、看完 A/B 对比之后自己会选。

---

我用了差不多三个月 CodeBuddy 之后，才发现自己一直在"裸奔"。

之前我就是把它当成一个高级版 ChatGPT 嵌在代码编辑器里——聊天、改代码、生成文件。用着还行，但没觉得跟 Cursor 有啥本质区别。

直到有一次，我随手加载了一个叫 `python-best-practices` 的 Skill。然后做了个测试：把同一个需求——"写一个 REST API 接口，带参数校验和错误处理"——让它在加载 Skill 和没加载的情况下各写一遍。

结果让我心里一沉。

没加载 Skill 的那个版本，功能上能用，但代码像实习生写的：函数名随意、没有类型标注、异常处理只糊了一层 try-catch、连 request body 都没校验。

加载了 Skill 的版本，完全变了个样——分层架构（Router → Service → Repository）、Pydantic v2 数据模型校验、异步 async/await、所有异常分支都有对应的 HTTP 状态码返回，甚至主动写了单元测试。

**同样的模型，同样的需求，出来的东西天差地别。不是 AI 变聪明了，是 Skill 给它"上了规矩"。**

---

## Skill 到底是个啥——三个比喻讲清楚

**比喻1：给 AI 安装 App**

你手机不装 App 的时候只能打电话发短信。装了地图 App → 能导航，装了支付宝 → 能付款。Skill 也一样——不装的时候 AI 就是个通用助手，装了特定 Skill → 它在那个领域突然变"专业"了。

**比喻2：给新同事发工作手册**

你招了个新同事，不告诉他公司流程、命名规范、技术栈偏好，他只能按自己习惯来，出来的结果五花八门。你给他发一份"内部开发规范"——他马上就按规矩办事了。Skill 就是这份"工作手册"。

**比喻3：足球队的战术板**

没有战术板就是野球——大家各跑各的。摆了战术板，每个人知道什么时候该跑位、什么时候该回防。Skill 就是 AI 的战术板。

技术上讲，Skill 是一组**预定义的提示词 + 工具调用规则 + 领域知识**的打包文件，放在 `.codebuddy/skills/` 目录下。当你在对话中加载某个 Skill，CodeBuddy 会把这组指令注入到 AI 的"系统提示"里——相当于在 AI 干活之前，先给它读一遍"工作规范"。

> *知识引用：Skills 机制继承了 Claude 的 System Prompt 设计理念（Claude 允许通过系统提示设定角色行为），CodeBuddy 将其产品化为可插拔、可组合的专业模块。*

## Skills 藏在哪里——两层存储，用法不同

Skill 有两个存放位置，它们的作用范围不一样：

**用户级 Skills**（`~/.codebuddy/skills/`）
- 在你电脑上所有项目通用
- 适合放"通用型"技能：比如 `article-writing`（文章写作）、`brainstorm`（头脑风暴）
- 装一次，所有项目都能用

**项目级 Skills**（`项目根目录/.codebuddy/skills/`）
- 只在这个项目里生效
- 适合放"项目专属"技能：比如团队内的代码规范、特定框架的最佳实践
- 跟项目代码一起提交到 Git，团队共享

一个简单原则帮你判断：**能用项目级的就用项目级。** 因为用户级 Skills 越积越多之后会拖慢 AI 响应速度——每次对话都要把所有用户 Skills 加载进上下文，即使你用不上。

## 值得一试的内置 Skills——我的 TOP 5 排名

CodeBuddy 内置了几十个 Skills，不用全部学，先试试这几个。

这是我的真实使用频率排名，从高到低：

### 🥇 `brainstorm` —— 头脑风暴

用得最多。每次遇到"不知道该怎么做"的问题，直接加载它。

适合场景：想不清技术方案、不确定功能怎么设计、需要有人跟你讨论产品方向。

实操一句："我现在要做一个 XXX，帮我 brainstorm 一下技术选型和架构方案。"

它的回答不是糊弄的"你可以用 A 也可以用 B"——它会真的追问你约束条件（用户量多少？预算多少？团队几个人？），然后给你结构化的分析。

### 🥈 `diagnose` —— Bug 诊断

碰到 bug 不知道怎么排查的时候，它是救星。

适合场景：程序报错但看不懂错误信息、性能变慢找不到原因、线上出问题需要快速定位。

实操一句："这个项目跑起来之后内存一直在涨，帮我诊断一下是不是有内存泄漏。"

它会引导你：先复现 → 缩小范围 → 提出假设 → 验证 → 修复。不是一次性给答案，而是带着你找到答案。

### 🥉 `article-writing` —— 写文章

说实话，我写公众号的时候一定会加载它。

适合场景：写技术文章、教程、产品文档、公众号推文。

如果你只用它写作，质感会很 AI——我的做法是让它出框架和草稿，然后我自己改语气、换例子、加真实体验。它负责"不出错"，我负责"有人味"。

### 4️⃣ `python-api-endpoint-creator` —— API 开发

写 Python 后端必备。加载之后，它会自动采用 Controller → Manager → Repository 的分层架构，每个层只做自己该做的事。

如果不加载这个 Skill，你可能得到的是一个把所有逻辑塞在一个函数里的"意大利面"代码。这个 Skill 的价值不是让你写得快，是让你的代码以后改得动。

### 5️⃣ `to-issues` —— 需求拆解

把一个大计划拆成可以独立开工的 Issue。我在做复杂项目的时候，先用 `brainstorm` 想方案，再用 `to-issues` 拆任务。

## A/B 对比：同一个需求，有 Skill 和没 Skill 天差地别

说得再多不如看代码。我拿一个真实需求来演示。

**需求**："用 Python 写一个用户注册的 API 接口，包含用户名、邮箱、密码三个字段，邮箱要校验格式，密码至少 8 位。"

### 🔴 没加载 Skill 的版本（代码有删节）

```python
from flask import Flask, request, jsonify
import re

app = Flask(__name__)

@app.route('/register', methods=['POST'])
def register():
    data = request.get_json()
    username = data.get('username')
    email = data.get('email')
    password = data.get('password')
    
    if not email or not re.match(r"[^@]+@[^@]+\.[^@]+", email):
        return jsonify({"error": "invalid email"})
    
    if not password or len(password) < 8:
        return jsonify({"error": "password too short"})
    
    # 存数据库...（省略）
    return jsonify({"msg": "ok"})
```

能用，但问题很明显：每个函数开头的 `data.get()` 重复了三次、错误信息不统一、没有类型定义、框架用了没人维护的 Flask。

### 🟢 加载 `python-api-endpoint-creator` + `python-best-practices` 的版本（代码有删节）

```python
# routers/user_router.py
from fastapi import APIRouter, Depends
from pydantic import BaseModel, EmailStr, Field
from services.user_service import UserService

router = APIRouter(prefix="/users", tags=["users"])

class RegisterRequest(BaseModel):
    username: str = Field(..., min_length=2, max_length=50)
    email: EmailStr
    password: str = Field(..., min_length=8, max_length=128)

@router.post("/register")
async def register(req: RegisterRequest, service: UserService = Depends()):
    """Register a new user account."""
    user = await service.create_user(req)
    return {"id": user.id, "username": user.username, "email": user.email}
```

区别立竿见影：Pydantic 模型统一管理输入校验、FastAPI 的 async/await、依赖注入（Depends）、docstring 注释、分层结构清晰。

**这不是"写法不同"的问题，是工程质量的代差。**

## 两个你必须知道的避坑规则

**规则1：同时加载的 Skill 别超过 3 个**

每个 Skill 都会消耗 AI 的"上下文预算"（你可以理解为 AI 的短期记忆力）。加载太多 Skill，AI 记不住你的项目细节，反而变笨。

我的经验：写代码时加载 1 个编程 Skill + 如果涉及测试就加 1 个测试 Skill。写作时只加载 `article-writing`。别贪多。

**规则2：不要同时加载冲突的 Skill**

比如 `python-best-practices` 和 `kotlin-best-practices` —— 同时加载会让 AI 搞混应该用哪套规范。写 Python 就只加载 Python 相关的，写 Kotlin 就只加载 Kotlin 的。

## Skills + 自定义 Agent = 真正的 AI 团队

2026 年 CodeBuddy 新增了自定义 Agent 功能，你可以创建专属于你的 AI 智能体。

最实用的玩法：给每个 Agent 预设不同的 Skills 组合，像一个团队里不同分工的成员：

- **代码审查员 Agent**：自动加载 `security-checklist` + `testing-strategies`
- **API 开发 Agent**：自动加载 `python-api-endpoint-creator` + `python-best-practices`
- **写作助理 Agent**：自动加载 `article-writing` + `brainstorm`

切换 Agent = 切换角色，不用每次都手动加载 Skill。这是入门到进阶的转折点——别急着学，但记住有这条路。
