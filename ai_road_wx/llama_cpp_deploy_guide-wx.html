1 为什么换 llama.cpp？

我用 Ollama 跑了三个月，一直觉得还行——直到有一次让模型分析一份 200 页的合同，等了 8 分钟。朋友说你换成 llama.cpp，同样的模型同样的机器，2 分钟出结果。

📌 3.1 CPU 编译（双平台）

克隆仓库：

# 务必包含子模块！
git clone --recurse-submodules https://github.com/ggml-org/llama.cpp.git
cd llama.cpp

⚠️ 如果已克隆但忘记 --recurse-submodules：
git submodule update --init --recursive

Linux CPU 编译：

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j$(nproc)

编译产物在 build/bin/ 目录下：llama-cli（命令行推理）、llama-server（HTTP 服务）、llama-quantize（量化工具）、llama-embedding（嵌入向量提取）、llama-perplexity（困惑度评估）

Windows CPU 编译：

⚠️ 必须在 "Developer PowerShell for VS 2022" 中执行！

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j $env:NUMBER_OF_PROCESSORS

编译产物在 build\bin\Release\ 目录下（.exe 后缀）。

· · ·

📌 3.2 CUDA GPU 加速编译

查询 GPU 计算能力：

nvidia-smi --query-gpu=compute_cap --format=csv,noheader
# 示例输出：8.9 → 架构代码为 "89"

常用架构代码速查：

RTX 2060/2070/2080 → 架构 75（Turing）
RTX 3060/3070/3080/3090 → 架构 86（Ampere）
RTX 4060/4070/4080/4090 → 架构 89（Ada Lovelace）
RTX 5070/5080/5090 → 架构 100（Blackwell）
A100 → 架构 80 · H100 → 架构 90

推荐：指定 GPU 架构优化编译（以 RTX 4090 为例）：

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DGGML_CUDA_F16=ON \
  -DGGML_CUDA_ARCHITECTURES="89" \
  -DBUILD_SHARED_LIBS=OFF

cmake --build build --config Release -j$(nproc)

参数说明：
· -DGGML_CUDA=ON — 启用 CUDA 后端
· -DGGML_CUDA_F16=ON — FP16 张量核心加速（RTX 20xx+ 支持）
· -DGGML_CUDA_ARCHITECTURES="89" — 强烈推荐，避免运行时崩溃
· -DBUILD_SHARED_LIBS=OFF — 静态二进制，可独立分发

验证 CUDA 是否启用：

成功标志（输出中应看到）：

llm_load_tensors: offloaded 32/33 layers to GPU
llm_load_tensors: VRAM used: 4782 MiB

如果看到 offloaded 0/33 layers，说明 CUDA 未生效，需要清理 build 目录重新编译。

· · ·

📌 3.3 其他 GPU 后端

Vulkan（AMD/Intel GPU，跨平台）
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_VULKAN=ON
cmake --build build --config Release -j$(nproc)

Metal（Apple Silicon / macOS）

HIP（AMD GPU，Linux）

📌 4.2 HuggingFace 模型转 GGUF

如果只有 safetensors/pytorch 格式的模型，需要先转换：

  --outtype f16

# 支持的输出类型：f32, f16, bf16, q8_0

📌 4.3 GGUF 模型量化

使用 llama-quantize 工具将 FP16 模型量化为更小的版本：

./build/bin/llama-quantize \
  ./models/model-f16.gguf \
  ./models/model-Q4_K_M.gguf \
  Q4_K_M

量化等级选择：

Q8_0 ~50% 体积 · 几乎无损 · 质量优先
Q6_K ~38% 体积 · 极高质量 · 质量优先
Q5_K_M ~33% 体积 · 高质量 · 推荐质量默认值
Q4_K_M ~25% 体积 · 入门首选，体积效果最均衡
Q4_K_S ~25% 体积 · 比 K_M 稍小
Q3_K_M ~19% 体积 · 显存紧张时可用
Q2_K ~13% 体积 · 极限压缩，质量明显下降

💡 建议：优先从 Q4_K_M 开始，质量不够升级到 Q5_K_M 或 Q6_K；显存不够降级到 Q3_K_M。

5 关键参数配置与启动命令

📌 5.1 核心参数速查表

模型加载参数：

-m / --model — 模型文件路径，如 -m ./models/qwen.gguf
--n-gpu-layers / -ngl — GPU 卸载层数，-1 为自动
--no-mmap — 禁用内存映射，低内存设备用
--mlock — 锁定模型到内存，防交换

上下文与性能参数：

--ctx-size / -c — 上下文窗口大小（Token 数），如 --ctx-size 8192
--threads / -t — CPU 推理线程数，如 -t 8
--batch-size / -b — 单批最大 Token 数，默认 2048
--flash-attn / -fa — 启用 Flash Attention

采样参数：

--temp 0.8 — 温度：0=贪心，0.7-1.0=平衡，>1=随机
--top-k 40 — Top-K 采样
--top-p 0.95 — 核采样（Nucleus）
--repeat-penalty 1.0 — 重复惩罚，1.1 为轻度

单轮对话：

./build/bin/llama-cli \

./build/bin/llama-cli \

6 常见报错排查

📌 编译阶段 Top 5

fatal error: ggml.h: No such file
→ 未拉取子模块：git submodule update --init --recursive

CMake Error: Could not find CMAKE_C_COMPILER
→ Linux: sudo apt install build-essential / Windows: 安装 VS Build Tools

CMAKE_CUDA_ARCHITECTURES must be non-empty
→ 添加 -DGGML_CUDA_ARCHITECTURES="89"（替换为你的架构）

undefined reference to cudaFree
→ 清理重建：rm -rf build && cmake -B build -DGGML_CUDA=ON ...

The CXX compiler identification is unknown（Windows）
→ 从 "Developer PowerShell for VS 2022" 启动

📌 运行时 Top 5

CUDA error: no kernel image is available
→ CUDA 架构不匹配，重新编译指定正确架构

offloaded 0/33 layers to GPU
→ CUDA 未正确链接，清理 build 目录重新编译

CUDA error: out of memory
→ 减少 --n-gpu-layers 数值，或使用更低量化等级

Segmentation fault (core dumped)
→ ① 检查 CUDA 架构匹配 ② 检查模型完整性 ③ 尝试纯 CPU 运行

模型输出乱码
→ 避免使用 CUDA 13.2！使用 12.x 或 13.0/13.1

7 性能优化建议

📌 GPU 推理优化

① 尽可能卸载所有层到 GPU：--n-gpu-layers 99 或 -1（自动）
② 启用 Flash Attention：--flash-attn，显著降低 KV Cache 显存占用
③ 指定 GPU 架构编译：-DGGML_CUDA_ARCHITECTURES="89"
④ 增大 batch size：--batch-size 4096（显存充足时）

📌 CPU 推理优化

① 线程数设为核心数（非超线程数）：--threads 8（8 核 CPU）
② 物理核心绑定（Linux）：--cpu-strict 1
③ 批处理线程分离：--threads-batch 16

📌 通用优化

① 合适的量化等级：Q4_K_M 是体积与效果的最佳平衡点
② 合理设置上下文窗口：8192-16384 对多数场景已足够
③ 锁定内存：--mlock 防止操作系统将模型页交换到磁盘
④ 使用 SSD 存放模型，减少首次加载时间
⑤ 生产环境固定版本，推荐稳定版（如 b9601）

9 llama.cpp vs Ollama 对比选型指南

看完上面的教程，你可能会有一个疑问："说了那么多，到底该用 llama.cpp 还是 Ollama？"这个问题直接关系到你后续的使用体验。

📌 9.1 一句话定位

Ollama — 开箱即用的 AI 应用，像装一个 App 一样简单，5 分钟跑起大模型
llama.cpp — 面向开发者的推理引擎，给你最大的控制权，但需要你愿意动手

打个比方：Ollama 像自动挡汽车，踩油门就走；llama.cpp 像手动挡赛车，起步要学，但弯道极限更高。

📌 9.2 多维度对比

安装与上手：

Ollama 安装包→双击→完成 · 零依赖 · 新手⭐⭐⭐⭐⭐
llama.cpp 免编译解压10分钟 / 源码编译30-60分钟 · 新手⭐⭐⭐/⭐⭐

结论：易用性上 Ollama 完胜，尤其适合 Windows 新手。

模型管理：

Ollama 统一管理、自动组织 · ollama pull 一行下载 · 内置搜索 · Tag 区分版本
llama.cpp 手动管理 · 去 HuggingFace 下载 · 文件名管理 · 完全自由

性能（2026 年 5 月 benchmark，RTX 4090，Llama 3.1 8B Q4_K_M）：

单请求吞吐量：Ollama ~170 tok/s vs llama.cpp ~186 tok/s（快约 9%）
Prompt 处理速度：Ollama ~3200 tok/s vs llama.cpp ~3550 tok/s（快约 11%）
显存占用 / 首次加载：基本一致

💡 说人话：对普通用户的日常使用来说，这个 9-11% 的差距几乎感知不到。除非你在做批处理、高并发、或对延迟极度敏感。

灵活性与可控性：

Ollama GPU 层数自动（黑盒）· 编译不可定制 · 仅 CUDA/Metal · 生态最丰富（130k+ Stars）
llama.cpp 精确到层 · 可指定 GPU 架构编译 · CUDA/Vulkan/Metal/HIP/SYCL 全覆盖 · 技术深度更深（75k+ Stars）

结论：llama.cpp 在灵活性和底层控制上远超 Ollama。开发者、需精细化调参、或跑 AMD/Intel 显卡，选 llama.cpp。

📌 9.3 性能实测

同一台机器（RTX 4090 24GB，64GB RAM），Qwen2.5-7B-Instruct-Q4_K_M：

Ollama ollama run qwen2.5:7b
→ 42.3 tok/s（生成），3.8s 首 token 延迟

📌 9.5 终极建议：两个都用

💡 事实上：Ollama 底层用的就是 llama.cpp 引擎。

它们是同一技术栈的不同封装层级——Ollama 封装了 llama.cpp 并套上易用外壳，llama.cpp 是更底层、更自由的原始引擎。

推荐使用策略：

📅 入门期（第 1-2 周） Ollama — 快速体验模型，建立基本认知
📅 进阶期（第 3-4 周） llama.cpp — 学编译、GPU 调优、理解推理参数
📅 稳定期（日常使用） 两者混用 — Ollama 对话，llama.cpp 定制任务
📅 开发者 llama.cpp 为主 — 接入自定义推理管线

具体分工：

日常聊天、写作、翻译 → 用 Ollama，省心省力

搭建团队共享 AI 服务 → 用 llama.cpp 的 llama-server，部署更灵活
