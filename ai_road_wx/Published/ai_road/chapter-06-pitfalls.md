# 第六章：避坑指南 —— 搭建 AI 团队最容易踩的 7 个误区

> **本章定位**：前面五章教你"怎么做对"。这一章告诉你"怎么做会错"——把我和身边朋友实战中踩过的坑、见过别人踩的坑，浓缩成 7 个最常见的误区。每个都标注了：坑的表现、为什么会掉进去、怎么爬出来。

---

## 引言：方法论教你怎么赢，避坑指南教你怎么不输

搭建 AI 团队这件事，难的不是"开始"，而是"开始之后"。大部分人会经历一个相同的曲线：

```
热情高涨 ──→ 疯狂堆工具 ──→ 产出没提升 ──→ 怀疑 AI 是不是没用 ──→ 放弃
```

这条曲线上的每一个转折点，都是一个可以提前避开的坑。

---

## 误区 1：盲目堆砌工具/模型，角色重复，流程混乱

### 表现

```
- 你的 AI 团队里：写作 Agent 有 3 个（分别用的 Claude、GPT、DeepSeek）
- 选题 Agent 和策略 Agent 输出高度重叠但名字不同
- 工作流里 Agent A 和 Agent B 的串行顺序是"随便放的"
- 每次执行前你都要想：到底该用哪个？
```

### 为什么会掉进去

典型的"FOMO 驱动决策"——看到新模型出来就加一个 Agent，看到别人用什么工具就跟着加，不是因为需要，而是因为"万一有用呢"。

### 怎么爬出来

**做一次"Agent 大扫除"**：

```
1. 列出你所有 Agent 的名字和职责
2. 对每对 Agent 问：如果删掉 A，B 能不能做 A 的事？
3. 能 → 合并；不能 → 保留
4. 目标：每个职责有且只有一个 Agent 负责
```

**工具精简原则**：

> 一个任务上，最好用的一个工具 > 三个"差不多"的工具。选一个主方案 + 一个备选（应对故障），就这两种。不是备胎越多越好。

## 误区 2：过度依赖 AI，完全放弃人工审核

### 表现

```
- "我让 AI 直接发文了，省得我自己看"
- 代码 Review 只看 AI 审查 Agent 的结论："🟢 通过"→ 直接 Merge
- 连续 2 周没看过 AI 产出的具体内容
- 读者在评论区指出"这篇文章的数据是错的"，你才发现
```

### 为什么会掉进去

AI 刚开始用的时候产出的质量很好（蜜月期效应）。你逐渐建立信任 → 减少审核频率 → 减少审核深度 → 完全放手。

每一环的信任都是合理的，但加起来就是一个危险的正反馈循环：**你审得越少，你就越不知道它在退步。**

### 怎么爬出来

**建立"最低审核标准"，不可妥协**：

| 场景 | 最低审核标准 | 理由 |
|------|-------------|------|
| 内容发布 | 人工通读全文至少 1 遍 | AI 的事实性错误在发布后修复成本极高 |
| 代码 Merge | 看懂核心逻辑 + 确认 Review 报告中 🔴 项已修复 | AI Reviewer 会漏，你的判断是最后防线 |
| 客户方案 | 人工通读 + 关键数据双人确认 | 发给客户的一次错误 = 丢一个客户 |
| 社交媒体回复 | AI 自动回复可以，但每天抽查 10% | 一次不当回复可能上热搜 |

**一个实用的自检问题**：

> "如果这篇文章/这段代码明天出了问题，我能跟别人解释我审过什么吗？"
>
> 如果能说出你的审核点和决策逻辑 → 审核足够。
> 如果说不出 → 你没审。

## 误区 3：追求"大模型万能"，忽略轻量化模型的分工价值

### 表现

```
- 所有任务都用 Claude 3.5 Sonnet："反正是最好的，为什么不用？"
- 渠道改写、数据格式化、标签生成——这些简单任务也在用大模型
- 月底一看 API 账单：¥1,200。算了下，60% 的费用花在了不需要 Sonnet 的任务上
- 本地部署：努力要把 70B 模型塞进 24GB 显存，跑出了 2 token/s 的幻灯片效果
```

### 为什么会掉进去

「最好的一定最划算」——这在 AI 领域不成立。大模型的价值在于复杂推理，在简单任务上它的"额外能力"是闲置的，但成本是照付的。

### 怎么爬出来

**给任务分级，匹配对应模型**：

```
任务复杂度          推荐模型           成本比（相对 Sonnet）
──────────────────────────────────────────────────────────
🟢 简单格式转换     Claude Haiku /     1/10
  · 长文→小红书版     GPT-4o-mini /
  · 数据→表格         Qwen2.5-7B
  · 标签生成

🟡 中等分析推理     Qwen2.5-14B /      1/3 ~ 1/2
  · Code Review     DeepSeek-V2
  · 测试用例生成
  · 竞品分析

🔴 复杂创作/决策    Claude Sonnet /    1×
  · 深度长文写作    GPT-4o
  · 策略分析
  · 客户方案定稿
```

**本地模型同理**：

- 编码主力用 Qwen2.5-Coder-14B Q5（质量优先）
- 文档/安全用 Qwen2.5-7B Q4（效率优先）
- 不要强行在 24GB 显存跑 70B——量化到 Q2 会变成傻子，不如用 32B 的 Q5

## 误区 4：不做资产沉淀，每次使用都重新写 Prompt

### 表现

```
- 每次开新选题，都要花 10 分钟"调一下 Prompt"
- 写作 Agent 三个月里换了 5 版 System Prompt，没有任何版本记录
- 上个月发现的一个好用的 Prompt 写法，这个月忘了，又在重试
- 你的 Prompt 散落在 Claude/ChatGPT/Dify/Cursor 四个地方，没有统一管理
```

### 为什么会掉进去

因为 Prompt 最初就是一两条指令，你觉得"没什么好管理的"。但它会生长——你每次调优加一句，慢慢就变成几百字的 System Prompt。等它长到你记不住的时候，管理成本已经很高了。

### 怎么爬出来

**已经在第五章（5.1 资产沉淀）中给了完整方案。这里再强调三条"今天就能做"的最低配版：**

```
1. 创建一个 Git 仓库叫 ai-team-prompts，把你所有 Agent 的 System Prompt 存进去
2. 用 CHANGELOG.md 记录每次修改（一句话就行："v1.2：加入多样性约束，解决选题同质化"）
3. 每个月回顾一次：哪个 Prompt 调了但没有效果？删掉改动，回退到上一个好用的版本
```

**一个反直觉的经验**：

> 你花在"调 Prompt"上的时间如果超过了你花在"审核 AI 产出"上的时间，说明你的 Prompt 管理出了问题。好的 Prompt 是稳定的——偶尔微调，不是每次重写。

## 误区 5：无视硬件限制，强行跑超高上下文、多模型并行导致崩溃

### 表现

```
- 在 Mac Mini 24GB 上同时加载了 Qwen2.5-Coder-14B + Code Review 模型 + 测试生成模型
- 运行时看到 Swap 占用 20GB，系统卡到鼠标都移不动
- "为什么本地模型这么慢？"——因为它一半的参数在 SSD 上跑
- 强行把 32000 上下文塞给 24GB 显卡，OOM 崩溃后归咎于"模型不行"
```

### 为什么会掉进去

两个认知偏差：
1. "统一内存 = 无限显存"——Mac 的统一内存可以当显存用，但不是没有上限
2. "上下文越大越好"——上下文窗口是显存的头号杀手，但大多数人只关注参数大小

### 怎么爬出来

**三条硬规则**（已在第五章 5.4 详述，此处提炼核心）：

```
规则 1：模型显存占用 ≤ 总显存的 70%
       留 30% 给上下文和系统开销。
       32GB 统一内存 → 模型最多占用 22GB

规则 2：上下文大小按需设置，不追求最大值
       代码审查：8192 tokens 足够（PR diff 通常不会超过）
       文档书写：4096 tokens 足够
       只有复杂创作才需要 16000+

规则 3：多 Agent 不做真正的"并行"
       除非你有双卡或多台机器，否则同一时间只跑 1 个重量模型。
       轻量模型（7B）可以和重量模型共存，但不要两个重量模型同时跑。
```

**一个快速诊断命令**（Mac）：

```bash
# 查看当前显存/内存压力
sudo memory_pressure

# 查看 Ollama 加载了哪些模型，占用多少
ollama ps
```

## 误区 6：照搬别人的 AI 角色，不结合自身业务定制

### 表现

```
- 看了某博主的文章，他用了"选题Agent + 写作Agent + 设计Agent"，
  你也原封不动搭了一套——但你是做 SaaS 开发的，不写内容
- 朋友说"客服 Agent 超好用"，你就加了一个——但你没有客户咨询量
- 团队里 8 个 Agent，3 个几乎没产出过有用的东西，但你不敢删，
  因为"别人都这么配的"
```

### 为什么会掉进去

AI 团队架构这个领域太新了，没有成熟的最佳实践可以参考。人的本能是从已有的成功案例里抄——但别人的成功案例是别人的业务、别人的工作流、别人的能力边界。**抄架构 = 抄答案，但你的考题跟他的不一样。**

### 怎么爬出来

**先做需求映射，再搭 Agent**：

```
Step 1：把你一周的工作拆成具体的任务
  例：写代码 30% / 写文档 15% / Code Review 10% /
       测试 10% / 开会 15% / 排期 10% / 客户沟通 10%

Step 2：标出哪些任务 AI 能做
  ✅ 写代码   ✅ 写文档   ✅ Code Review
  ✅ 测试     ✅ 排期     ❌ 开会（AI 不能替你开会）
                         ❓ 客户沟通（AI 辅助方案撰写，不能替代沟通）

Step 3：为每个 ✅ 任务设计 1 个 Agent
  你的 Agent 清单：编码 Agent / 文档 Agent / 审查 Agent / 测试 Agent / 排期 Agent

Step 4：检查是否有重叠 → 合并
  文档 Agent 和 排期 Agent 工作量都较小？→ 合并为运营 Agent

最终：4 个 Agent，每个都有明确且高频的工作。
```

**关键心法**：

> 不是"别人有什么 Agent 我就要有什么 Agent"，而是"我的时间花在哪，Agent 就替我在哪出力"。
> 如果一个 Agent 一周只被用到一次，删掉。用的时候手动调一次 AI 就行了。

## 误区 7：只搭建不迭代，团队长期一成不变，跟不上 AI 更新

### 表现

```
- 半年前搭的 AI 团队，到现在还是同一套 Prompt、同一批模型
- Claude 4 出了但还在用 Claude 3——"懒得迁移"
- 工作流还是最初版本的 Make.com 蓝图，中间加了 5 个补丁但从来没重构过
- 你会发现文章质量"好像不如刚搭的时候好了"——但其实不是,
  是你的写作能力进步了，而 AI 的输出水平停留在了半年前
```

### 为什么会掉进去

"跑得挺好就别动"的心态——这在一个稳定系统中是正确的，但 AI 工具链不是一个稳定系统。Model 每季度更新，工具每月上新功能，你的业务需求在变化，你自己的能力也在变化。**一个不迭代的 AI 团队是一个匀速后退的团队。**

### 怎么爬出来

**建立"迭代日历"，而不是"想起来再改"**：

```
每周（5分钟）
□ 扫一眼 Agent 产出，有没有明显退步的迹象
□ 看一条 AI 领域新闻（模型更新/工具上新）

每月（30分钟）
□ 跑一次 Agent 质量基准测试（用固定测试用例对比输出）
□ 清理一次知识库（去重、过期标记）
□ 回顾 Prompt CHANGELOG，删掉上个月被证明无效的改动

每季度（2小时）
□ 模型选型评估：有没有性价比更高的新模型可以替换
□ 工作流重构：有没有更简洁的方式完成同样的任务
□ Agent 大扫除：删掉/合并没用或低效的 Agent
□ 能力对齐：你进步了（写得更好/代码更复杂），Agent 的 Prompt 需要升级
```

**一个保持迭代动力的技巧**：

> 不要把迭代当成"有问题才做的事"。把它当成"AI 团队是我的一个产品，我在持续迭代我的产品"。
>
> 每周看到一个新模型/新工具/新用法，问自己一句话：**"这能让我的 AI 团队变好 1% 吗？"** 如果能，试一下。如果不能，无视。持续 1% 的改进，一年是 37 倍。

## 本章小结

7 个误区总结成一张清单，贴在电脑旁边：

```
□ 1. 我的 Agent 有没有重复的？（每个职责只一个）
□ 2. 我最近一次认真审核 AI 产出是什么时候？
□ 3. 简单任务还在用大模型吗？换个便宜的能省多少？
□ 4. 我的 Prompt 存在哪里？上次改是什么时候？
□ 5. 同时跑了几个模型？显存还够吗？
□ 6. 我的每个 Agent 都有明确的使用场景吗？还是有"别人都装"的？
□ 7. 我的 AI 团队更新日志从几月开始是空的？
```

这 7 个误区每一个都不是致命伤，但叠加在一起会让你的 AI 团队从"增益"变成"负担"。避坑不是让你变成完美主义者，而是让这份投入持续产生回报。
