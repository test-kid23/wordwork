1 RAG到底是什么：一个比方说完

不知道大家有没有过这种经历——打开 ChatGPT 问一个问题，它回答得头头是道，但仔细一看，全是编的。

我遇到过最离谱的一次是问它"我们公司去年Q3的营收数据"，它给我列了一串带小数点的数字，格式工整、逻辑自洽，看起来比我司财务做的还专业。问题是——我根本没说我是哪家公司的。

这就是大模型的根本问题：它是一个闭卷考生。 训练完之后，脑子里只有训练数据灌进去的那些东西。训练数据之外的事——它不知道，但它不会说"我不知道"，而是硬着头皮编。

RAG 解决的就是这个问题。

RAG 四个字母拆开：Retrieval-Augmented Generation，检索增强生成。 听起来唬人，说白了就一件事：大模型回答问题之前，先去翻资料。

还是考试那个比方：

🔹 纯大模型 = 闭卷考试。全靠记忆，记得住就答，记不住就编。
🔹 RAG = 开卷考试。给一堆参考资料，先查、再答。答出来的东西有出处、能溯源。

一句话定义：RAG 就是在用户问问题之后、大模型回答之前，先到知识库里检索相关内容，把检索结果和问题一起塞给大模型，让它"参考着回答"。

拆开就三个动作：

① 检索（Retrieval）
从知识库里翻出跟问题相关的资料

② 增强（Augmented）
把翻出来的资料拼到问题里，让大模型能看到

③ 生成（Generation）
大模型看着问题+资料，给出有依据的回答

这个定义不花哨，但它划了一条硬线：AI 回答有没有事实依据，能不能查到来源。

跟"直接喂资料"的区别：有人会问——"那把资料复制粘贴到对话框里，不也一样吗？"不一样。复制粘贴是手动翻书，上限是"人能翻几页"。RAG 是从百万份文档里自动翻出最相关的那三两段——人做不到这个量级。RAG 不是替代"喂资料"，是让喂资料的规模从"几页"变成"几万页"。

跟"微调/Fine-tuning"的区别：微调是把新知识"背下来"——相当于让考生重新学一遍新教材，学了就记住了但更新教材得从头再学。RAG 是把资料放旁边"随时查"——教材更新了直接换一本就行。微调改的是模型参数，RAG 改的是检索库。哪个好？不是取代关系，是互补。微调适合"风格和格式"（让模型学会某种表达方式），RAG 适合"事实和知识"（让模型回答时引到对的内容）。打个比方——微调是让厨师学新菜系，RAG 是给厨师一本菜谱让他照着做。

2 为什么需要RAG：三个绕不过去的死穴

RAG 被全行业追捧，不是因为"有技术含量"，是因为不搞 RAG，大模型有三个死穴根本绕不过去。每个死穴都是实际落地时会撞上的墙。

📌 死穴1：知识截止，训练完就是"历史人物"

大模型训练一次动辄几个月、成本上亿。GPT-4 的知识截止在 2023 年底（不同版本不同），Claude 也是类似的时间点。训练之后发生的事——新一代操作系统发布了、某个库的 API 不兼容了、某家公司倒闭了——它通通不知道。

我还记得 2024 年有段时间，所有大模型都在教人用"已被弃用的 LangChain 旧版 API"，因为训练数据里只有旧版文档。每个照着跑的开发者都在踩坑，且踩完还不知道为什么——模型回答得太自信了，根本看不出"这是两年前的写法"。

RAG 解决这个问题的方式很简单：不是让模型重新训练以"记住"新信息，而是让模型每次回答前先去"查"最新资料。 训练数据不用动，把新的文档放进检索库就行。

📌 死穴2：私有数据盲区，不知道"我们公司的事"

这是企业场景最致命的一个。GPT-4 再强，不知道我们公司的报销流程怎么走、不清楚我们这个产品的内部定价策略、不明白某个客户的合同条款写了什么。

但真正有价值的 AI 应用，80% 的问答都跟私有数据有关——"这个项目的排期是什么""上个月的销售数据总结一下""客户A的合同里关于违约条款怎么写的"。

没有 RAG，这些问题要么回答不了（大模型不知道），要么瞎编一个（大模型硬着头皮编）。有了 RAG，把公司内部文档向量化丢进检索库，大模型每次回答都从里面查——私有数据盲区的问题就解了。

RAG 本质上干了一件事：把大模型的"通用智能"和企业的"私有数据"接上了。

📌 死穴3：幻觉编造，不知道就瞎编

这是三个死穴里最危险的一个。前两个是"答不出来"，这一个是"答一个错的但看起来像对的"。

大模型的底层工作机制是"预测下一个词"，不是"判断对错"。当一个问题的答案不在训练数据里，大模型不会停下来承认"不会"，而是基于概率硬造一个"看起来合理的"——语法正确、逻辑自洽、数字精确，但全是假的。

我见过最经典的一次幻觉：让 GPT-4 引用一篇论文的结论，它给出了完整的作者名、论文标题、发表年份、期刊名称、甚至页面范围——看起来比真的还真。逐项核查，这篇论文根本不存在。作者名是从相关领域学者里拼出来的，期刊名是真的期刊，页码格式无可挑剔——但整篇论文是虚构的。

RAG 是怎么治这个的：不让模型"凭记忆回答"，强迫它"依据资料回答"。 资料里有的就答，资料里没有的就别编。检索到的文档块就是这个回答的"底稿"，追问来源时能指出来哪一段、哪一行。

这不是消除幻觉——RAG 不会消除幻觉，模型仍然可能在"理解检索内容"这一步出错。但 RAG 把幻觉从"漫天胡编"缩到了"阅读理解偏差"——后者至少有个锚点可以核查。

3 RAG怎么跑起来的：四步流水线

理解了"为什么需要"，这一章拆"怎么跑"。RAG 的核心不是魔法，是一条四步流水线。

📌 第一步：数据准备——把文档变成机器能搜的

首先得有一套"知识库"。可能是公司内部 Wiki 上的几百页文档、一个产品手册的 PDF、一批客服对话记录、或者某个开源项目的所有 issue。

这些文档大模型"看"不懂——它只能处理 token。所以第一步是把文档转换成向量。

流程是这样的：

① 文档切块（Chunking）
把一个长文档切成一块一块的小段。比如一篇 5000 字的文章，按 500 字一段切，切成 10 块。切多大是门学问——太小了上下文不够，太大了检索不准。实践中 300-800 token 一块比较常见。

② 向量化（Embedding）
每一块用嵌入模型（Embedding Model）转成一个高维向量——一串数字，比如 1536 个浮点数。这个向量的神奇之处在于：语义相近的文本，向量距离也近。 "感冒发烧怎么办"和"流鼻涕吃什么药"生成的向量会靠得很近，尽管字面上没几个一样的词。

③ 存向量库
把所有文档块的向量存进向量数据库。

这一步做完之后，知识库已经可以检索了——它不再是一堆人类读的文档，而是一个"语义搜索系统"。

📌 第二步：检索——找到最相关的那两三块

用户问了一个问题，这个问题的处理路径：

1. 用户问题向量化：用同一个嵌入模型把用户的问题转成向量。
2. 相似度检索：在向量库里找跟问题向量"距离最近"的 top-k 个文档块——通常 k 取 3 到 10 之间。
3. 返回文档块：把检索到的几个文档块的原始文本取出来。

比如用户问："感冒了吃什么药好得快？"向量库检索后可能返回三块内容——一块是"感冒药分类与选择"，一块是"普通感冒的自然疗法"，一块是"何时需要就医的判断标准"。这三块都是相关的，但角度不同——这正是 RAG 的价值：不是找"最像问题"的一段，是找"能从不同角度回答"的多段。

这个检索过程快得离谱——毫秒级。因为不是在扫描全文，是在做向量距离计算。

📌 第三步：增强——把查到的资料拼进问题

这是 RAG 三个字母里"A"的部分，也是最容易被人忽略但最关键的一步。

检索返回 3 个文档块，每个块 500 字，一共 1500 字。直接把这 1500 字和用户问题一股脑塞给大模型？效果很烂。

增强这一步要做的：

🔹 排序：把最相关的放最前面，次相关的往后排
🔹 去重：两块内容如果高度重叠（比如两段都在讲同一个药），只保留信息最全的一段
🔹 重组：给每个文档块加上来源标记，让模型回答时能引用出处
🔹 构建 Prompt：组合成类似这样的结构——

请根据以下参考信息回答问题。如果参考信息中没有相关内容，请明确说明。

参考信息：
[来源：药品说明书] 布洛芬适用于...（检索块1）
[来源：医疗指南] 普通感冒多为自限性疾病...（检索块2）
[来源：患者手册] 以下情况建议及时就医...（检索块3）

问题：感冒了吃什么药好得快？

这一步的好坏，直接决定了 RAG 的回答质量。检索到的资料再好，Prompt 组织得烂，大模型照样跑偏。

📌 第四步：生成——大模型"看着资料"回答

把组织好的 Prompt 发给大模型，大模型看着"参考资料"回答用户问题。

这时候大模型的行为跟之前完全不同：

🔹 没有 RAG：大脑里搜索训练数据里跟"感冒药"有关的知识，拼一个回答——可能拼对了，也可能拼到伪科学内容。
🔹 有 RAG：一字一句对着检索出来的文档块回答，回答的每一句都能在检索块里找到依据。

差距有多大：没用 RAG 时回答"布洛芬和泰诺有什么区别"，大模型可能从训练数据里的各种帖子、论文、论坛讨论中拼凑——质量取决于训练数据的质量。用了 RAG 后，大模型是从你指定的权威药品说明书中提取对比——质量取决于你存入检索库的资料质量。

💡 关键认知：RAG 把 "AI 回答质量" 从 "模型训练数据的质量" 转移到了 "你的知识库的质量"。能不能管好知识库，决定了 AI 给的答案靠不靠谱。能力控制权回到了自己手里。

📌 一个完整的请求链路，花 2 秒

用户问："公司年假怎么算？"
  ↓ (100ms)
Embedding 模型把问题转成向量
  ↓ (50ms)
向量库检索到3个文档块：
  块1: 年假管理规定（HR制度文档）
  块2: 年假计算示例（HR培训材料）
  块3: 年假特殊情况处理（HR FAQ）
  ↓ (200ms)
构建 Prompt：参考资料+问题
  ↓ (1.5s)
大模型生成回答

从提问到拿到答案，整个过程大约 2 秒——比直接问大模型多了检索的几百毫秒，但换来了"回答有出处"这个质的飞跃。

4 RAG的几个关键变体

基础 RAG（上面讲的四步流水线）够用 80% 的场景。但实际工程中，根据不同需求演化出了几个重要变体。这里不讲论文，讲实践中真实的用法。

📌 变体1：基础RAG（Naive RAG）

就是前面讲的四步。一次检索、一次生成。简单直接，适合大多数文档问答场景。

优点：快、简单、容易理解。缺点：检索效果完全取决于 Embedding 模型和文档切块质量，搜索能力单一（纯向量相似度）。

📌 变体2：多路召回（Hybrid Search）

基础 RAG 只靠向量相似度检索。向量检索强在"语义理解"——"感冒"能搜到"流感"，"裁员"能搜到"人员优化"。但弱在"精确匹配"——搜"合同编号 CT-2024-0887"，向量检索可能找歪，因为相邻编号的向量可能也很近。

多路召回的做法：同时跑两条搜索线——

🔹 向量搜索线：语义搜索，用 Embedding 找"意思相近"的
🔹 关键词搜索线：精确搜索，用 BM25 或类似算法找"字面匹配"的

两边结果合并、去重、重排序，再给到大模型。这种做法在企业场景里特别实用——内部文档里充斥着精确编号、产品代码、人名地名，光靠向量搜索根本搜不准。

📌 变体3：Agentic RAG

基础 RAG 是"不管问什么都先检索一次"。Agentic RAG 是"Agent 先判断需不需要检索、检索什么、检索完够不够、不够再搜"。

举个例子：用户问"对比一下我们Q3和Q4的销售数据"。

🔹 基础 RAG 的做法：把问题向量化→在知识库里找"销售数据"相关的文档→拿回来→让大模型回答。结果可能搜到了Q3的数据但没搜到Q4的，或者搜到了销售数据但不知道是哪个季度的。
🔹 Agentic RAG 的做法：Agent 拿到问题后自己规划——先搜 Q3 销售数据→搜到了→再搜 Q4 销售数据→也搜到了→两个放一起比较→不够？再搜一下"销售口径定义"→汇总回答。

Agentic RAG 把"检索几次、检索什么、什么时候停"的决策权交给了 Agent 自己。这种方式更适合复杂问题，但延迟更高、成本也更高——因为涉及多次 LLM 调用和多次检索。

📌 变体4：GraphRAG

这是 2024 年中微软提出后迅速火起来的一个方向。前面三种 RAG 变体，本质上都是"从文档中找跟问题最像的几段"——匹配的是文本相似度。

但很多问题需要的不是"跟问题相似的文本"，而是"知识之间的关系"。比如问"张三的上级的上级是谁"——这不是一个相似度搜索问题，这是一个图谱查询问题。

GraphRAG 的思路：在传统向量检索之上，再建一层知识图谱。 把文档里的实体（人、公司、产品、事件）和关系（属于、汇报给、产生于）抽取出来，构成一张图。回答问题时，既搜向量库（找相似文本），又查知识图谱（找实体关系），然后把两边的结果合在一起给大模型。

比如问"过去一年我们团队出了多少次 P0 事故"——传统 RAG 可能搜到一堆包含"P0"关键词的文档块，但没法跨文档汇总计数。GraphRAG 的做法是从图谱里查出"我的团队"有哪些人、"P0 事故"关联了哪些事件、这些事件是否发生在过去一年——结构化的答案。

GraphRAG 的代价很明显：建知识图谱比向量化文档得多花 10 倍的工程投入。它不是"替换基础 RAG"，而是"基础 RAG 搞不定关系型问题时的补充方案"。目前属于前沿方向，中小团队暂时没必要碰。

💡 四个变体一句话总结：基础 RAG 够用大多数场景，多路召回补精确搜索短板，Agentic RAG 让检索更灵活但成本更高，GraphRAG 解决关系型问题但工程投入大。

5 RAG不是万能的：三个最常见的坑

前面写的都是 RAG 能干什么、怎么干。这章讲它经常在什么地方翻车。这些坑不是理论推演，是真实落地时会撞上的。

📌 坑1：检索不准——明明有答案，就是搜不到

这是 RAG 最高发的故障。知识库里明明有一段完美回答了用户的问题，但检索这一步没搜到，大模型拿到的全是"不相关但长得很像"的资料，回答自然跑偏。

为什么搜不到？几个常见原因：

嵌入模型选错了。 向量检索的核心是 Embedding 模型——它决定了"什么是相似的"。英文模型搜中文文档基本无效，通用模型搜专业领域（医疗、法律、工程）准确率跳水。我自己踩过这个坑：用 OpenAI 的 text-embedding-ada-002 检索中文技术文档，召回率惨不忍睹。换了 BGE 中文模型后改善明显。把"相似"的定义交给一个通用模型，本身就是一件不靠谱的事。

文档切块切烂了。 切太小（200 token）——一段话被裁成三截，每截单独看都像说了什么但又不完整，语义向量天然残缺。切太大（2000 token）——一段里塞了五个主题，向量代表的是"平均语义"，搜什么都不对。实践中一般 500-800 token 一个块，且最好按自然段落切而不是机械按长度切。

用户问法跟文档写法不一样。 用户问"怎么退钱"，文档里写的是"退款流程说明"。向量搜索理论上能跨表达方式理解语义——但实际上 Embedding 模型对口语化查询和专业文档之间的语义鸿沟，处理得并不好。解决方式：在检索前做查询改写（Query Rewriting）——把用户的自然语言问题翻译成更接近文档表达方式的查询语句。

📌 坑2：上下文太长——搜到的太多，把答案淹了

检索返回 10 个块，每个 500 字，5000 字塞进 Prompt——再加上用户问题、系统指令、对话历史，轻松过万 token。

结果是什么？大模型得到的上下文里，"关键信息"被"大量相关信息但不重要"淹没了。大模型不是不知道答案——是答案被噪声包围，找不到重点。

典型表现：大模型开始"平均"所有检索结果，而不是聚焦最相关的——生成出一段"各方面都沾了一点但什么都没说清楚"的回复。

解决思路不是"少搜几个块"。有时候搜少了，关键信息刚好不在。更好的做法：

🔹 重排序（Re-ranking）：检索后用更高质量的重排序模型把 top-k 个结果重新打分排序，把真正相关的顶到最前面
🔹 压缩检索结果：对每个检索到的块做摘要压缩，只保留直接回答问题的关键句
🔹 分层策略：先做个粗检索（多拿一些），再用重排序做精筛（留最相关的 3-5 个）

📌 坑3：拆文档失误——把重要的上下文切断了

文档切块时按固定长度一刀切，最容易出的问题：一段话被从中间切开。

比如保险条款里的一句："若被保险人在保险期间内因意外伤害导致身故，保险公司按保险金额给付身故保险金。但以下情况除外——"——切块刚好在"但以下情况除外"后面切断，后半段的"除外条款"被切到另一个块里去了。

检索时可能只搜到前半段，大模型拿着"按保险金额给付身故保险金"这段话回答"保险公司赔"——而真正的答案在隔壁切块里，写的是"但在酒后驾驶、无证驾驶等情况下免责"。

这个坑的解法：

🔹 重叠切块（Overlapping Chunking）：切块时让相邻块之间有 10-20% 的内容重叠，保证边界处的上下文不丢失。比如按 500 token 一块切，滑动步长设 400 token，每块跟前一块重叠 100 token。
🔹 父子块索引（Parent-Child Indexing）：检索时用小块（提高搜索精度），但返回给大模型时把小块所在的"父块"（更大的上下文窗口）一起带上。
🔹 结构化切块：根据文档类型用不同策略——Markdown 按标题切、代码按函数切、法律合同按条款切。比一刀切的机械方式效果好很多，但需要针对每种文档类型写专门的切块逻辑。

6 什么时候该用RAG，什么时候不该用

RAG 不是银弹。这章给一个实用决策框架，帮大家判断一个场景该不该上 RAG。

📌 该用 RAG 的信号

信号1：知识量大到"靠人喂"不现实。

Prompt 里塞一份文档叫"手动喂资料"，塞十份文档叫"Prompt 塞不下了"。当知识的总量超过大模型上下文窗口（即使是 200K token 的长窗口模型，塞满之后回答质量也有明显下降），就该上 RAG 了。

粗暴判断标准：如果知识量多到一个人半天内看不完，该上 RAG。

信号2：知识经常更新，不能"今天训完明天作废"。

文档每天都在变——公司政策更新、产品新版本发布、法规修订、FAQ 每周新增。微调模型要重新训练、重新部署，RAG 只要把新文档放进向量库就行，整个更新过程可以是分钟级的。

信号3：回答需要溯源——"谁说的""哪一页写的"。

这是 RAG 最核心的价值之一。没有 RAG，大模型的回答是"基于训练数据的综合理解"，追问出处只能得到"根据我的知识……"——其实编的。有 RAG，每个回答都能定位到具体的文档块。"这个结论来自产品手册 v3.2 第 7 页"——这种级别的溯源，只有 RAG 能给。

📌 不该用 RAG 的信号

信号1：数据量极小。

只有三份文档、不到一万字。直接塞进 Prompt（或者用 System Prompt 写死）比搭一套 RAG 流水线快得多。RAG 的最小可行投入是"搭 Embedding 流水线+选向量库+调检索参数+写 Prompt 模板+持续维护知识库"——对极少量数据来说，过度工程。

信号2：场景固定，问题类型可穷举。

比如一个内部工具只有三种功能——查排期、查预算、查负责人。所有可能的问题都能用 if-else + SQL 查询解决，不需要"语义理解"来匹配问题到文档。RAG 解决的是"问题不可穷举、答案藏在非结构化文档里"的场景。

信号3：对延迟要求极高，等不起检索的几百毫秒。

RAG 至少比直接调用 LLM 多 200-500ms 的检索延迟——加了重排序更多。如果场景是"实时对话，每轮 500ms 内必须返回"，且用缓存能覆盖大部分问题，RAG 的投入回报不成正比。但注意：1000ms 以内的延迟对绝大多数用户而言是无感的，这个信号只适用于极端实时场景。

📌 一个要不要上 RAG 的决策流水线

遇到一个场景，按这个顺序问自己：

① 知识能不能塞进 Prompt？→ 能 → 不用 RAG，直接塞。

② 知识是不是经常变？→ 是 → 用 RAG。

③ 回答需不需要溯源？→ 需要 → 用 RAG。

④ 知识量大不大、非结构化文档多不多？→ 大、多 → 用 RAG。

⑤ 有没有团队能维护 RAG 的知识库？→ 没有 → 先别上，找更轻的方案。

⚠️ 经验之谈：最后一条最容易忽略。RAG 不是搭完就永远好用——知识库要持续更新（新文档不断加进来）、检索质量要持续调优（发现搜不准就调 Embedding 模型、调切块策略、调 Prompt 模板）、过时文档要清理。没有人管知识库的 RAG 系统，三个月后就退化成一个"搜不准还要硬编"的劣化版 AI。

7 一个纸上RAG例子：帮你查保险条款

前面六章把"RAG 是什么、为什么、怎么跑、有哪些坑"全讲完了。这章不写代码，用一个完整的具体场景，把四步流水线跑一遍。看完这个例子，RAG 的整条链路就彻底清楚了。

📌 场景设定

我们把知识库设定为一份综合医疗保险的条款文档，大概 50 页 PDF。里面包含了门诊报销规则、住院报销规则、免责条款、理赔流程、等待期规定等等。为了方便讲，假设这个条款文档已经被切成了 83 个文档块，每个块大约 400-500 字，存进了向量数据库。

现在来了一个问题——一个买了这份保险的用户问：

"我上周感冒了，去医院看了门诊，开了药，花了 380 块。这个能报销吗？能报多少？"

我们来看 RAG 是怎么一步步回答这个问题的。

📌 第一步：数据准备（已经完成）

假设条款已经做了切块和向量化。为了说明"好的切块 vs 差的切块"的区别，先展示两种切法：

差的切法（机械按 500 字一刀切）：

[块 #12]
第三条 门诊医疗保障
被保险人在保险期间内因疾病在指定医院接受门诊治疗的，本公司对每次门诊发生的、符合当地社会基本医疗保险规定的医疗费用，在扣除免赔额 100 元后，按 80% 的比例给付门诊医疗保险金。每次门诊给付限额为 500 元，每个保险年度内门诊给付累计限额为 3000 元。
以下情况不在门诊医疗保障范围内：（1）非指定医院就诊...
—— 切断了，后面是另一个块 ——

[块 #13]
（2）未持医保卡结算的就诊费用；（3）美容、整形、减肥类医疗服务；（4）与本次疾病无直接关联的体检费用。

好的切法（按条款语义切）：

[块 #12]
第三条 门诊医疗保障
被保险人在保险期间内因疾病在指定医院接受门诊治疗的，本公司对每次门诊发生的、符合当地社会基本医疗保险规定的医疗费用，在扣除免赔额 100 元后，按 80% 的比例给付门诊医疗保险金。每次门诊给付限额为 500 元，每个保险年度内门诊给付累计限额为 3000 元。以下情况不在门诊医疗保障范围内：（1）非指定医院就诊；（2）未持医保卡结算的就诊费用；（3）美容、整形、减肥类医疗服务；（4）与本次疾病无直接关联的体检费用。

差切法把一条完整的理赔规则劈成两半，检索可能只搜到前半段、没搜到后半段的免责条款——这就会导致错误的"能赔"回答。好的切法保证了一条完整规则在同一块里。

📌 第二步：检索

用户问题："我上周感冒了，去医院看了门诊，开了药，花了 380 块。这个能报销吗？能报多少？"

Embedding 模型把这个问题转成向量，在 83 个文档块的向量库里做相似度搜索。与"感冒看门诊花了钱能不能报销"在语义上最相关的几块，假设检索结果如下：

排名 #1 — 块 #12，相似度 0.92
内容：门诊报销规则——免赔额100元、80%比例、单次限额500元

排名 #2 — 块 #7，相似度 0.85
内容：指定医院列表和就诊要求

排名 #3 — 块 #15，相似度 0.81
内容：等待期规定——投保后30天内就医不赔

排名 #4 — 块 #22，相似度 0.78
内容：理赔流程和所需材料

top 取 4，把这四个块的内容拿出来。

📌 第三步：增强

把四个块的内容拼进 Prompt，加上来源标记：

请根据以下参考信息回答问题。如果参考信息中没有足够信息，请明确说明缺失了什么，不要编造。

参考信息：
[来源：保险条款 第3条] 被保险人在保险期间内因疾病在指定医院接受门诊治疗的，本公司对每次门诊发生的、符合当地社会基本医疗保险规定的医疗费用，在扣除免赔额100元后，按80%的比例给付门诊医疗保险金。每次门诊给付限额为500元...

[来源：保险条款 第2条] 指定医院列表如下：...（医院名单）

[来源：保险条款 第4条] 等待期：自保险合同生效之日起30日内，被保险人因疾病发生的医疗费用，本公司不承担保险责任。

[来源：保险条款 第8条] 理赔需提供：身份证复印件、医疗费用发票原件、门诊病历...

问题：我上周感冒了，去医院看了门诊，花了380块。这个能报销吗？能报多少？

📌 第四步：生成

大模型拿到这个 Prompt，给出的回答：

能不能报销：取决于以下几个条件是否同时满足——

1. 等待期已过：如果这份保险生效已满 30 天，感冒门诊在保障范围内。如果还在 30 天等待期内，本次不赔。

2. 去的是指定医院：就诊的医院必须在保险条款指定的医院列表中。如果是在非指定医院看的，不赔。

3. 持医保卡结算：未持医保卡结算的费用不在保障范围内。

能报多少（假设以上条件都满足）：

· 总花费：380 元
· 扣除免赔额 100 元：380 - 100 = 280 元
· 按 80% 报销：280 × 80% = 224 元
· 单次限额 500 元，224 元未超限，不受影响

预计报销金额：224 元。

理赔需要准备：身份证复印件、医疗费用发票原件、门诊病历。

以上分析基于保险条款第3条、第2条、第4条、第8条。如条款有更新或存在特殊约定，以最新正式保单为准。

📌 这个例子说明了什么

用户只问了一句话——"感冒花 380 块能报销吗"。RAG 的四步流水线自动完成了：

🔹 在 50 页条款里找到了"门诊报销规则"这一页（检索）
🔹 同时还找到了"指定医院""等待期""理赔材料"这些用户没问但回答必须考虑的约束条件（检索的多维度覆盖）
🔹 大模型不只是复读条款文字，而是根据 380 这个具体数字做了计算：380 - 100 = 280，280 × 80% = 224（理解+应用规则）
🔹 每个结论都能追溯到条款具体条款号（溯源）
🔹 不确定的地方（是否在等待期内、是否在指定医院）没有硬编，而是如实列出条件让用户自查（不编造）

💡 这就是 RAG 的完整运行：从用户提问到有据可查的回答，2 秒。

8 做RAG常用工具速查

前面七章讲完了原理和流程。这章给一个工具速查——做 RAG 需要哪些组件，每个组件有什么选择，怎么搭配。

注意：这里不是"最好用的是哪个"——工具没有最好，只有适不适合当前阶段。按"这个工具擅长什么、不擅长什么"来写，给两套组合方案。

📌 向量数据库

这是 RAG 的存储引擎。存文档块向量、做相似度检索。选哪个主要看数据量和部署偏好。

Chroma —— 最轻量的向量库，Python 几行代码就能跑
适合：原型验证、学习 RAG、数据量 < 10 万块

Milvus —— 国内最成熟的分布式向量库，性能强
适合：生产环境、数据量大、需要高并发

Qdrant —— Rust 写的，性能好，API 设计干净
适合：中型项目，想要性能又不想部署太复杂

Pinecone —— 全托管云向量库，不用自己部署
适合：不想管运维的团队，直接用 SaaS

Weaviate —— 向量库+关键词搜索原生一体
适合：需要多路召回又不想搭两套系统的

Elasticsearch —— 老牌搜索引擎，8.0 加了向量支持
适合：已有 ES 基础设施的团队，加向量插件即可

💡 怎么选：
· 刚学 RAG → Chroma（零配置，5 行代码）
· 有正经项目要上线 → Milvus 或 Qdrant
· 不想管服务器 → Pinecone（贵但省心）
· 已有 Elasticsearch → 别另起炉灶，直接开向量插件

📌 嵌入模型（Embedding Model）

这是 RAG 检索质量的决定性因素。选什么嵌入模型，基本决定了"能不能搜到对的东西"。

OpenAI text-embedding-3-small —— 512/1536 维，英文最强，中文还行
适合：英文为主的场景

BGE-M3（BAAI） —— 1024 维，中文表现极好，支持多语言
适合：中文场景首选，开源免费

BGE-large-zh —— 1024 维，纯中文模型
适合：只做中文的，比 BGE-M3 更专注

Jina embeddings v3 —— 1024 维，多语言，擅长长文本
适合：文档块较长（>1000 token）的场景

Cohere Embed v3 —— 1024 维，分类和聚类表现突出
适合：需要区分不同类型文档（如合同 vs 手册）

💡 选模型的三条原则：
1. 中文场景直接用 BGE——OpenAI 的嵌入模型对中文语义的捕捉不如 BGE，这是实测结论。
2. 除非有明确理由，别频繁换嵌入模型——每次换都要全部重新向量化，成本不低。
3. 向量维度不是越高越好——3072 维比 1024 维多存三倍数据，检索也慢。中文场景 1024 维完全够用。

📌 RAG 框架

框架帮你把"切块→向量化→检索→Prompt组装→调用LLM"这条流水线写好了，不用从零撸。

LlamaIndex —— 专注数据索引和检索，RAG 框架里最专业的
适合：想把检索这步做到极致的人，入门门槛中等

LangChain —— 通用 LLM 应用框架，RAG 只是它的一部分
适合：项目里不止 RAG，还有 Agent/Chain 等，门槛中高

Dify —— 低代码 AI 应用平台，拖拽搭 RAG
适合：不想写代码的人，快速验证，门槛低

RAGFlow —— 国产开源，深度文档理解+可视化编排
适合：中文文档处理，尤其是复杂格式 PDF，门槛中等

💡 怎么选：
· 只做 RAG、想把检索做到极致 → LlamaIndex
· 项目里 RAG 只是其中一块，还要做 Agent 等 → LangChain
· 不会写代码或想 30 分钟搭个 demo → Dify
· 要处理复杂格式的中文文档（扫描件 PDF、表格密集型）→ RAGFlow

📌 两套组合方案

🚀 方案A：极简入门（30 分钟跑通）

✅ 嵌入模型：BGE-M3（开源免费，中文首选）
✅ 向量库：Chroma（pip install 即可）
✅ 框架：LlamaIndex
✅ LLM：DeepSeek（便宜，中文好）

这条组合全部开源免费，没有 API 费用。适合第一次动手搭 RAG 的人——先把流程跑通，理解每个环节在干什么。Chroma 不用部署服务器，数据直接存在本地文件里。

🏗️ 方案B：正经生产（能扛住真实流量）

✅ 嵌入模型：BGE-M3（中文检索）+ text-embedding-3-small（重排序参考）
✅ 向量库：Milvus（分布式部署，支持高并发）
✅ 框架：LlamaIndex + LangChain
✅ LLM：DeepSeek / GPT-4o / Claude Sonnet（按任务复杂度选）
✅ 重排序：BGE-Reranker（开源，中文重排序效果好）

这套组合是"工业级 RAG"的最低配置。相比方案 A，多了重排序（大幅提高检索精度）、分布式向量库（数据量到百万级也不怕）、多模型策略（不同环节用不同模型）。

━━━━━━━━━━━━━━

写在最后

写到这，RAG 这块拼图——从"是什么"到"怎么搭"——就讲完了。八章内容，不算短。但 RAG 这个东西值得花时间搞懂——它不是什么前沿炫技，是大模型从"玩具变成工具"最核心的一块砖。

🚀 RAG 的本质就一句：给大模型配一套"随时能查的资料库"，让它每次回答前先翻资料再说话。

就这么简单。但把"搜得准、找得快、答案有出处"这三件事同时做到，每个环节都得认真对待——选对嵌入模型、切好文档、调好检索参数、写好 Prompt 模板、持续维护知识库。它不是"一招鲜吃遍天"，是一个需要持续打磨的工程体系。
