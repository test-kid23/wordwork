## 写在前面

每次模型更新，公告里都是一堆数字：某基准涨了 11 分，成本降了六成，超越某某旗舰。

看完还是不知道该不该换。因为那些分数是别人任务集上的分数，跟手上这摊活没关系——我们的活是改一个跑不通的脚本、把一份会议记录压成三百字、查一下某个产品这三个月有没有涨价。

判断"要不要换"，只有一条路：**拿自己的三个活跑一遍，看三列数字。**

这篇不长篇分析，直接给一套测法：挑三个覆盖不同能力的任务、一张六列的记录表、一段能直接跑的脚本、三条判断线，以及四个最常见的误测——很多人测完觉得"没区别"，八成是踩了这四个坑之一。

## 一、先把三个事实钉死

省掉铺垫，只留结论：

**① 成本下降不在单价上。** 模型名 `deepseek-flash` 没变，价格表也没动（空闲：输入未命中 1 元/百万 token、命中 0.02、输出 4）。降的是**用量**——同一件事吐的字少了，账单自然下来。官方口径是"缩短任务运行时间与输出长度"，官方之外的权威媒体转述为"多场景 Token 消耗降低超五成"。

**② 分数涨在哪要看清。** 涨得最猛的是动手类：终端操作、程序逆向、多模态 Agent；知识问答类涨得相对少。这一版的取向很清楚——**把事做完**，而不是把题答对。

**③ 框架要跟着升。** 官方点名针对 DeepSeek Harness、腾讯 CodeBuddy、WorkBuddy 做了优化，Harness 要求 0.2.1-rc.1 以上。框架不升，模型的新能力吃不满。

三句话之外的东西，都不用背。剩下的靠实测。

## 二、榜单为什么帮不上忙

不是分数造假，是三个错配：

**错配一：任务不一样。** 榜单跑的是标准化题目，我们的活是"这份表格里的金额为什么对不上"。前者有唯一答案，后者要判断。

**错配二：框架不一样。** 同一个模型在不同 Agent 框架里表现会有可见差距——官方自己都在给特定框架做优化。别人的分数是在他们的壳里跑出来的。

**错配三：取的是上限。** 演示与榜单展示的是"最好能到哪"，不是"平均能到哪"。官方四个案例（故宫、赛车、传送门、Valley of Ages）都是精挑的，拿它当日常产出预期，落差会很大。

所以别问"它多少分"，问"**我这三个活，它能不能一次交对**"。

## 三、测试包：三个任务，覆盖三种能力

挑任务的原则只有一条：**结果能一眼判对错。** 判断不了的活（写文案、做设计），测不出模型差异，只会测出自己的心情。

**任务 A｜压缩类：把长文压成能用的三百字**

输入（直接抄）：给一份 8000 字左右的会议记录或制度文件，指令写：

> 把这份记录压成 300 字以内的摘要。要求：① 保留所有明确的决定和时间节点；② 列出三条待办，每条注明负责人；③ 原文没写的信息不要补，缺就标"未明确"。

**判对错的标准**（30 秒能验完）：
- 有没有编造原文没有的数字或人名 → 编了直接判失败；
- 关键决定漏没漏；
- 待办有没有负责人。

**任务 B｜改代码：修三个 bug，补三个测试**

输入：一段故意埋了三个坑的 Python 函数——时区用本地时间、除法没判零、循环边界差一。

> 这个函数有三个问题：时区处理、除零、边界。修好，并补三个能跑过的测试，用 pytest 写法。

**判对错的标准**：
- `pytest` 能不能一次跑过；
- 修的是不是那三个问题（有没有顺手改坏别处）；
- 测试是不是真的会失败（把修复回滚，测试应该红）。

**任务 C｜联网类：查一件会变的事，给来源**

输入：

> 用搜索查一下 DeepSeek API 的 Search / Fetch 接口现在怎么收费，只要最近三个月的信息。输出 300 字以内，附三个可点开的来源链接。

**判对错的标准**：
- 三条链接能不能打开；
- 日期在三个月内；
- 数字和链接里的原文对得上（最容易翻车的一项——它可能引用半年前的旧价）。

三个任务各自对应一种能力：**长文理解、代码修改、联网核实**。覆盖了日常八成以上的活。

## 四、一张表，只记六列

跑完不要凭感觉，填表：

| 任务 | 一次交付？ | 返工轮次 | 耗时（秒） | 输出 token | 花费（元） |
|------|-----------|---------|-----------|-----------|-----------|
| A 压缩 | ✅ / ❌ | 0 | | | |
| B 改代码 | ✅ / ❌ | 0 | | | |
| C 联网 | ✅ / ❌ | 0 | | | |

六列的道理：

- **一次交付**是质量线——能不能不用人返工；
- **返工轮次**比"交付与否"更细，两轮以内算可接受；
- **耗时**决定它能不能进日常工作流（超过三分钟的任务，人就会走神去干别的）；
- **输出 token** 是成本的真身，比单价重要；
- **花费**最后算，别一开始就算，容易把自己绕进去。

**一个关键动作：把这套结果存档，标上日期和模型版本号。**

因为旧版本调不回来了——模型名没变，底层已经换人。所以这套测试的真正用法不是"新旧对比"，而是**建基线**：今天存一份，下次更新再跑一遍，两份表放一起，差异就出来了。

这一步做完，以后每次更新都不需要看公告也能判断。

## 五、脚本：一次跑完，自动出表

把三个任务存成三个 txt，跑这段脚本，直接输出 CSV：

```python
import csv, time, requests

BASE  = "https://api.deepseek.com"
KEY   = "sk-xxx"          # 换成自己的
MODEL = "deepseek-flash"

# 空闲时段价格（元 / 百万 token）：命中 0.02、未命中 1、输出 4
P_HIT, P_MISS, P_OUT = 0.02, 1.0, 4.0

def run(task_text):
    t0 = time.time()
    r = requests.post(
        f"{BASE}/chat/completions",
        headers={"Authorization": f"Bearer {KEY}"},
        json={"model": MODEL,
              "messages": [{"role": "user", "content": task_text}]},
        timeout=600,
    )
    dt = time.time() - t0
    r.raise_for_status()
    d = r.json()
    u = d["usage"]

    hit  = u.get("prompt_cache_hit_tokens", 0)
    miss = u.get("prompt_cache_miss_tokens",
                 max(u.get("prompt_tokens", 0) - hit, 0))
    cost = (hit * P_HIT + miss * P_MISS + u["completion_tokens"] * P_OUT) / 1e6

    return {
        "sec": round(dt, 1),
        "out_tokens": u["completion_tokens"],
        "cost": round(cost, 4),
        "text": d["choices"][0]["message"]["content"],
    }

rows = []
for name in ["A_压缩", "B_改代码", "C_联网"]:
    task = open(f"tasks/{name}.txt", encoding="utf-8").read()
    res = run(task)
    open(f"out/{name}.md", "w", encoding="utf-8").write(res["text"])
    rows.append([name, res["sec"], res["out_tokens"], res["cost"]])
    print(name, res["sec"], "s", res["out_tokens"], "tok", res["cost"], "元")

with open("result.csv", "w", newline="", encoding="utf-8-sig") as f:
    w = csv.writer(f)
    w.writerow(["任务", "耗时秒", "输出token", "花费元"])
    w.writerows(rows)
```

几点说明：

- `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 是缓存计费的两个口径，**命中与未命中差 50 倍**，所以这段必须分开算，否则成本会算得离谱；
- 输出写到 `out/` 目录，人工再过一遍判断"一次交付"；
- 想跨版本对比，把 CSV 改名存档（如 `result-20261103.csv`），下次同名任务再跑一次。

整段跑完的实际花费通常在一块钱以内——三个任务，各跑一次。

## 六、别人跑出来的三组结果

自己跑之前，可以先看别人的结果建立预期。三组都有公开出处，也都标了局限。

**① 160 字提示词 → 78KB 单文件赛车游戏，不到 6 分钟**

产物：78,568 字节、2,739 行、零外部依赖、零图片素材；换浏览器复验能开局、能计分、撞车能结算。

参考价值：这类"看得见"的活，它在速度和完整度上都够用。注意这是"官方提示词 + 特定题材"的结果，不是随便许愿就能复现。

**② 两个 3D 项目，合计约 6 元**

一组公开测试做了古代开封 3D 探索场景和网页赛车，都是一次性完成，合计花费约 6 元。评语里同时给了短板：人物还是多边形方块，放大经不起推敲。

参考价值：**单个项目的真实成本是几块钱**，这个量级值得拿它做原型。

**③ 精确复刻会翻车**

同一批测试里，复刻埃菲尔铁塔时环境细节（广场、行人、塞纳河）给得很足，唯独铁塔本身"看着不太对"。

参考价值：**擅长氛围，不擅长精确复刻。** 有严格参照物的活，别指望一次成型。

三组结果合起来给的是一个边界：**能自己验证对错的活（游戏能不能玩、场景能不能转），它很强；要人判断像不像、好不好的活，它一般。**

## 七、测完怎么判断：三条线

拿到自己的表，按三条线判断：

**第一条：质量线（先看这个）**

- 3 个任务一次交付 3 个 → **换，别犹豫**；
- 2 个 → 换，剩下的那个单独看；
- 1 个 → 先别整体切，只在新任务上试；
- 0 个 → 不是模型问题，是任务没描述清楚，回到第三步重写指令再测。

**第二条：成本线（跟自己的基线比）**

- 同任务花费降 20% 以上 → 有实感，值得推；
- 持平 → 看质量有没有涨，涨了就换；
- 涨 30% 以上 → 先查是不是档位调高了、上下文变长了、缓存失效了（见下一节）。

**第三条：速度线**

- 同类任务比基线快 20% → 能明显感觉到；
- 差不多 → 别为速度换，为质量换。

三条线打完，结论一般会自己浮出来。真正难判断的是"三条线互相打架"——质量涨了但成本也涨了。这时候看一件事：**涨的那部分钱，是不是换来了一次交付率的提升。** 少返工一轮，省下的时间远超那点 token 钱。

## 八、四个常见误测

这一节比前面所有内容都重要。很多人测完说"没感觉"，基本都是这四条之一。

**误测一：拿 max 档跟默认档比。**

档位调高，思考链变长，token 直接翻几倍。结果就是"新模型又贵又慢"——贵慢是真的，但不是模型的问题，是档位的问题。对比时把档位固定住：要么都用默认，要么都用同一档。

**误测二：改了 prompt 前缀，缓存全失效。**

缓存命中 0.02、未命中 1，差 50 倍。前面加一句"你是资深分析师"，整段前缀变新，缓存归零，成本立刻虚高。对比测试期间，**任务文本一个字都别动**。

**误测三：任务太简单，天花板效应。**

让两版模型都做"把这段翻译成英文"，都能做对，看不出差别，于是得出"没变化"。任务要有难度梯度——至少要有一个会失败的任务，否则测的是自己的题目太软。

**误测四：只跑一次。**

输出长度本身有波动，跑一次就下结论，是在测方差。每个任务至少跑两次，看两次的差距——**如果两次之间差得比两版之间还多，说明这个任务测不出东西**。

## 写在最后

公告可以看，但别拿它做决定。

一个模型值不值得换，答案不在任何榜单里，就在自己那三个活、那张六列表里。花一块钱、半小时，得到的是往后半年每次更新都能复用的判断能力——这套东西一旦建起来，就再也不用等别人测了。

至于"到底强多少"这种问题，本来就答不准。能答准的只有一句：**这批活，它一次交付了几个。**
