## 一、它卖的不是搜索，是"给模型看的搜索结果"

传统搜索 API 返回的东西是给网页用的：一列标题加链接，加一句摘要。模型拿到之后还得自己判断哪条可信、哪条过时、哪条是营销软文——判断不了，只能全读。

这两个接口从设计上就是给模型吃的：

| 维度 | 传统搜索 API | DeepSeek Search |
|------|--------------|-----------------|
| 返回结构 | 标题 + 链接 + 短摘要 | 标题 + 链接 + **短摘要 + 长摘要 + 正文** |
| 质量信号 | 无 | **排序分 + 权威性分级 + 发布时间** |
| 过滤语法 | 有限 | `site:` / `lang:` / `after:` / `before:` / 排除词 |
| 使用成本 | 按次或按量预付 | 按成功次数，5 元 / 千次 |

底层是 DeepSeek 自研的搜索引擎：千亿级网页索引、支持多语言、实时返回。官方特别提到对 **SEO 作弊、GEO 操纵、低质 AIGC** 有识别与过滤机制——这条不是技术细节，是使用体验的关键：搜索结果里少一堆"AI 洗过的垃圾页"，模型的判断负担直接降一半。

## 二、两个接口，先跑通最小例子

鉴权和主 API 完全一致，不用申请新 Key：

```
Authorization: Bearer <DeepSeek API Key>
Content-Type: application/json
```

**Search：**

```bash
curl https://api.deepseek.com/v1/tools/search \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "DeepSeek V4 模型 发布",
    "count": 5,
    "need_content": true
  }'
```

**Fetch：**

```bash
curl https://api.deepseek.com/v1/tools/fetch \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/article"}'
```

Python 版本：

```python
import requests

KEY = {"Authorization": "Bearer sk-xxx"}

# 搜索
r = requests.post(
    "https://api.deepseek.com/v1/tools/search",
    headers=KEY,
    json={"query": "DeepSeek 计费 lang:zh after:2026-10-01", "count": 10},
)
r.raise_for_status()
for item in r.json()["results"]:
    print(item["rerank_score"], item["authority"], item["title"])
    print(item["summary"])

# 抓单页
page = requests.post(
    "https://api.deepseek.com/v1/tools/fetch",
    headers=KEY,
    json={"url": "https://example.com/article"},
)
page.raise_for_status()
print(page.json()["title"], len(page.json()["content"]))
```

两个接口都是只读的，跑失败不会改任何东西——这一点让试错成本很低。

## 三、Search 五个参数，只有两个真重要

| 参数 | 必填 | 默认 | 实际作用 |
|------|------|------|----------|
| `query` | 是 | — | 搜索词，**1～128 个 Unicode 字符**，支持搜索语法 |
| `count` | 否 | 10 | 返回条数，1～50 |
| `need_content` | 否 | false | 是否在 `content` 里返回网页正文 |
| `ori_question` | 否 | — | 用户的原始问题，帮引擎理解意图，同样限 128 字符 |
| `localization` | 否 | "" | 传一个 IP，用于优先返回本地化结果 |

**真正决定效果的是 `query` 和 `need_content`。**

**① `query` 有两个隐性约束。**

一百二十八个字符，看着够用，但很多人习惯把整段需求粘进去——直接 400。正确用法是**关键词式短语**：`DeepSeek 计费 lang:zh after:2026-10-01`，而不是"帮我查一下 DeepSeek 最近的计费调整是怎么回事，我想知道十一月份之后搜索接口收不收钱"。

后者的意图，放进 `ori_question`——不过它同样限 128 字符，所以也别指望拿来装长文。

**② `need_content` 是省钱与省事的开关。**

默认 `false`，此时 `content` 字段恒为空字符串。想看正文必须显式打开。

这里有个容易踩的坑：**打开之后返回的体积会暴涨**。十条结果、每条带正文，可能就是几十万字符。所以在 Agent 里通常分两步——先用 `need_content: false` 拿摘要做筛选，挑出两三条，再对这几条的 URL 单独调 Fetch 取正文。这样既省上下文，也省后面的模型 token。

## 四、返回字段：三个分数决定要不要用

一条结果长这样（节选）：

```json
{
  "rerank_score": 2.4,
  "title": "DeepSeek V4 模型发布",
  "url": "https://example.com/deepseek-v4",
  "snippet": "DeepSeek V4 已上线，支持工具调用与长上下文。",
  "summary": "DeepSeek 发布了 V4 模型。此次发布改进了工具调用与长上下文能力……",
  "content": "",
  "site_name": "Example News",
  "date": "2026-06-01T00:00:00+00:00",
  "authority": 3
}
```

**三个字段值得设阈值：**

| 字段 | 范围 | 判读标准 |
|------|------|----------|
| `rerank_score` | 0～3 | 综合相关性、权威性、时效性；**≥ 1.5 算优质结果** |
| `authority` | 0～4（-1 未知） | **≥ 3 为极权威**，适合直接引用；0～2 要交叉验证 |
| `date` | UTC 时间或 null | 时效敏感的题目（价格、政策、版本号）必须看这一栏 |

**还有两个字段的用法要分清：**

- `snippet` 约 100～200 字符，给界面展示用；
- `summary` 约 600～800 字符，**给模型读用**。

很多人接完接口之后抱怨"模型答得空"，原因就是把 `snippet` 喂进去了。六百字的 summary 才是设计给模型的输入。

一个可抄的过滤逻辑：

```python
good = [r for r in resp["results"]
        if r["rerank_score"] >= 1.5 and r["authority"] >= 3]
```

如果过滤完只剩一两条，说明这条 query 太窄或者题目太新——这时候该换关键词，而不是硬用。

**一个公开观察值得记：** 有人拿同一篇航线首航新闻做过对比——发在省政府网站拿到 `rerank_score` 2.84，发在新闻门户 2.70，发在当事公司官网只有 0.58。内容一样，分值差五倍。

这说明这个分数评估的是**"信源在该话题上的采信度"**，不是"文章写得好不好"。对做内容、做品牌的人来说，这是第一次能直接看见 AI 是怎么给信源打分的——过去这套逻辑完全在黑盒里。

## 五、被低估的部分是搜索语法

这是这套接口最容易被跳过、但最能省事的部分。语法直接透传给搜索引擎，可以组合：

| 语法 | 示例 | 用途 |
|------|------|------|
| `site:` | `DeepSeek site:github.com` | 只在指定站点找 |
| `-site:` | `DeepSeek -site:example.com` | 排除某站 |
| `-` | `DeepSeek -广告` | 排除含某词的页面 |
| `-"..."` | `DeepSeek -"release notes"` | 排除含某短语的页面 |
| `"..."` | `DeepSeek "精确短语"` | 精确匹配短语 |
| `lang:` | `DeepSeek lang:zh,en` | 限定语言 |
| `after:` | `DeepSeek after:2026-10-01` | 只要这个日期之后 |
| `before:` | `DeepSeek before:2026-06-01` | 只要这个日期之前 |

组合起来就是一句话完成"范围 + 时间 + 语言"的限定：

```
DeepSeek 模型 site:github.com OR site:huggingface.co lang:zh after:2025
```

三个最实用的组合：

1. **查版本/价格这类会变的东西**——`after:` 卡住时间，避免读到半年前的旧文；
2. **查官方口径**——`site:` 限定官网或文档站，直接跳过二手解读；
3. **做竞品对比**——`-site:` 排除自家站，`-` 排除"招聘""招商"这类噪音页。

不写这些语法也能用，但加了之后，`rerank_score` 的整体分布会明显变好——这是最直接的体感差异。

## 六、把整条链路换掉：7 个动作变 2 个

回到开头那七个动作。老链路是这样：

**旧：**选搜索源 → 谈额度 → 写解析器 → 处理反爬（代理、重试、UA）→ 清洗正文 HTML → 去重 → 拼进 prompt。

**新：**Search 拿候选 → Fetch 拿正文。

省掉的不只是代码量，而是三类长期维护负担：反爬策略会变、页面结构会变、额度要谈。这三件事现在都在对面。

**三个能直接落地的场景：**

**场景一：给本地 Agent 装联网工具。** 把两个接口注册成工具，模型自己决定什么时候搜。提示词里给一句约束："回答时效性问题前必须先搜，且只引用 `authority ≥ 3` 的结果"。

**场景二：资料汇总。** Search 拿 20 条候选 → 按 `rerank_score` 排序取前 5 → 逐个 Fetch → 让模型做交叉核对。这个流程比"让模型自己一边搜一边读"稳得多，因为筛选和阅读被拆成了两步。

**场景三：RAG 的实时兜底。** 本地知识库没命中时，回落一次 Search。判断逻辑很简单：检索得分低于阈值就走联网，并在回答里标注"以下内容来自实时检索"。

**和"Agent 自带搜索"的关系也要说清。** 在 Harness、Claude Code、Codex 里，工具调用已经会走服务端的 Search / Fetch——这部分现在不用自己接。所以两条路各有用处：

- 想做自己的产品/工作流 → 直接调接口；
- 只用现成 Agent → 享受内置能力，等 11 月 1 日之后它开始计费。

## 七、账怎么算：11 月 1 日起计费

规则不复杂，但有几处容易看错：

| 项目 | 规则 |
|------|------|
| 单价 | **5 元 / 1000 次成功请求**（Search、Fetch 各算各的） |
| 计费口径 | 只有 **HTTP 200 且产生结果**才计费；Search 的 `results` 必须非空，Fetch 必须拿到正文 |
| 不计费的 | 请求失败、搜索无结果、超时 |
| `count` | 只控制条数，**不影响单价**（1 条和 50 条一个价） |
| 限速 | Search **100 QPS**、Fetch **25 QPS**，账号级、互相独立；Fetch 另有目标域名级限速 |
| 生效时间 | **北京时间 2026 年 11 月 1 日 00:00** 起 |

**换算成日常单位：一次成功搜索 = 0.005 元。**

- 一个 Agent 任务平均搜 3～5 次 → **1.5～2.5 分钱**；
- 一天跑 100 个这类任务 → 约 **1.5～2.5 元**；
- 一天 1 万次调用的重度场景 → **50 元**。

跟模型费用比，这个量级基本可以忽略——一次带长上下文的模型调用，往往就比它贵。

**免费窗口要留个记号：** 在 Harness、Claude Code、Codex 里通过服务端工具调用触发的 Search / Fetch，目前不计费，11 月 1 日零点开始按上表收费。这也是"什么时候上生产"的实际分界线：之前是免费试运行，之后每一笔都在账上。

**一个容易混淆的点：** 接口是商业服务，按次收费；而模型权重是另一回事，V4.1 Flash 的权重以宽松许可开源。**别把"开源"理解成"搜索也免费"。**

**什么时候该自建？** 三个信号：调用量稳定在每天十万次以上（自建摊薄成本）、有强定制需求（私有索引、内部文档）、对可用性有硬要求（不能接受单一供应商）。在这三条之外，买比自己搭划算。

## 八、踩坑清单与重试策略

官方错误码是 OpenAI 兼容格式（`param` 恒为 null），按处理方式分三类：

| 状态码 | 含义 | 处理 |
|--------|------|------|
| 400 | 请求不合法（`count` 越界、`query` 超 128 字符、JSON 错） | 改请求，别重试 |
| 401 / 402 | Key 无效 / 余额不足 | 修凭证或充值后再试 |
| 403 | Fetch 被安全策略拒绝 | 换 URL，别重试 |
| 404 | Fetch 拿不到可用内容（不可用、被拦截、无可提取正文） | 不计费，换源 |
| 408 / 429 / 5xx | 超时 / 限流 / 服务端问题 | **退避后重试** |
| 413 | 请求体过大 | 改请求 |

四条实操经验：

1. **404 很常见，并且不收费**——目标站反爬、内容全是 JS 渲染、正文抽不出来，都会落到这一档。批量抓取时要预留失败率，别假设 100% 成功。
2. **429 有两个来源**：账号级 QPS 打满，或者 Fetch 撞上目标域名的限速。后者更隐蔽——总 QPS 没超，但某个站的请求被拦。批量场景按域名分桶、错开时间。
3. **Fetch 的 URL 不能带用户名密码**，长度上限 8192。带认证的页面抓不了，这是设计如此。
4. **`need_content: true` 要慎用在大 count 上**：`count: 50` 加正文，单次响应可能几十万字符，很容易把模型上下文和账单一起打爆。

## 写在最后

把搜索单独拿出来卖，这件事的意义比"多了两个接口"大。

过去搜索是产品的功能，现在它成了基础设施的一部分，和模型、框架并列——三者拼起来，才是"Agent 能干活"的完整条件：模型负责想，框架负责动手，搜索负责知道当下发生了什么。

对开发者，短期是省事：少写一堆解析、少维护一套反爬。
对内容站点，这是个新变量：进来的流量会越来越多是"机器在查资料"，而不是"人在浏览"。
对做 Agent 的人，最实际的提醒只有一句：**11 月 1 日之前把该压测的压测完**，之后每一次成功请求都开始记账。
